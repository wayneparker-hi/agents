# 限界上下文识别与映射工作流

这个工作流帮助团队识别系统的限界上下文，并设计上下文间的关系和通信方式。

## 目标

- 识别并定义限界上下文的清晰边界
- 建立上下文间的协作关系
- 设计上下文映射
- 规划团队组织结构

## 工作流阶段

### Phase 1: 需求收集与业务流程分析
**时长**：1-2 小时

1. 理解项目的核心业务价值
2. 识别主要的业务流程和场景
3. 列出业务中的主要角色和活动
4. 用例分析：每个场景涉及的用例

**输出**：业务流程图、主要场景列表、用例清单

**使用 Agent**：strategic-designer
```
Prompt: 分析这个项目的核心业务价值和主要流程。
提供：
- 业务流程概述
- 主要参与者和活动
- 高层用例分析
```

### Phase 2: 领域语言与概念提取
**时长**：2-3 小时

运行工作坊会议：
1. 与业务人员讨论关键业务概念
2. 提取业务术语和定义
3. 识别概念间的关系
4. 开始建立术语表

**输出**：初步术语表、业务概念图

**使用 Agent**：ubiquitous-language-facilitator
```
Prompt: 帮助团队建立对这些业务术语的统一理解。
提供：
- 术语表模板和示例
- 术语提取方法
- 语言沟通协议
```

### Phase 3: 业务边界识别
**时长**：2-3 小时

使用事件风暴识别业务活动和边界：
1. 识别领域事件（橙色便签）
2. 识别触发事件的命令（蓝色便签）
3. 识别相关聚合（黄色便签）
4. 按照业务相关性分组

**输出**：事件流图、初步聚合清单、边界草图

**使用 Agent**：domain-modeler
```
Prompt: 从这些业务事件和命令识别聚合和上下文边界。
提供：
- 聚合设计指导
- 边界识别标准
- 初步上下文建议
```

### Phase 4: 团队边界与工作组织
**时长**：1 小时

考虑团队结构：
1. 当前团队规模和分布
2. 团队技能和专长
3. 应用康威定律
4. 规划团队与上下文的对应关系

**输出**：团队组织建议、上下文与团队对应表

**使用 Agent**：strategic-designer
```
Prompt: 根据团队结构和上下文边界，设计最优的团队组织。
提供：
- 团队规模考虑
- 康威定律应用
- 特性团队设计
```

### Phase 5: 上下文映射关系设计
**时长**：2-3 小时

设计上下文间的关系：
1. 识别上下文间的依赖
2. 选择映射模式（partnership, customer-supplier 等）
3. 设计通信协议
4. 识别集成点

**输出**：上下文地图、映射关系文档

**使用 Agent**：architecture-advisor
```
Prompt: 设计这些上下文间的协作关系和通信方式。
提供：
- 映射模式选择指南
- 通信模式建议
- 集成策略设计
```

### Phase 6: 技术边界与架构决策
**时长**：1-2 小时

考虑技术实现：
1. 每个上下文的数据独立性
2. 部署和通信方式（单体vs微服务）
3. 技术栈选择
4. 扩展计划

**输出**：架构决策记录、实现路线图

### Phase 7: 验证与冲突解决
**时长**：1 小时

验证识别结果：
1. 检查边界是否合理
2. 解决冲突和不确定性
3. 确认业务人员同意
4. 识别风险和假设

**输出**：已验证的上下文定义、风险清单

### Phase 8: 文档化与总结
**时长**：1 小时

创建最终文档：
1. 限界上下文清单（名称、职责、关键概念）
2. 上下文地图（可视化表示）
3. 术语表（最终版）
4. 约束和假设
5. 下一步行动

**输出**：
- `bounded-contexts.md` - 上下文定义
- `context-map.md` - 上下文关系图
- `glossary.md` - 术语表
- `architecture-decisions.md` - 架构决策

## 配置选项

### --domain（必需）
域的名称或描述（如：电商、SaaS、ERP）
```
/bounded-context-mapping --domain=电商平台
```

### --team-structure（可选）
团队数量和分布
```
--team-structure=分布式:3个城市:15人
```

### --complexity（可选）
系统复杂度评估：简单、中等、复杂
```
--complexity=复杂
```

### --existing-system（可选）
如果是重构现有系统，指定现有问题
```
--existing-system=单体应用,代码混乱,需要重构
```

## 执行参数

### 必需参数
- `--domain`: 业务域描述

### 可选参数
- `--team-structure`: 团队情况
- `--complexity`: 复杂度评估
- `--existing-system`: 现有系统信息
- `--duration`: 工作流时长（默认 2-3 天）

## 成功标准

- [ ] 识别出了所有主要的限界上下文（通常 5-10 个）
- [ ] 每个上下文都有清晰的职责定义
- [ ] 上下文间的关系被明确定义
- [ ] 业务人员认可了上下文边界
- [ ] 术语表包含了所有关键概念
- [ ] 团队组织与上下文对应
- [ ] 创建了上下文地图和文档
- [ ] 识别了主要风险和假设

## 回滚策略

如果发现边界划分不合理：
1. 召集团队讨论具体问题
2. 重新运行 Phase 3（业务边界识别）
3. 调整聚合和边界
4. 更新后续的映射和组织计划
5. 重新验证

## 预期产出

### 文档
- 限界上下文清单和定义
- 上下文地图（图表）
- 统一语言术语表
- 架构决策记录（ADR）
- 风险和假设记录

### 成果物
- 上下文边界清晰，团队理解一致
- 技术团队为详细设计做好准备
- 业务人员认可整体划分

## 注意事项

1. **包含所有利益相关者**
   - 业务分析师、领域专家
   - 技术架构师、开发人员
   - 产品经理

2. **保持迭代心态**
   - 初期边界可能不完美
   - 实现过程中继续细化
   - 定期评审和调整

3. **重点明确**
   - 关注业务价值和边界
   - 不要过度设计
   - 技术细节留给后续

4. **文档可视化**
   - 使用图表而非文字
   - 拍照记录工作坊白板
   - 创建上下文地图
