# DDD 遗留系统重构工作流

这个工作流帮助团队将现有的单体或混乱的系统逐步重构为 DDD 的架构。使用"窒息者"（Strangler）模式实现渐进式重构。

## 目标

- 分析现有系统的问题和边界
- 规划渐进式重构路线图
- 建立新旧系统的集成桥梁
- 最小化重构风险和成本

## 工作流阶段

### Phase 1: 现状评估
**时长**：1-2 天

分析现有系统：
1. 代码结构和代码质量
2. 数据模型和一致性
3. 隐藏的业务边界
4. 技术债务和问题
5. 团队能力和约束

**使用 Agent**：strategic-designer
```
Prompt: 分析这个遗留系统的现状。
提供：
- 代码结构分析
- 隐藏边界识别
- 问题和痛点评估
```

**输出**：系统现状报告

### Phase 2: 问题与目标定义
**时长**：1 天

明确：
1. 最痛苦的问题是什么？
2. 重构的目标是什么？
3. 优先级是什么？
4. 成功标准是什么？

**输出**：目标清单、优先级排序

### Phase 3: 限界上下文识别
**时长**：2-3 天

从现有代码识别隐藏的上下文：
1. 分析代码依赖关系
2. 识别数据库表的分组
3. 找出自然的业务边界
4. 访谈关键人员确认

**使用 Agent**：strategic-designer
```
Prompt: 从这个遗留系统中识别限界上下文。
提供：
- 边界识别方法
- 代码分析指导
- 上下文命名建议
```

**输出**：上下文清单、初步上下文地图

### Phase 4: 重构优先级规划
**时长**：1 天

为每个上下文优先级：
1. 业务价值
2. 技术复杂度
3. 依赖关系
4. 风险评估

**输出**：优先级排序的上下文清单

### Phase 5: 防腐层设计
**时长**：2 天

为即将重构的关键上下文设计防腐层：
1. 定义新旧系统的接口
2. 实现翻译和适配
3. 规划过渡期的双写
4. 设计数据同步机制

**使用 Agent**：architecture-advisor
```
Prompt: 设计新旧系统间的集成防腐层。
提供：
- 防腐层架构
- 数据同步策略
- 双写实现方案
```

**输出**：防腐层设计文档

### Phase 6: 第一个上下文的详细设计
**时长**：3-5 天

按照 DDD 方式详细设计优先级最高的上下文：
1. 使用 bounded-context-mapping 工作流
2. 使用 domain-modeling-workflow 工作流
3. 创建新服务代码框架
4. 规划测试策略

**输出**：完整的上下文设计和代码框架

### Phase 7: 防腐层实现与测试
**时长**：3-5 天

实现防腐层：
1. 实现新旧系统的数据映射
2. 测试数据转换的正确性
3. 测试性能和可靠性
4. 准备流量切换

**输出**：可投产的防腐层代码

### Phase 8: 试验性投产
**时长**：1-2 周

小范围投产：
1. 灰度发布（如 10% 流量）
2. 监控关键指标
3. 收集反馈和问题
4. 逐步扩大流量（30%, 70%, 100%）

**输出**：已验证的新服务

### Phase 9: 验证与反思
**时长**：1 天

验证结果：
1. 功能是否正确？
2. 性能是否符合预期？
3. 有什么问题需要改进？
4. 下一个上下文的重构计划

**输出**：经验总结、改进建议

### Phase 10: 迭代其他上下文
重复 Phase 6-9，逐步迁移其他上下文

### Phase 11: 旧系统归档
**时长**：1 天

当所有关键上下文都已迁移：
1. 确保没有其他系统依赖旧代码
2. 备份旧系统数据
3. 安全删除旧代码
4. 文档和知识转移

**输出**：完成的重构、清理的代码库

## 重构策略选择

### --migration-strategy（必需）

**big-bang**
```
--migration-strategy=big-bang
```
- 一次性大规模重写
- 高风险、快速
- 仅在小系统或时间紧张时选择

**strangler**（推荐）
```
--migration-strategy=strangler
```
- 渐进式重构，保持系统可用
- 风险可控
- 允许学习和调整

**parallel-run**
```
--migration-strategy=parallel-run
```
- 新旧系统并行运行
- 最安全但成本最高
- 适合关键系统

## 执行参数

### 必需参数
- `--legacy-type`: 遗留系统类型（monolith/distributed）
- `--migration-strategy`: 迁移策略（big-bang/strangler/parallel-run）

### 可选参数
- `--timeline`: 预期完成时间（如 6个月、12个月）
- `--team-size`: 团队规模
- `--risk-tolerance`: 风险容忍度（low/medium/high）

## 成功标准

- [ ] 识别了所有主要限界上下文
- [ ] 优先级清晰，风险评估完整
- [ ] 防腐层设计完备
- [ ] 第一个上下文成功重构
- [ ] 防腐层经过充分测试
- [ ] 新系统经过投产验证
- [ ] 团队学到了重构经验
- [ ] 有清晰的后续计划

## 关键风险与缓解

| 风险 | 缓解措施 |
|------|--------|
| 新系统有 bug，影响用户 | 灰度发布、充分测试、快速回滚 |
| 防腐层数据转换错误 | 详细设计、充分测试、数据验证 |
| 团队学习曲线陡峭 | 培训、知识转移、充分支持 |
| 迁移时间过长 | 优先级明确、定期评审、及时调整 |
| 旧系统难以弃用 | 逐步迁移、保持兼容、定期清理 |

## 成功案例模式

新系统成功上线后：
1. 逐步增加功能，而非全部迁移
2. 集中在最痛苦的部分先重构
3. 充分学习后再重构其他部分
4. 定期评审和调整计划

## 输出物

- `legacy-system-analysis.md` - 现状评估报告
- `context-identification.md` - 上下文识别结果
- `refactoring-roadmap.md` - 重构路线图
- `acl-design.md` - 防腐层设计
- `migration-plan.md` - 迁移计划
- `lessons-learned.md` - 经验总结
