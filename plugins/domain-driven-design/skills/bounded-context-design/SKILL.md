# 限界上下文设计

限界上下文是领域驱动设计中最核心的战略模式。它通过明确的边界将不同的领域知识、业务过程和团队组织分离开来，形成独立自治的系统单元。

## When to Use This Skill

- 设计新系统时，需要识别主要的业务领域
- 重构现有系统，需要明确化隐藏的领域边界
- 组织开发团队，需要按照业务领域划分工作
- 解决系统间的通信和集成问题
- 评估系统的可维护性和独立演化能力
- 规划微服务或模块的边界

## Core Concepts

### 1. 限界上下文的定义

限界上下文（Bounded Context）= 边界（Bounded）+ 上下文（Context）

**上下文（Context）**：业务流程中的场景片段。整个业务流程由多个活动组成，随着流程的进行，不同的活动需要不同的角色参与，上下文因此而切换。

**边界（Bounded）**：对上下文的静态划分。用明确的边界将动态的业务流程进行静态切分，保护上下文内部的概念一致性。

**关键洞察**：上下文是业务目标，限界是保护和隔离上下文的边界，避免因业务目标的不单一而带来的混乱与概念的不一致。

### 2. 限界上下文的三个控制力维度

限界上下文并非仅仅是模块、服务或组件，而是通过控制三个维度的边界来应对软件复杂度：

#### A. 业务边界控制

限界上下文首先分离了业务边界，约束不同上下文的领域模型。在同一上下文中，相同的概念有一致的含义。

**示例**：电商系统中的"产品（Product）"
- 在**采购上下文**：关注进价、最小起订量、供货周期
- 在**市场上下文**：关注品质、售价、促销图片、销售类型
- 在**仓储上下文**：关注存放位置、重量、体积、易碎性
- 在**推荐上下文**：关注类别、销量、收藏数、正面评价数

每个上下文有自己的 Product 模型，避免了跨上下文耦合。

#### B. 工作边界控制

限界上下文定义了开发团队的工作边界。理想团队规模遵循"两个披萨规则（Two-Pizza Teams）"，约 7-10 人。

**康威定律**：系统的结构会反映组织的沟通结构。同一限界上下文应该由一个团队负责，不同限界上下文应该由不同团队负责。

**特性团队 vs 组件团队**：
- **特性团队**（推荐）：端对端垂直团队，负责一个领域的完整功能
- **组件团队**：按技术层次组织，但容易导致沟通成本高、整合困难

#### C. 技术边界控制

限界上下文确定了系统架构的应用边界，保证系统层和上下文领域层各自的一致性。不同限界上下文可以采用不同的架构风格和技术决策。

### 3. 限界上下文的四个自治要素

"自治"是限界上下文的核心特征，包含四个相辅相成的要素：

#### A. 最小完备（Minimal Completeness）

**定义**：自治单元履行的职责是完整的，无需针对自己的信息去求助别的自治单元。

**意义**：避免了不必要的依赖关系。每个上下文拥有完成业务价值所需的最小功能集。

**示例**：订单上下文
- ✓ 应该包含：订单创建、验证、确认等完整订单生命周期
- ✗ 不应该包含：商品细节、运费计算（这些属于其他上下文）

#### B. 自我履行（Self-Fulfillment）

**定义**：由自治单元自身决定要做什么。根据自己掌握的信息做出符合自身利益的判断，是否应该履行该职责。

**意义**：避免一个上下文被其他上下文的需求支配。为避免风险，一个上下文只履行其掌握知识范围内的职责。

**示例**：订单上下文可以自我判断
- ✓ 订单是否有效（我有订单规则）
- ✓ 是否应该发送给支付上下文（订单已验证）
- ✗ 支付是否成功（这是支付上下文的判断）

#### C. 稳定空间（Stable Space）

**定义**：减少外界变化对限界上下文内部的影响。上下文拥有自己稳定的内部空间。

**实现方式**：
- 划定分属自己的稳定空间
- 开放空间接口应对外部请求
- 根据依赖关系强弱找到间隙，在最弱之处划分边界

**示例**：订单和评价
- 订单和发货强相关 → 应该在同一上下文
- 订单和评价弱相关 → 可以分离到不同上下文

#### D. 独立进化（Independent Evolution）

**定义**：减少限界上下文的变化对外界的影响。内部实现可以演化，但公共接口必须稳定。

**实现方式**：
- 保证对外公开接口的稳定性
- 考虑版本兼容性和演化
- 大多数消费者使用这些接口，一旦修改就会牵一发而动全身

**示例**：支付上下文向订单上下文提供支付接口
- 支付内部实现可以随意变化
- 但支付接口需要保持兼容（或版本化）

### 4. 上下文的三层识别方法

限界上下文的识别不是一蹴而就，需要从业务边界、工作边界、应用边界三个层次分析：

#### A. 从业务边界识别（第一层）

**步骤 1**：梳理主要业务流程，识别业务活动
- 例如电商平台：浏览-查询-购买-支付-物流-评价

**步骤 2**：抽象业务场景
- 例如：订单管理、支付处理、物流配送、用户评价

**步骤 3**：应用语义和功能分析

**语义相关性**：相同业务概念的活动归为一类
- 例如：创建订单、修改订单、查询订单都涉及"订单"概念

**功能相关性**：相互依赖和关联的活动归为一类
- 例如：订单验证是订单创建的前置条件

**步骤 4**：为业务边界命名
- 名字应该能反映该边界内所有业务活动的共同特征
- 例如：订单上下文、支付上下文、评价上下文

#### B. 从工作边界识别（第二层）

考虑团队组织和沟通成本：
- 同一上下文应该由一个特性团队负责
- 避免一个团队跨多个上下文工作
- 一个上下文可能需要多个团队共同维护，但应该最小化

#### C. 从应用边界识别（第三层）

考虑技术实现和架构：
- 不同上下文可能有不同的技术栈
- 考虑数据存储、通信、部署的独立性
- 确保上下文间的技术隔离

## Patterns & Practices

### 1. 限界上下文识别检查清单

使用这个清单验证识别的上下文是否合理：

**业务合理性检查**
- [ ] 这个上下文代表了一个独立的业务价值流吗？
- [ ] 是否有明确的业务目标？
- [ ] 上下文内的概念是否一致？
- [ ] 与其他上下文的依赖关系清晰吗？

**团队可行性检查**
- [ ] 一个 7-10 人团队能否完整负责这个上下文？
- [ ] 团队需要的技能和知识清楚吗？
- [ ] 是否需要与其他团队频繁沟通？

**技术可行性检查**
- [ ] 上下文的数据模型独立吗？
- [ ] 能否采用不同的技术栈？
- [ ] 与其他上下文的集成方式清晰吗？

### 2. 限界上下文的通用模式

#### 模式 A：单体内的模块化上下文
```
优点：
- 共享数据库，强一致性
- 团队间协作紧密
- 部署简单

缺点：
- 模块间耦合风险
- 难以独立扩展
- 技术选型受限

适用于：
- 团队规模小
- 业务逻辑变化不频繁
- 一致性要求高
```

#### 模式 B：服务化上下文
```
优点：
- 独立部署和扩展
- 技术栈灵活
- 团队真正独立

缺点：
- 分布式事务复杂
- 网络通信成本
- 运维复杂度高

适用于：
- 团队分散
- 业务逻辑差异大
- 扩展需求高
```

#### 模式 C：渐进演化
```
步骤：
1. 开始：单体内清晰的模块边界
2. 中期：通过 ACL（反腐层）保护边界
3. 后期：逐步分离为服务
```

### 3. 常见上下文边界划分示例

**电商系统**
```
一级上下文：
- 商品上下文（Product Catalog）
- 订单上下文（Order）
- 支付上下文（Payment）
- 库存上下文（Inventory）
- 物流上下文（Shipping）
- 评价上下文（Review）
- 推荐上下文（Recommendation）
```

**SaaS 产品**
```
一级上下文：
- 账户上下文（Account）
- 订阅上下文（Subscription）
- 计费上下文（Billing）
- 权限上下文（Authorization）
- 通知上下文（Notification）
```

## Best Practices

1. **领域优先，技术次要**
   - 优先考虑业务含义划分上下文
   - 不要被现有技术决策束缚
   - 一旦找到合理边界，技术自然跟随

2. **迭代和演化**
   - 初期边界可以不完美
   - 随着理解深化，逐步调整
   - 实现会暴露边界问题，及时重构

3. **明确命名和定义**
   - 每个上下文都要有明确的名字
   - 写下上下文的职责和边界
   - 用统一语言定义上下文的关键概念

4. **最小化跨上下文通信**
   - 频繁通信表明边界划分不合理
   - 考虑合并上下文或重新划分

5. **兼容演化**
   - 设计上下文边界时，为未来留出扩展空间
   - 考虑上下文的独立部署能力

6. **文档化**
   - 创建上下文地图（Context Map）
   - 记录上下文间的关系和通信方式
   - 定期审视和更新

## Common Pitfalls

1. **过度微粒化**
   - 陷阱：将太小的功能作为独立上下文
   - 后果：大量上下文间通信，反而增加复杂度
   - 避免：确保每个上下文代表有意义的业务价值

2. **技术驱动的边界**
   - 陷阱：按照技术层次划分上下文（前端、后端、数据库）
   - 后果：违反业务逻辑的自然分离
   - 避免：始终从业务出发

3. **忽视工作边界**
   - 陷阱：规划的上下文与实际团队组织不匹配
   - 后果：团队沟通困难，频繁跨界合作
   - 避免：设计时考虑团队结构

4. **共享数据库**
   - 陷阱：多个上下文共用同一数据库和表
   - 后果：上下文间紧耦合，难以独立演化
   - 避免：每个上下文拥有自己的数据存储

5. **忽视版本兼容性**
   - 陷阱：上下文间的接口变化随意调整
   - 后果：频繁修改消费者代码，引入 bug
   - 避免：设计稳定的公共接口，版本化

6. **边界不清晰**
   - 陷阱：边界模糊，某些功能既可以在 A 也可以在 B
   - 后果：代码位置不确定，难以维护
   - 避免：明确划定每个上下文的责任
