# 事件风暴方法论

事件风暴是一个快速、可视化的协作工作坊，用于探索复杂业务域、识别业务流程、发现关键领域概念。

## When to Use This Skill

- 启动新项目或新领域探索
- 理解复杂的业务流程
- 识别聚合和限界上下文
- 与非技术利益相关者沟通
- 团队共同建立领域知识
- 发现系统隐藏的问题和机遇

## Core Concepts

### 1. 事件风暴的核心思想

事件风暴利用**便签和颜色**代表不同的领域概念，通过大白板上的**可视化排列**快速探索领域。

**三个核心元素**：
1. **事件**（Events）：系统中发生的事情
2. **命令**（Commands）：导致事件发生的动作
3. **聚合**（Aggregates）：保持数据一致性的单元

### 2. 便签颜色与含义

| 颜色 | 含义 | 示例 |
|------|------|------|
| 🟠 橙色 | 领域事件（已发生的事） | OrderCreated, PaymentProcessed |
| 🔵 蓝色 | 命令（导致事件的动作） | CreateOrder, ProcessPayment |
| 🟡 黄色 | 聚合（保持一致性的单元） | Order, Payment, Inventory |
| 🟣 紫色 | 策略/业务规则 | 订单优惠规则、库存算法 |
| 🟢 绿色 | 读模型/查询 | 订单列表、推荐商品 |
| 🔴 红色 | 系统/外部系统 | 支付网关、物流系统 |

### 3. 事件风暴的标准步骤

#### 第 1 步：识别事件（15-30 分钟）
- 参与者自由讨论系统中发生了什么
- 用橙色便签写下所有事件（用过去式）
- 按时间顺序排列在白板上
- 不要解释原因，只记录事实

输出：业务流程的事件序列

#### 第 2 步：识别命令（15-30 分钟）
- 每个事件背后是什么命令触发的？
- 用蓝色便签写下命令（用祈使式）
- 放在对应事件的前面
- 考虑哪些角色可以执行这个命令

输出：事件和导致它们的命令

#### 第 3 步：识别聚合（15-30 分钟）
- 每个命令操作什么聚合？
- 用黄色便签写下聚合名称
- 聚合通常是命令的对象

输出：聚合与命令的关系

#### 第 4 步：识别策略（15-30 分钟）
- 什么业务规则决定了流程的进行？
- 用紫色便签写下重要的业务规则
- 指出规则应用的位置

输出：业务规则的显式化

#### 第 5 步：识别查询（15-30 分钟）
- 系统需要什么信息来做决策？
- 用绿色便签写下读操作
- 指出谁需要这个信息

输出：读写分离的视角

#### 第 6 步：识别外部系统（10-20 分钟）
- 涉及哪些外部系统？
- 用红色便签标记外部系统
- 定义与外部系统的集成点

输出：系统间的依赖关系

#### 第 7 步：识别限界上下文（20-30 分钟）
- 用虚线重新分组相关的概念
- 每组形成一个潜在的限界上下文
- 讨论上下文间的关系

输出：上下文边界和映射

### 4. 工作坊参与者

理想的参与者组合（8-12 人）：
- **业务分析师**：理解业务规则
- **领域专家**：深度领域知识
- **技术架构师**：理解技术可行性
- **开发人员**：实现角度的见解
- **产品经理**：产品目标和优先级

**每个人都应该参与和发言**——这是民主的探索过程。

## Patterns & Practices

### 1. 工作坊的成功要素

**物理环境**
- ✓ 大白板或墙面（最少 4m x 2m）
- ✓ 充足的便签（每种颜色 100+ 张）
- ✓ 粗头笔（便于远距离阅读）
- ✓ 舒适的空间和茶水

**时间安排**
- ✓ 总时长 4-8 小时（取决于复杂度）
- ✓ 中间休息
- ✓ 允许离线讨论但要同步

**气氛营造**
- ✓ 鼓励自由表达
- ✓ 没有坏主意（先记录，后评估）
- ✓ 避免权力差异压制想法

### 2. 便签书写最佳实践

```
❌ 不好的便签
- 模糊：某事发生了
- 被动：订单被创建
- 复杂：当客户选择商品并支付后发生

✓ 好的便签
- 清晰：OrderCreated
- 主动/过去式：OrderLineItemAdded
- 原子化：一张便签代表一个事件
```

### 3. 常见问题处理

**问题 1：太多细节**
- 症状：陷入实现细节，讨论 SQL 和代码
- 解决：提醒重点是业务事件，技术细节后来再谈

**问题 2：不完整的流程**
- 症状：缺少某些路径（异常情况、取消流程）
- 解决：有意识地探索异常场景和边界情况

**问题 3：跳跃式讨论**
- 症状：跳到关键决策，跳过前提步骤
- 解决：可视化帮助人们看到全貌

### 4. 工作坊输出产物

- **领域模型素描**：初步的聚合和实体设计
- **事件流图**：业务过程的可视化
- **上下文地图草图**：潜在的限界上下文
- **术语表初版**：关键概念和定义
- **问题和机会清单**：发现的问题和优化点

## Best Practices

1. **多做几次**
   - 第一次工作坊是高层概览
   - 为重要子域再做一次深入探索
   - 随着理解演化，多次迭代

2. **包容非技术人员**
   - 邀请业务人员和领域专家
   - 使用他们的语言和视角
   - 记录他们的见解和故事

3. **可视化一切**
   - 避免长列表，用空间布局
   - 颜色编码便于扫一眼理解
   - 拍照记录，便于后续参考

4. **从问题开始**
   - 问"为什么做这个？"
   - 理解业务价值，而非仅仅技术需求
   - 发现隐藏的机遇

5. **快速迭代**
   - 不要追求完美
   - 足够好就继续
   - 实现中会发现更多细节

## Common Pitfalls

1. **只有技术人员参与**
   - 导致遗漏业务观点
   - 记录的是"系统应该做什么"而非"业务需要什么"

2. **过度设计**
   - 在工作坊中试图定义所有细节
   - 应该是快速探索，不是完整设计

3. **没有后续行动**
   - 工作坊后，黑板擦掉了，回到原点
   - 应该拍照、记录、跟进

4. **忽视异常流程**
   - 只关注"happy path"
   - 应该主动探索失败、取消、异常场景

5. **非参与式**
   - 少数人讲，多数人听
   - 应该每个人都参与、都发言
