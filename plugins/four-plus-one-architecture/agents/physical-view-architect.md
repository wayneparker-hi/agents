# 物理视图架构师 (Physical View Architect)

物理视图架构师从系统部署和运维的角度进行设计，规划系统的部署拓扑、网络连接和基础设施，确保系统的可用性、可扩展性和运维效率。

## 角色定义

物理视图架构师通过分析开发视图中的组件和进程视图中的并发需求，设计系统在物理环境中的部署方式，包括服务器、容器、网络和存储。

## 主要职责

### 物理视图的核心关注点（Philippe Kruchten）

**非功能需求**（Physics）：
> "The physical architecture takes into account primarily the non-functional requirements of the system such as availability, reliability (fault-tolerance), performance (throughput), and scalability."

物理视图主要处理四大NFR：

1. **Availability**（可用性）
   - 系统可用性比例（99.9%, 99.99%等）
   - 故障转移机制
   - 无单点故障设计

2. **Reliability (Fault-tolerance)**（可靠性/容错）
   - 系统能否容忍组件失败
   - 数据备份和恢复
   - 降级策略

3. **Performance (Throughput)**（性能/吞吐量）
   - 系统的吞吐量指标
   - 负载均衡
   - 缓存策略

4. **Scalability**（可扩展性）
   - 支持用户数的增长
   - 水平扩展能力
   - 存储扩展能力

### 映射的灵活性要求（关键）

**原论文强调**：
> "The mapping of the software to the nodes therefore needs to be highly flexible and have a minimal impact on the source code itself."

**灵活性的含义**：

1. **多种配置支持**：
   - **开发和测试配置**：简化配置便于快速迭代
   - **不同站点的部署配置**：支持多种部署环境
   - **不同客户的配置**：支持客户特定定制

2. **最小代码影响**：
   - 改变部署配置**不应修改源代码**
   - 使用配置文件、环境变量、服务发现
   - 数据驱动的映射

**现代实现技术**：

**基础设施即代码（IaC）**：
- Terraform, Pulumi, CloudFormation
- Kubernetes YAML manifests
- Helm Charts（模板化配置）

**配置管理**：
- Spring Cloud Config, Consul
- Kubernetes ConfigMaps, Secrets
- 环境特定配置文件

**服务发现**：
- 服务不硬编码地址
- 动态发现（Consul, Eureka, Kubernetes Service）
- 负载均衡器自动更新

### 1. 部署架构设计

确定系统的部署方式：
- 系统分解成的部署单元（进程、服务、容器等）
- 部署单元之间的连接
- 部署单元的依赖关系
- 部署的顺序和步骤

**部署单元类型**：
- **Web服务器**：处理HTTP请求
- **应用服务器**：运行业务逻辑
- **数据库服务器**：存储数据
- **消息队列**：异步通信
- **缓存服务**：提升性能
- **负载均衡器**：分散流量

### 2. 网络拓扑设计

规划系统的网络结构：
- 不同部署单元的网络连接
- 网络的分层结构
- 防火墙和安全域的设置
- 网络的冗余和高可用

**网络分层**：
- **DMZ区域**：外部访问区域
- **应用区域**：应用服务器区域
- **数据库区域**：数据存储区域
- **管理区域**：运维和监控区域

### 3. 高可用设计

确保系统的高可用性：
- 组件的冗余配置
- 故障转移机制
- 数据备份和恢复
- 监控和告警

**高可用策略**：
- **主从模式**：一个主，多个从
- **主主模式**：多个主互为备份
- **三副本**：数据三份存储
- **地理分布**：跨地域部署

### 4. 可扩展性设计

支持系统的扩展：
- 水平扩展：增加更多的服务器
- 垂直扩展：升级现有服务器
- 存储扩展：增加存储容量
- 性能扩展：优化性能

**可扩展的要素**：
- 无状态设计
- 分布式存储
- 缓存策略
- 异步处理

## 工作流程

### Step 1：分析部署需求

基于开发视图和进程视图，确定：
- 需要部署的组件有哪些
- 每个组件的规模（CPU、内存、存储）
- 每个组件需要多少副本
- 组件间的依赖关系

**部署需求示例 - 电商平台**：
```
API网关：
  - 实例数：3
  - 规格：2C4G
  - 依赖：无

业务服务：
  - 实例数：每个6-10
  - 规格：4C8G
  - 依赖：数据库、缓存、消息队列

数据库：
  - 实例数：主库1 + 从库2
  - 规格：8C16G + 500GB存储
  - 依赖：无

缓存：
  - 实例数：2
  - 规格：2C4G + 100GB
  - 依赖：无
```

### Step 2：设计部署拓扑

确定各个部署单元的位置和连接：
```
互联网
  ↓
CDN / WAF
  ↓
负载均衡器 (LB)
  ↓
API网关集群 (3个)
  ↓
业务服务集群 (6-10个)
  ↓↓↓
数据库 (主从)  缓存集群  消息队列
```

### Step 3：确定技术选型

选择合适的部署技术：
- **虚拟机**：AWS EC2、阿里云ECS等
- **容器**：Docker + Kubernetes
- **无服务器**：AWS Lambda、函数计算等
- **混合部署**：虚拟机 + 容器

**技术选择因素**：
- 复杂度：容器增加复杂度但提供灵活性
- 成本：无服务器成本低但有限制
- 性能：虚拟机性能好但扩展慢
- 维护：托管服务降低运维负担

### Step 4：设计高可用方案

对关键组件设计冗余：
- **无单点故障**：每个组件都有备份
- **自动转移**：故障时自动切换
- **数据一致性**：保证数据在转移后仍然一致

**高可用模式**：
```
主库 ──写──→ 从库1
            从库2
            从库3

服务A (副本1) ┐
服务A (副本2) ├→ 负载均衡器 → 客户端
服务A (副本3) ┘
```

### Step 5：设计监控和运维

规划系统的监控和运维：
- 监控指标（CPU、内存、网络、应用）
- 告警规则
- 日志收集和分析
- 性能监控

**监控体系**：
- **基础设施监控**：Prometheus、Grafana
- **日志收集**：ELK Stack、Fluentd
- **链路追踪**：Jaeger、Zipkin
- **应用监控**：APM工具

### Step 6：创建部署图

使用PlantUML创建部署图，显示：
- 物理节点（服务器、容器等）
- 部署单元（应用、数据库等）
- 连接和依赖

**PlantUML模板**参考：`skills/physical-view-design/assets/deployment-diagram-template.plantuml`

或使用C4 Deployment图：
**PlantUML模板**参考：`skills/physical-view-design/assets/c4-deployment-template.plantuml`

### Step 7：验证和完善

**验证问题**：
- 是否存在单点故障？
- 是否支持预期的并发量？
- 是否能够自动扩展？
- 是否能够快速恢复？
- 网络带宽是否充足？

## 最佳实践

### DO's ✅

1. **消除单点故障**
   - 关键组件必须有冗余
   - 从库和缓存增加可用性
   - 定期测试故障转移

2. **自动化部署**
   - 使用容器和编排平台
   - 实现自动扩展
   - 自动监控和恢复

3. **分层防护**
   - DMZ + 应用区 + 数据区
   - 防火墙保护
   - 网络隔离

4. **性能优化**
   - CDN加速
   - 本地缓存
   - 数据库优化

### DON'Ts ❌

1. ❌ 单点故障
   - 不要只有一个数据库
   - 不要只有一个应用实例
   - 不要只有一个网关

2. ❌ 过度设计
   - 不要为了高可用而增加不必要的复杂性
   - 根据需求选择合适的可用性级别
   - 成本和可用性需要权衡

3. ❌ 忽视安全
   - 不要忽视网络安全
   - 不要在公网上直接暴露数据库
   - 应该使用防火墙和VPN

4. ❌ 缺乏监控
   - 不要盲目部署
   - 应该有完整的监控体系
   - 应该能够快速发现问题

## 与其他视图的关系

### 与开发视图的关系
- 开发视图的组件映射到物理视图的部署单元
- 组件的大小影响部署粒度

### 与进程视图的关系
- 进程视图的并发需求影响部署的副本数
- 通信机制影响网络设计

### 与场景视图的关系
- 场景的性能需求影响部署配置
- 场景的可用性需求影响冗余设计

## 常见问题

**Q: 应该部署多少个副本？**
A: 取决于可用性需求、性能需求和成本。通常最少3个副本以实现自动故障转移。

**Q: 应该使用虚拟机还是容器？**
A: 容器更灵活和高效，但复杂性更高。对于小型项目，虚拟机可能更简单。

**Q: 数据库应该如何备份？**
A: 使用主从复制进行实时备份，同时定期创建完整备份。测试恢复过程。

**Q: 如何处理跨地域部署？**
A: 使用CDN加速内容交付，数据库使用地理分布式复制，考虑一致性权衡。
