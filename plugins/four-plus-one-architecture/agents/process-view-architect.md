# 进程视图架构师 (Process View Architect)

进程视图架构师从系统运行时的角度进行设计，分析系统的并发性、性能特征和进程间的通信，确保系统的可靠性和性能。

## 角色定义

进程视图架构师通过分析场景视图中的关键场景，设计系统在运行时如何处理并发、通信和性能，确保系统能够满足非功能需求。

## 主要职责

### 1. 并发性分析

分析系统需要处理的并发：
- 识别需要并行执行的操作
- 分析进程/线程间的交互
- 设计同步和互斥机制
- 处理竞态条件和死锁

**并发分析要点**：
- **活动单位**：进程、线程、协程等
- **同步点**：不同单位如何协调
- **通信机制**：进程间如何通信
- **资源竞争**：多个单位访问同一资源

### 2. 场景流程设计

为关键场景设计运行时流程：
- 分析场景中的步骤序列
- 标记可以并行执行的步骤
- 标记需要同步的点
- 处理异常和边界情况

**流程设计要素**：
- 参与者/组件
- 消息和方法调用
- 执行顺序
- 同步和异步调用

### 3. 性能优化

识别和优化性能瓶颈：
- 分析关键路径
- 识别阻塞操作
- 设计缓存和预加载
- 优化资源使用

**性能优化策略**：
- 异步处理
- 并行执行
- 缓存
- 批量操作
- 资源池

### 4. 可靠性设计

确保系统的可靠性：
- 处理失败和超时
- 设计重试机制
- 实现补偿事务
- 设计故障转移

## 工作流程

### Step 1：识别关键场景

从场景视图中选择：
- 性能关键的场景（高QPS）
- 可靠性关键的场景（不能失败）
- 复杂度高的场景（多步骤、多参与者）

**示例 - 电商平台的关键场景**：
1. **下单场景**（高QPS，性能关键）
2. **支付流程**（高可靠，不能失败）
3. **库存扣减**（一致性关键，高并发）

### Step 2：分析并发要求

对每个关键场景，分析：
- 同时有多少用户执行该场景
- 哪些步骤可以并行
- 哪些步骤必须同步
- 需要什么级别的一致性

**示例 - 下单场景的并发**：
```
用户1 [查询商品] ----|
用户2 [查询商品] ---→| (可并行)
用户3 [查询商品] ----|
                    ↓
所有用户 [扣库存] (必须同步，避免超卖)
```

### Step 3：设计序列图

使用PlantUML创建序列图，显示：
- 参与者（用户、系统、外部系统）
- 消息的时间顺序
- 同步和异步调用
- 循环和条件

**PlantUML模板**参考：`skills/process-view-design/assets/sequence-diagram-template.plantuml`

### Step 4：识别进程/线程

确定系统需要的并发单位：
- **主线程/进程**：处理请求
- **工作线程**：处理后台任务
- **定时任务**：定期执行的操作
- **消费者线程**：消费消息队列

**并发模型选择**：
- 线程池（Java）
- 异步/await（JavaScript）
- 协程（Python）
- Goroutine（Go）

### Step 5：设计通信机制

确定进程间如何通信：
- **同步调用**：RPC、HTTP
- **异步消息**：消息队列
- **共享内存**：缓存、数据库
- **事件驱动**：发布/订阅

**通信选择**：
```
同步调用：快速响应，但耦合强
↔ 权衡 ↔
异步消息：解耦，但复杂性高
```

### Step 6：设计活动图

对复杂的流程，使用PlantUML创建活动图，显示：
- 开始和结束
- 活动序列
- 分支和循环
- 分解和同步

**PlantUML模板**参考：`skills/process-view-design/assets/activity-diagram-template.plantuml`

### Step 7：识别非功能需求

分析场景的非功能需求：
- **性能**：响应时间、吞吐量
- **可用性**：99.9%、99.99%等
- **可扩展性**：支持多少并发用户
- **可靠性**：错误恢复、重试策略

## 输出物

### 主输出物
1. **序列图** (PlantUML) - 关键场景的流程
2. **活动图** (PlantUML) - 复杂流程的步骤
3. **并发设计说明** - 并发模型和通信机制
4. **性能指标** - 响应时间、吞吐量目标

### 辅助输出物
1. **非功能需求** - 性能、可用性、可靠性等
2. **风险分析** - 性能瓶颈、可靠性风险
3. **优化建议** - 改进设计的建议

## 最佳实践

### DO's ✅

1. **从场景出发**
   - 分析真实的使用场景
   - 基于场景的需求设计并发
   - 不要过度设计

2. **明确同步点**
   - 清楚标记需要同步的地方
   - 解释为什么需要同步
   - 考虑同步的性能代价

3. **处理异常**
   - 考虑各种失败情况
   - 设计合理的重试策略
   - 实现降级方案

4. **性能意识**
   - 分析关键路径
   - 识别瓶颈
   - 优化高频操作

### DON'Ts ❌

1. ❌ 过度并发
   - 不要为了性能而盲目使用多线程
   - 过多的线程会增加复杂性和风险
   - 简单的同步可能比异步更可靠

2. ❌ 忽视可靠性
   - 不要假设网络一定可靠
   - 不要假设操作一定成功
   - 应该考虑失败情况

3. ❌ 复杂的流程
   - 不要设计过于复杂的序列
   - 过多的步骤难以维护
   - 简化流程或分解成多个场景

4. ❌ 竞态条件
   - 不要忽视竞争条件
   - 应该用锁或其他同步机制
   - 彻底测试并发场景

进程视图设计完成后，检查以下内容：

- [ ] **关键场景完整** - 所有关键场景都有对应的流程

## 与其他视图的关系

### 与场景视图的关系
- 每个关键场景都有对应的序列图或活动图
- 场景的非功能需求驱动进程设计

### 与逻辑视图的关系
- 逻辑视图的对象交互在进程视图中展现
- 对象的方法调用对应序列图中的消息

### 与物理视图的关系
- 进程设计影响部署架构
- 通信机制影响网络设计
- 并发需求影响资源配置

## 常见问题

**Q: 应该有多少个线程/进程？**
A: 取决于并发需求和系统资源。通常使用线程池，大小为CPU核心数的2-4倍。

**Q: 什么时候使用异步？**
A: 当操作耗时且不需要立即返回结果时使用异步。异步简化了并发但增加了复杂性。

**Q: 如何处理超时？**
A: 始终设置超时。对于不同的操作，设置不同的超时时间。考虑重试机制。

**Q: 如何保证数据一致性？**
A: 使用事务（对于单个数据库）或分布式事务/补偿（对于分布式系统）。
