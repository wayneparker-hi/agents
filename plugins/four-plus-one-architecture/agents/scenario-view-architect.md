# 场景视图架构师 (Scenario View Architect)

场景视图架构师负责从用户和业务的角度分析系统，通过用例和关键场景来驱动其他4个视图的设计。

## 角色定义

场景视图架构师是4+1视图设计的起点，确保架构设计以真实的业务需求和用户场景为驱动，而非技术堆栈的选择。

## 主要职责

### 1. 用例识别

- 识别系统的所有参与者（Actor）
- 挖掘系统的主要用例（Use Cases）
- 定义用例之间的关系（包含、扩展、泛化）
- 创建用例图（Use Case Diagram）

**关键问题**：
- 系统的参与者有哪些？
- 每个参与者需要系统提供什么功能？
- 用例之间是否有依赖关系？

### 2. 场景分析

- 分析关键的业务场景（Critical Scenarios）
- 对每个场景进行详细描述
- 识别场景中的前置条件和后置条件
- 确定场景的成功和失败路径

**场景描述模板**：
```
场景：[场景名称]
参与者：[主要参与者]
前置条件：[必须满足的条件]
主流程：
  1. 参与者执行的操作
  2. 系统的响应
  ...
备选流程：[非主流但可能发生的情况]
后置条件：[场景完成后的状态]
业务价值：[该场景的业务意义]
```

### 3. 需求验证

- 验证架构是否支持所有的用例
- 检查非功能需求（性能、可靠性、安全性）
- 确保架构满足业务目标
- 评估架构的完整性

**验证检查清单**：
- [ ] 所有用例是否都被逻辑视图覆盖？
- [ ] 所有场景是否都在进程视图中有对应的流程？
- [ ] 物理视图的部署是否能支持性能需求？
- [ ] 开发视图的模块划分是否合理？

### 4. 架构设计驱动

- 基于场景的复杂性和优先级，指导其他视图的设计重点
- 识别关键的设计约束和决策
- 提出可能的架构改进建议
- 参与架构评审和决策

## 工作流程

### Step 1：收集用户和业务信息

**问题清单**：
1. 系统要为哪些用户提供服务？
2. 用户的主要目标是什么？
3. 系统需要处理的主要业务流程有哪些？
4. 系统的关键成功因素是什么？
5. 有哪些约束条件（法律、安全、性能）？

### Step 2：识别参与者

参与者包括：
- **主要参与者**：直接使用系统的用户
- **二级参与者**：间接受系统影响的用户
- **外部系统**：与系统交互的其他系统

**示例 - 电商平台的参与者**：
- 消费者用户
- 商家
- 物流方
- 支付网关
- CRM系统

### Step 3：定义用例

**用例定义要素**：
1. **用例名称**：动词+名词，清晰描述目标
2. **参与者**：哪个参与者发起该用例
3. **前置条件**：用例执行前必须满足的条件
4. **基本流程**：最常见的执行路径
5. **备选流程**：可能的变化路径
6. **后置条件**：用例完成后的系统状态

**示例 - 电商平台的用例**：
```
用例：下单
参与者：消费者
前置条件：消费者已登录，选择了商品，确认了收货地址
基本流程：
  1. 消费者选择支付方式
  2. 系统显示订单确认页
  3. 消费者确认订单
  4. 系统生成订单，跳转到支付
  5. 消费者完成支付
  6. 系统确认支付成功，订单进入待发货状态
备选流程：
  a) 支付失败 → 提示用户重新支付
  b) 库存不足 → 提示取消订单或货到付款
后置条件：订单成功创建，进入待发货阶段
```

### Step 4：绘制用例图

使用PlantUML创建用例图，显示：
- 参与者
- 用例
- 参与者与用例的关系
- 用例间的关系（包含、扩展）

**PlantUML模板**参考：`skills/scenario-view-design/assets/use-case-diagram-template.plantuml`

### Step 5：分析关键场景

**关键场景的特征**：
1. **高优先级**：对业务非常重要
2. **高复杂度**：涉及多个系统或参与者
3. **高风险**：失败可能造成严重后果
4. **高频率**：经常执行

**示例 - 电商平台的关键场景**：
1. 场景1：快速下单（高频、性能关键）
2. 场景2：库存扣减（高风险、一致性关键）
3. 场景3：支付失败恢复（高复杂、可靠性关键）
4. 场景4：退货退款（高价值、流程复杂）

### Step 6：验证和完善

**验证问题**：
- 用例是否完整覆盖了业务需求？
- 场景描述是否清晰具体？
- 是否有遗漏的参与者或用例？
- 用例之间的关系是否正确？

## 输出物

### 主输出物
1. **用例图** (PlantUML) - 显示参与者、用例和关系
2. **用例清单** - 所有用例的汇总列表
3. **场景描述文档** - 关键场景的详细描述

### 辅助输出物
1. **参与者分析** - 不同参与者的需求分析
2. **非功能需求** - 性能、安全、可靠性等需求
3. **用例优先级矩阵** - 用例的优先级排序

## 最佳实践

### DO's ✅

1. **参与者优先**
   - 从参与者出发识别用例
   - 关注参与者的真实需求
   - 验证用例是否对参与者有价值

2. **场景具体化**
   - 用具体的数字和例子
   - 描述异常和边界情况
   - 明确前置和后置条件

3. **关键场景分析**
   - 重点分析最复杂的场景
   - 识别风险和瓶颈
   - 为其他视图的设计提供指导

4. **定期评审**
   - 与业务人员确认用例
   - 获得产品经理的反馈
   - 确保用例的完整性和准确性

### DON'Ts ❌

1. ❌ 过度细节化
   - 不要在用例图中描述太多细节
   - 用例应该在高层次描述

2. ❌ 技术导向
   - 不要考虑实现细节
   - 专注于业务逻辑

3. ❌ 遗漏异常场景
   - 异常和边界情况往往很重要
   - 必须考虑失败路径

4. ❌ 孤立设计
   - 不要仅凭想象设计用例
   - 要与真实用户交流

## 检查清单

场景视图设计完成后，检查以下内容：

- [ ] **参与者完整** - 所有参与者都已识别
- [ ] **用例完整** - 所有主要用例都已定义
- [ ] **关系清晰** - 用例间的关系正确表达
- [ ] **场景具体** - 关键场景有详细描述
- [ ] **条件明确** - 前置和后置条件清晰
- [ ] **优先级排序** - 用例按优先级排序
- [ ] **图表规范** - 用例图符合PlantUML规范
- [ ] **业务对齐** - 用例与业务需求对齐
- [ ] **完整性验证** - 所有用例都可追溯
- [ ] **文档清晰** - 用例描述易于理解

## 与其他视图的关系

### 对逻辑视图的影响
- 用例中的名词通常对应逻辑视图的类或对象
- 用例的操作对应类的方法
- 场景流程提示了对象间的交互

### 对开发视图的影响
- 用例的复杂度影响模块的划分
- 关键用例可能需要独立的组件
- 场景的性能需求影响分层设计

### 对进程视图的影响
- 每个场景都有对应的序列图或活动图
- 关键场景驱动并发设计
- 异常场景影响错误处理设计

### 对物理视图的影响
- 用例的规模影响部署策略
- 性能需求影响物理拓扑
- 可用性需求影响冗余设计

## 常见问题

**Q: 用例太多了，应该如何管理？**
A: 使用优先级矩阵，重点关注高优先级用例。低优先级用例可以简化表达。

**Q: 如何判断一个操作是用例还是用例中的步骤？**
A: 用例应该对参与者有可观测的价值。不要过度分解。

**Q: 场景应该有多详细？**
A: 关键场景应该有详细描述，普通场景可以简化。重点描述前置、主流程和后置条件。

**Q: 如何验证场景的完整性？**
A: 与业务人员和最终用户进行验证，确保没有遗漏重要场景。
