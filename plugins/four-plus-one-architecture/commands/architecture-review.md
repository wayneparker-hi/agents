# 架构评审工作流 (Architecture-Review Command)

对现有架构进行全面评审和优化的2-3周工作流。

## 工作流概览

这个工作流适用于已有完整4+1架构设计，需要进行全面评审、验证一致性、优化和改进的项目。

### 时间表
```
第1周：架构现状调查和分析
第2周：详细评审和问题识别
第3周：优化建议和行动计划（可选）
```

## 前提条件

✅ 已有完整的4+1架构设计（或至少5个视图中的大部分）

✅ 已有架构文档和图表

✅ 有实施经验（知道设计中哪些有效，哪些有问题）

---

## Week 1: 架构现状调查

### Day 1-2: 整理现有文档

**任务**：收集并整理所有架构文档和图表

```
文档清单：
□ 场景视图（用例图、非功能需求）
□ 逻辑视图（类图、设计说明）
□ 开发视图（包图、组件图、分层说明）
□ 进程视图（序列图、活动图、性能指标）
□ 物理视图（部署图、网络拓扑、高可用方案）
□ 架构决策记录（ADR）
□ 实施指南
□ 代码审查标准

检查：
□ 所有图表都是最新的吗？
□ 文档是否与实际实现一致？
□ 有没有缺失的关键文档？
```

**输出**：
- 现有文档清单
- 文档最新度评分
- 缺失文档清单

---

### Day 3-4: 与团队访谈

**任务**：与开发、运维、产品团队进行访谈

```
访谈问题：

给开发人员：
□ 你认为当前的架构清晰吗？
□ 开发过程中是否遇到了架构问题？
□ 有哪些地方不符合设计？
□ 有什么地方可以改进？

给运维人员：
□ 部署和运维过程如何？
□ 是否有难以维护的地方？
□ 监控和告警配置是否充分？
□ 故障转移是否有效？

给产品经理：
□ 需求有没有变化？
□ 系统性能是否满足预期？
□ 有没有新的需求对架构的影响？
```

**输出**：
- 访谈记录
- 问题清单（优先级排序）
- 意见汇总

---

### Day 5: 代码和文档抽样审查

**任务**：随机抽样审查代码和文档的一致性

```
审查内容：
1. 代码组织
   - 是否遵循包结构？
   - 是否遵循分层规则？

2. 类设计
   - 是否与逻辑视图一致？
   - 是否遵循SOLID原则？

3. 依赖关系
   - 是否存在未预期的依赖？
   - 是否有循环依赖？

4. 文档
   - 代码文档是否完整？
   - 是否有设计意图的说明？
```

**输出**：
- 代码审查样本报告
- 符合度评分
- 发现的问题样本

---

## Week 2: 详细评审

### Day 1-2: 5个视图的一致性检查

**任务**：验证视图间的对齐

```
检查清单：

场景 → 逻辑：
□ 用例中的对象都在逻辑视图中吗？
□ 用例的操作都映射到方法了吗？
□ 非功能需求都有体现吗？

逻辑 → 开发：
□ 所有类都分配到包中了吗？
□ 依赖关系是否单向？
□ 有没有循环依赖？

开发 → 进程：
□ 包的依赖指导了通信设计吗？
□ 并发单位与模块对应吗？
□ 异步处理恰当吗？

进程 → 物理：
□ 并发需求映射到部署规模了吗？
□ 性能需求能否满足？
□ 可用性设计充分吗？
```

**推荐使用Agent**：`/41view-master-architect`

**输出**：
- 视图对齐检查报告
- 一致性评分
- 发现的不一致项

---

### Day 3-4: 非功能需求验证

**任务**：检查是否满足所有非功能需求

```
验证内容：

性能需求：
□ 关键操作的响应时间是否达标？
  - 使用性能测试数据验证
□ 系统QPS是否满足需求？
□ 缓存策略是否有效？

可用性需求：
□ 系统可用率是否达标？
  - 检查故障转移机制
□ RTO和RPO是否满足？
□ 数据备份和恢复流程是否完善？

可扩展性需求：
□ 是否支持水平扩展？
□ 是否支持预期的增长？
□ 有没有明显的瓶颈？

安全性需求：
□ 认证和授权机制是否完善？
□ 数据加密是否充分？
□ 有没有安全漏洞？
```

**输出**：
- 非功能需求满足度报告
- 性能测试数据汇总
- 发现的问题清单

---

### Day 5: 技术债务评估

**任务**：评估当前的技术债务

```
评估维度：

设计层面：
□ 是否存在明显的设计缺陷？
□ 是否有过度设计的地方？
□ 是否有设计不足的地方？

代码层面：
□ 代码质量如何？（圈复杂度、覆盖率等）
□ 有多少遗留代码？
□ 有多少重复代码？

文档层面：
□ 文档是否完整？
□ 文档是否最新？
□ 文档是否易于理解？

运维层面：
□ 部署流程是否自动化？
□ 监控和告警是否充分？
□ 有多少手工操作？

优先级排序：
- P0（阻塞项）：影响用户的bug、严重的性能问题
- P1（高优先）：会逐步恶化的问题、不合规问题
- P2（中优先）：影响维护性的问题
- P3（低优先）：可以后续改进的项目
```

**输出**：
- 技术债务清单
- 按优先级排序的改进项目
- 改进工作量估算

---

## Week 3（可选）: 优化建议和行动计划

### Day 1-2: 优化建议

**任务**：根据评审结果，提出优化建议

```
分类：

立即改进（高风险）：
  - 可用性问题
  - 安全问题
  - 严重的性能问题

短期改进（1-2个月）：
  - 代码质量
  - 文档更新
  - 明显的设计问题

中期改进（3-6个月）：
  - 重构某些模块
  - 引入新的技术
  - 扩展功能

长期改进（6-12个月）：
  - 架构优化
  - 平台建设
  - 技术栈升级

示例建议：
1. 优化下单流程
   - 当前：同步调用，耗时800ms
   - 优化：引入缓存+异步，目标<500ms
   - 工作量：2周
   - 收益：用户体验改善，服务器负载降低

2. 改进高可用
   - 当前：单个数据库实例
   - 优化：主从+自动转移
   - 工作量：1周
   - 收益：可用性从99.5% → 99.95%
```

**输出**：
- 优化建议清单（分类和优先级）
- 每个建议的详细说明
- 工作量和收益估算

---

### Day 3-4: 行动计划

**任务**：制定改进的行动计划

```
行动计划：

第一个月：
 Week 1-2：
   □ 修复P0的可用性问题
   □ 安全审计
   - Owner: 架构师+安全团队
   - Output: 问题修复报告

 Week 3-4：
   □ 代码质量改进
   □ 单元测试覆盖率提升
   - Owner: 开发团队
   - Output: 覆盖率报告

第二个月：
 □ 文档更新
 □ 架构review
 □ 性能优化
 - Owner: 架构师
 - Output: 更新后的文档，优化方案

第三个月及以后：
 □ 执行改进项目
 □ 定期review进度
 - Owner: 项目经理
 - Output: 定期进度报告
```

**输出**：
- 详细的行动计划（时间、人员、产出物）
- 里程碑和关键指标
- 风险评估和缓解措施

---

### Day 5: 总结报告

**任务**：编写完整的评审报告

```
报告内容：

1. 执行摘要（1页）
   - 评审目标
   - 关键发现
   - 建议优先级

2. 现状评估（2-3页）
   - 5个视图的评分
   - 非功能需求满足度
   - 技术债务评估

3. 详细发现（5-10页）
   - 视图一致性问题
   - 关键问题详细说明
   - 代码样本

4. 建议和行动计划（5-10页）
   - 优化建议（分类）
   - 详细的改进计划
   - 工作量和收益

5. 附录
   - 访谈记录
   - 代码审查样本
   - 参考资料
```

**输出**：
- 完整的架构评审报告（20-30页）
- 执行总结（可向管理层汇报）
- 行动计划（可立即执行）

## 评审标准参考

### 视图评分标准

**优秀（4-5分）**：
- 设计清晰完整
- 与实现一致
- 所有视图对齐
- 满足所有需求

**良好（3-4分）**：
- 设计基本清晰
- 大部分与实现一致
- 视图基本对齐
- 满足大部分需求

**一般（2-3分）**：
- 设计不够清晰
- 与实现有较多偏差
- 视图对齐度一般
- 部分需求未满足

**需要改进（1-2分）**：
- 设计不清晰或不合理
- 与实现差异大
- 视图不对齐
- 多个需求未满足

**严重问题（0-1分）**：
- 设计存在严重缺陷
- 与实现方向错误
- 无法支持需求

## 常见问题

**Q: 评审应该由谁主导？**
A: 通常由架构师或技术负责人主导，但需要包括：
- 开发团队代表
- 运维人员
- 产品经理
- 必要时引入外部顾问

**Q: 如何确定优化建议的优先级？**
A: 考虑以下因素：
- 对用户的影响（可用性、性能、安全）
- 实施难度
- 所需资源
- 预期收益

一般来说，影响大、难度小的优先。

**Q: 如果发现了很多问题怎么办？**
A: 这很正常。关键是：
1. 分清优先级（P0/P1/P2/P3）
2. 制定分阶段的改进计划
3. 逐步推进，不要一次性改所有东西
4. 定期检查进度

**Q: 评审中发现的问题可以改架构吗？**
A: 可以，但要：
1. 充分讨论和论证
2. 写下架构决策记录（ADR）
3. 评估对现有实现的影响
4. 制定迁移计划（如果涉及）

## 下一步

评审完成后：
1. 向管理层汇报评审结果
2. 与团队讨论并认可改进计划
3. 开始执行第一阶段的改进
4. 建立定期review机制（每月或每季度）

使用这个工作流，您可以全面了解架构的现状，识别关键问题，并制定有效的改进计划，不断提升系统的质量和可维护性！
