# 逻辑和开发视图快速工作流 (Logical-Development-Workflow Command)

针对已有场景视图，快速设计逻辑和开发视图的3-4周工作流。

## 工作流概览

这个工作流适用于已经有清晰的场景视图（用例和非功能需求），需要快速推进到编码阶段的项目。

### 时间表
```
第1周：逻辑视图设计
第2周：开发视图设计
第3周：检查和调整
第4周：文档和培训（可选）
```

## 前提条件

✅ 已有完整的场景视图：
- 15-30个用例定义
- 关键用例的详细流程
- 非功能需求规范
- PlantUML用例图

✅ 已有架构约束和技术栈决策

---

## Week 1: 逻辑视图设计

### Day 1-2: 领域建模

**任务**：从场景视图提取业务对象

```
方法：
1. 列出每个关键用例的主要对象
2. 识别重复和相似的对象
3. 分类为实体、值对象、聚合
```

**输出**：
- 业务对象清单（20-30个）
- 对象分类表
- 初步的类结构

**推荐使用Agent**：`/logical-view-architect`

---

### Day 3-4: 类结构详细设计

**任务**：为每个业务对象设计类

```
对于每个关键类：
- 列出关键属性
- 定义公开方法
- 标注不变性约束
- 定义状态和转换

示例 - Order类：
  属性：orderId, user, items, status, totalAmount
  方法：addItem(), confirm(), ship(), cancel()
  约束：items不为空, status有效转换
```

**输出**：
- 20-30个关键类的定义
- 方法签名清单
- 约束说明

---

### Day 5: 关系定义和类图

**任务**：定义类间关系，绘制类图

```
关系检查：
- 关联（→）：Order → User
- 聚合（◇）：User ◇ Address
- 组合（◆）：Order ◆ OrderItem
- 继承（▲）：避免过深继承
```

**输出**：
- PlantUML类图（1-3个，按领域分组）
- 多重性标注清单
- 关系验证报告

---

## Week 2: 开发视图设计

### Day 1-2: 模块分解和包结构

**任务**：将逻辑视图的类组织成包

```
方法：
1. 识别功能领域（订单、支付、库存等）
2. 为每个领域创建包
3. 按分层组织子包

示例包结构：
com.example.ecommerce/
├── order/
│   ├── domain/
│   ├── application/
│   ├── infrastructure/
│   └── api/
├── payment/
├── inventory/
└── common/
```

**推荐使用Agent**：`/development-view-architect`

**输出**：
- 包结构文档（树形图）
- 每个包的职责说明
- 类与包的映射表

---

### Day 3-4: 分层架构和依赖管理

**任务**：设计分层结构和管理依赖

```
标准4层架构：
表现层（API Controllers）→ 应用层（Services）
                ↓
业务逻辑层（Domain）→ 数据访问层（Repository）
```

**验证**：
- [ ] 依赖都是单向的
- [ ] 没有循环依赖
- [ ] 层间通信清晰
- [ ] 高内聚低耦合

**输出**：
- 分层架构图
- 依赖关系矩阵
- 循环依赖检查报告

---

### Day 5: 组件图和最终验证

**任务**：绘制组件图，验证整体一致性

```
组件包括：
- 3-5个主要模块
- 清晰的模块边界
- 标注模块依赖
- 接口定义
```

**验证对齐**：
- [ ] 逻辑视图的每个类都在某个包中
- [ ] 包的依赖反映了类的依赖
- [ ] 没有未预期的跨领域依赖

**输出**：
- PlantUML组件图
- PlantUML包图
- 最终的对齐验证报告

---

## Week 3: 检查和调整

### Day 1-2: 内部审查

**任务**：架构师内部审查设计

```
检查清单：
□ 是否遵循SOLID原则
□ 是否符合DDD方法
□ 是否便于独立测试
□ 是否支持所有用例
□ 包结构是否清晰
```

**产出**：
- 改进建议清单
- 需要调整的地方标记

---

### Day 3-4: 团队审查和反馈

**任务**：与开发团队进行设计评审

```
评审内容：
- 开发团队是否理解包结构
- 是否有技术实现的顾虑
- 是否有可以优化的地方
- 是否有不同的想法
```

**记录**：
- 评审意见
- 决策和理由
- 可能需要的调整

---

### Day 5: 最终调整和固化

**任务**：根据反馈调整设计，锁定最终版本

```
调整内容：
- 重组包结构（如果反馈强烈）
- 补充缺失的部分
- 澄清歧义
```

**输出**：
- 最终的设计文档
- 最终的图表
- 设计固化记录

---

## 快速启动检查清单

完成后，使用以下清单进行最终验证：

### 逻辑视图
- [ ] 所有用例对象都映射到类
- [ ] 每个类都有明确的职责
- [ ] 关系定义正确
- [ ] 类图清晰易懂

### 开发视图
- [ ] 所有逻辑类都分配到包
- [ ] 包的分层清晰（通常4层）
- [ ] 依赖是单向的
- [ ] 没有循环依赖
- [ ] 模块边界清晰

### 一致性
- [ ] 逻辑视图和开发视图对齐
- [ ] 包结构能支持所有用例
- [ ] 可以独立测试每个模块

### 文档和准备
- [ ] 有清晰的包结构文档
- [ ] 有实施指南
- [ ] 团队理解架构
- [ ] 已解答所有问题

## 常见问题和快速解决

**Q: 什么时候停止设计，开始编码？**
A: 当你有：
- 完整的包结构
- 所有关键类的定义
- 清晰的分层和依赖
- 团队的同意

通常不需要设计每个细微的方法。细节在编码时会逐步完善。

**Q: 如果设计发现问题怎么办？**
A: 发现问题越早越好。回到Week 3进行调整，比在编码时发现问题成本低得多。

**Q: 是否需要进程视图和物理视图？**
A: 这取决于：
- 如果性能要求高 → 需要进程视图优化
- 如果可用性要求高 → 需要物理视图规划
- 如果只是快速上线 → 可以暂时跳过，后续补充

设计完成后：

3. 定期检查是否偏离设计
4. 记录设计调整和决策

使用这个快速工作流，您可以在3-4周内完成逻辑和开发视图的设计，并准备好开始编码！
