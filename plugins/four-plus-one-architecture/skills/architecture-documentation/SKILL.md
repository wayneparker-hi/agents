# 架构文档编写技能 (Architecture Documentation Skill)

## 概述

好的架构文档是架构设计的最终呈现，也是知识转移和团队协作的基础。架构文档需要清晰、完整、易于理解，能够指导实施和后续的维护。

## 核心概念

### 1. 文档的目标受众

**不同受众的文档需求**：
```
开发人员：
  - 想了解代码应该如何组织
  - 需要包结构、模块依赖清晰
  - 关心如何实现特定功能

架构师：
  - 需要全局视图
  - 关心设计决策和权衡
  - 想了解非功能需求

产品经理：
  - 关心用例和用户流程
  - 需要理解系统容量和限制
  - 想了解可扩展性

运维人员：
  - 关心部署和运行要求
  - 需要监控指标和告警规则
  - 想了解故障恢复过程
```

### 2. 好的文档的特点

```
✅ 完整性：涵盖所有关键方面
✅ 清晰性：易于理解，不含歧义
✅ 准确性：与实际实现一致
✅ 易维护：结构清晰，便于更新
✅ 视觉化：使用图表和流程图
✅ 实用性：提供实际的指导
```

### 3. 文档的生命周期

```
设计阶段      编写阶段      实施阶段      运维阶段
├─ 初稿       ├─ 完整文档   ├─ 代码审查   ├─ 更新维护
├─ 评审       ├─ ADR        ├─ 偏差记录   ├─ 扩展/优化
└─ 反馈       └─ 部署指南   └─ 文档更新   └─ 经验教训
```

### 5. 04-Design-Decisions/ - 架构决策记录 (ADR)

**ADR模板**：
```markdown
# ADR-001: 微服务 vs 单体架构

**日期**: 2024-01-01
**状态**: 已批准
**决策者**: 架构师小组

## 背景
系统需要支持日均1000万订单，需要在扩展性和复杂性之间找到平衡。

## 决策
采用微服务架构，初期分为5个关键服务：
1. 订单服务（OrderService）
2. 支付服务（PaymentService）
3. 库存服务（InventoryService）
4. 用户服务（UserService）
5. 商品服务（ProductService）

## 理由
### 支持微服务的因素 ✅
- 高并发，需要独立扩展
- 业务边界清晰（订单、支付、库存独立）
- 团队可独立开发（可并行）
- 不同服务有不同的扩展需求

### 风险和缓解措施
| 风险 | 缓解措施 |
|------|---------|
| 网络延迟 | 引入缓存，异步处理 |
| 数据一致性 | 使用分布式事务或补偿 |
| 运维复杂性 | 使用Kubernetes简化管理 |
| 初期开发成本 | 优先实现3个核心服务 |

## 替代方案
### 选项1: 单体架构
- 优点：简单，初期快速开发
- 缺点：难以独立扩展，长期维护困难

### 选项2: 混合架构
- 优点：平衡简单性和扩展性
- 缺点：仍需解决后期微服务迁移

## 决策
**选择微服务架构**，理由：
1. 业务需求强烈要求高扩展性
2. 长期收益大于短期成本
3. 团队有微服务经验

## 后续步骤
1. 第1阶段（3个月）：实现3个核心服务
2. 第2阶段（3个月）：实现2个支撑服务
3. 第3阶段（3个月）：优化和灾难恢复

---
```

## 文档的最佳实践

### 1. 写作原则

```
✅ DO:
  - 使用清晰的语言，避免技术术语堆砌
  - 提供具体的例子
  - 使用表格和列表，而不是长段落
  - 对重要概念进行解释

❌ DON'T:
  - 过于冗长（关键部分>10页需要拆分）
  - 留下歧义（使用精确的语言）
  - 混合多个主题（一个文件一个主题）
  - 陈述过时的信息
```

### 2. 视觉化表达

```
✅ 使用：
  - 流程图展示步骤
  - 表格展示对比
  - 代码块展示实现
  - PlantUML图表展示架构

❌ 避免：
  - 长列表（超过7项改为分类）
  - 过多的文字描述（用图表代替）
```

### 3. 文档维护

**保持文档最新**：
```
设计变更 → 更新ADR
代码变更 → 更新实施指南
部署变更 → 更新部署指南
性能变更 → 更新非功能需求

检查清单：
□ 每个代码提交都关联一个设计文档链接
□ 大的设计变更必须更新相应的ADR
□ 每个季度审查一遍文档的准确性
```

## 文档审查清单

文档完成后，进行以下检查：

- [ ] **完整性** - 涵盖所有关键设计决策
- [ ] **准确性** - 与实际设计和实现一致
- [ ] **清晰性** - 易于理解，没有歧义
- [ ] **组织性** - 结构清晰，易于导航
- [ ] **视觉化** - 有足够的图表和流程图
- [ ] **实用性** - 对开发和运维有指导意义
- [ ] **易维护性** - 文档易于更新
- [ ] **一致性** - 术语使用一致
- [ ] **示例** - 有具体的代码示例
- [ ] **反馈** - 经过团队审查并收集反馈
