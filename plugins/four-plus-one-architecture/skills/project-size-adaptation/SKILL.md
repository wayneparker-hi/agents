# 项目规模适应技能

## 概述

Philippe Kruchten在论文中多次强调：**不同规模的项目需要不同的方法**。

特别重要的观察是：
> "We have found that the larger the project, the greater the distance between these views."

本技能指导如何根据项目规模调整4+1视图方法的应用。

---

## 项目规模分类

### 超小型项目（<1K SLOC）

**特征**：
- 单个开发者或小团队（1-2人）
- 开发周期：几天到几周
- 通常是原型、工具、脚本

**4+1应用**：
- **可能完全不需要**正式的4+1
- 如果需要架构文档：单一架构图或场景视图可能足够

**建议**：
- 重点：快速迭代
- 文档：最小化
- 场景：用户故事即可
- 不建议完整的5视图

---

### 小型项目（1K-10K SLOC）

**特征**：
- 小团队（2-5人）
- 开发周期：1-3个月
- 单体应用或简单分布式系统

**4+1应用选择性**：
- ✅ **场景视图**：必需，用例图
- ✅ **逻辑视图**：必需，但可以简化
- ⚠️ **开发视图**：如果结构与逻辑视图相似，可合并
- ❌ **进程视图**：如果只有单进程/单线程，可省略
- ❌ **物理视图**：如果只有单服务器，可省略

**迭代周期**：2-3周

**文档深度**：
- 轻量级文档（10-20页）
- 重点在关键决策而非详细描述
- PlantUML图表为主

**示例项目**：
- 小型Web应用
- 内部工具
- MVP产品
- 中小型移动应用后端

**检查清单**：
- [ ] 有场景视图（用例图）
- [ ] 有基本逻辑视图（核心类）
- [ ] 有部署说明
- [ ] 核心场景都能被支持
- [ ] 文档简洁清晰

---

### 中型项目（10K-100K SLOC）

**特征**：
- 中等团队（5-15人）
- 开发周期：3-12个月
- 微服务或模块化单体

**4+1应用**：
- ✅ **所有5个视图都需要**
- ✅ **完整的迭代过程**
- ✅ **详细的架构文档**

**迭代周期**：4-8周

**迭代次数**：通常3-6次迭代后架构稳定

**视图距离**：
- 逻辑-开发：开始有一定距离
  - 逻辑的类别不完全对应开发的包
  - 需要简单的映射文档
- 进程-物理：可能有多种部署配置

**架构团队**：
- 可能需要兼职架构师或技术负责人
- 或者由资深开发者兼任

**文档深度**：
- 完整架构文档（50-100页）
- 包含所有5个视图详细描述
- 主要非功能需求说明

**示例项目**：
- 中型SaaS应用
- 企业内部系统
- 移动应用后端
- 小型分布式系统

**检查清单**：
- [ ] 5个视图都完整
- [ ] 视图间对齐检查通过
- [ ] 有架构文档（50-100页）
- [ ] 有ADR记录重大决策
- [ ] 迭代4-8周，已进行3-6次迭代
- [ ] 架构已稳定

---

### 大型项目（100K-700K SLOC）

**特征**：
- 大型团队（15-50人）
- 开发周期：1-3年
- 复杂的分布式系统或企业级应用

**4+1应用**：
- ✅ **完整4+1 + 额外关注**
- ✅ **视图距离显著增大**
- ✅ **需要专门的架构团队**

**迭代周期**：6-9个月（论文原始数据）

**视图距离管理**：
这是大型项目的**关键挑战**

#### 逻辑-开发距离

**问题**：逻辑视图的类别不直接对应开发视图的包或层

**示例**（论文ATC系统）：
- 逻辑类别："External Interfaces—Gateway"
- 开发视图实现分布在：
  - 层1及以下：通信协议
  - 层2：通用网关机制
  - 层5：具体网关实现

**管理策略**：
1. 维护**跟踪矩阵**（逻辑-开发映射表）
2. 使用**命名约定**保持关联
3. **自动化验证**（ArchUnit等）
4. **定期评审**（每个迭代）

#### 进程-物理距离

**问题**：复杂的进程到节点/容器映射

**示例**：
- 进程可以分布到多个节点
- 节点可以运行多个进程
- 动态扩缩容
- 故障转移和重新部署

**管理策略**：
1. 使用IaC（Terraform, Kubernetes YAML）记录映射
2. 配置管理系统（ConfigMap, Helm）
3. 自动化部署验证
4. 定期同步检查

**架构团队**：
- 需要专职架构师团队
- 可能有分层责任：
  - 总架构师（Chief Architect）
  - 领域架构师（Domain Architects）
  - 组件架构师（Component Architects）

**文档深度**：
- **总体架构文档**：100-200页
- **ADR库**：关键决策，每个3-5页
- **设计指南**：50-100页
- **跟踪矩阵**：维护在工具中

**示例项目**：
- 大型电商平台
- 金融核心系统
- 电信系统
- 空中交通管制系统

**检查清单**：
- [ ] 5个视图深入且详细
- [ ] 维护跟踪矩阵（逻辑-开发、进程-物理）
- [ ] 视图距离已识别和管理
- [ ] 有架构治理流程
- [ ] 有架构评审委员会
- [ ] 有自动化架构测试
- [ ] 迭代6-9个月
- [ ] 所有主要抽象和映射关系稳定

---

### 超大型项目（>700K SLOC）

**特征**：
- 超大团队（50+人）
- 多年开发周期
- 可能是产品线或平台

**4+1应用**：
- ✅ **分层的4+1**：
  - 企业级4+1（整体系统）
  - 子系统级4+1（每个主要子系统）
  - 组件级4+1（关键组件）

**视图距离**：
- 非常大
- 需要专门的工具和流程管理
- 多个团队之间的协调复杂

**产品线考虑**：
通常是**产品线（Line-of-Product）**，需要：
- 共享基础设施（domain-independent）
- Domain-specific框架
- 变体管理

**架构治理**：
- 正式的架构治理流程
- 架构委员会定期审批
- 架构合规性自动化检查
- 架构演进计划

**文档系统**：
- Wiki或文档平台
- 架构决策库
- 自动生成的视图（从代码）
- 持续更新的跟踪矩阵

**检查清单**：
- [ ] 分层的4+1（企业级+子系统级）
- [ ] 产品线架构定义
- [ ] 完整的架构治理
- [ ] 架构合规性自动化检查
- [ ] 分阶段开发方法
- [ ] 基础设施和框架稳定

## 视图"距离"的含义和管理

### 什么是视图距离

**定义**：
两个视图之间的对应关系不是一对一的，需要额外的映射和翻译。

### 为什么距离会增大

**随着项目规模增大**：

#### 逻辑-开发距离增大
- **小项目**：
  - 一个逻辑类 = 一个文件
  - 逻辑类别 ≈ 包结构
  - 映射显而易见

- **大项目**：
  - 一个逻辑概念分散在多个层
  - 跨越多个包和模块
  - 需要明确的映射表

**原因**：
- 关注点分离（UI、业务、持久化）
- 技术框架要求
- 团队组织结构
- 可扩展性和可维护性需要

#### 进程-物理距离增大
- **小项目**：
  - 一个进程 = 一个服务器/Pod
  - 映射简单直接

- **大项目**：
  - 复杂的映射策略
  - 进程分布到多个节点
  - 节点运行多个进程
  - 动态扩缩容
  - 故障转移和重部署

**原因**：
- 性能和可扩展性需求
- 高可用和容错要求
- 成本优化
- 云原生架构

### 如何管理距离

#### 策略1：维护跟踪矩阵

**逻辑-开发跟踪矩阵示例**：

| 逻辑类别 | 逻辑类 | 开发包 | 开发层 | 备注 |
|---------|-------|-------|-------|------|
| Order Management | Order | order.domain | Domain | 核心聚合根 |
| | | order.api.dto | API | DTO表示 |
| | | order.infrastructure | Infrastructure | 持久化 |
| External Gateways | PaymentGateway | payment.gateway | Layer 5 | 具体实现 |
| | | common.protocol | Layer 1 | 协议支持 |

**好处**：
- 可追踪性强
- 便于代码审查
- 新成员快速上手

#### 策略2：命名约定

**保持逻辑和开发名称的关联**：

```
逻辑：OrderAggregate
  ↓ (对应)
开发：
  ├── order.domain.Order
  ├── order.domain.OrderItem
  ├── order.api.OrderController
  ├── order.api.dto.OrderDTO
  ├── order.application.OrderService
  └── order.infrastructure.JpaOrderRepository
```

**好处**：
- 容易追踪
- IDE搜索便捷
- 自动化检查容易

#### 策略3：自动化验证

**工具示例**：

**ArchUnit（Java）**：
```java
@ArchTest
public static final ArchRule layer_dependencies_are_respected =
    layeredArchitecture()
        .layer("API").definedBy("..api..")
        .layer("Application").definedBy("..application..")
        .layer("Domain").definedBy("..domain..")
        .layer("Infrastructure").definedBy("..infrastructure..")
        .whereLayer("API").mayNotBeAccessedByAnyLayer()
        .whereLayer("Application").mayOnlyBeAccessedByLayers("API")
        .whereLayer("Domain").mayOnlyBeAccessedByLayers("Application", "Infrastructure");
```

**其他工具**：
- Dependency Cruiser（JavaScript）
- Custom Scripts
- 政策作为代码

#### 策略4：定期评审

**评审频率**（基于项目规模）：
- 小项目：每个迭代结束时
- 中项目：每2-3个迭代
- 大项目：**每个迭代都要评审**（因为距离大）

**评审内容**：
- [ ] 所有逻辑类都映射到开发包了吗？
- [ ] 有没有"孤儿"包（开发中有，但逻辑视图中找不到）？
- [ ] 所有进程都映射到物理部署单元了吗？
- [ ] 部署配置与进程需求一致吗？
- [ ] 跟踪矩阵是最新的吗？
- [ ] 发现了新的映射规则吗？

## 迭代策略调整

### 小项目迭代

**周期**：2-3周

**内容**：
- 每次迭代：1-2个新场景
- 快速原型验证
- 最小文档

**稳定标准**：
- 2-3次迭代覆盖所有核心场景
- 架构不再有大变化

### 中项目迭代

**周期**：4-8周

**内容**：
- 每次迭代：3-5个新场景
- 完整的5个视图更新
- 详细文档

**稳定标准**：
- 4-6次迭代后架构稳定
- 所有主要抽象已识别

### 大项目迭代

**周期**：6-9个月（论文数据）

**内容**：
- 每次迭代：一组相关场景（可能10-20个）
- 所有5个视图 + 跟踪矩阵
- 深度文档 + ADR

**稳定标准**：
- 可能需要更多迭代
- 不仅架构元素稳定，映射关系也稳定

**额外活动**：
- 架构评审委员会审批
- 架构合规性检查
- 与其他子系统对齐

### 超大项目迭代

**分阶段方法**：

**Phase 1: 基础设施建立（18-24个月）**
- 建立domain-independent基础设施
- 建立domain-specific框架
- 关键机制和服务
- 目标：建立坚实的架构基础

**Phase 2: 功能迭代（每次6-12个月）**
- 基于稳定基础
- 添加功能
- 可能并行多个子系统
- 遵循产品线架构

## 文档深度调整

### 小项目文档

**核心文档**：
- README：系统概述 + 场景视图
- Architecture.md：简化的逻辑和开发视图

**总页数**：10-20页

### 中项目文档

**完整架构文档结构**（遵循Philippe Kruchten原论文图13）：

1. Scope
2. References
3. Software Architecture
4. Architectural Goals & Constraints
5. Logical Architecture
6. Process Architecture
7. Development Architecture
8. Physical Architecture
9. Scenarios
10. Size and Performance
11. Quality
12. Appendices（术语、缩写、设计原则）

**总页数**：50-100页

### 大型项目文档

**多层文档**：
- **总体架构文档**：100-200页
- **子系统架构文档**：每个50-100页
- **ADR库**：每个决策3-5页
- **设计指南**：50-100页
- **跟踪矩阵**：维护在工具中

**总页数**：可能500+页

### 超大型项目文档

**分布式文档系统**：
- Wiki或文档平台（Confluence, GitBook等）
- 架构决策库（分类、可搜索）
- 自动生成的视图（从代码和配置）
- 持续更新的跟踪矩阵
- 架构演进时间线

## 常见问题

**Q: 我的项目有15K SLOC，应该用哪个规模？**
A: 算小型或中型项目的边界。建议：如果团队<5人，按小型做；如果>5人，按中型做。

**Q: 我们是初创公司，快速迭代很重要。应该简化4+1吗？**
A: 可以，但不要忽视非功能需求。使用Hollow Architecture原型来快速验证关键假设。

**Q: 项目规模大时，怎么管理视图距离导致的复杂性？**
A: 三个关键：自动化（ArchUnit）、文档（跟踪矩阵）、治理（架构评审）。

**Q: 什么时候应该考虑拆分为产品线？**
A: 当>700K SLOC且有明显的可重用基础设施和多个相似产品时。

---

**记住**：方法论应该**适应项目**，而不是项目适应方法论。合理地应用4+1，避免过度设计或设计不足。
