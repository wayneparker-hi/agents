# 应用架构工作流

## 目的

应用架构工作流指导团队从业务需求出发，系统地设计应用架构。这个工作流确保设计的完整性和团队的对齐。

---

## 完整工作流

### 阶段 1：准备和规划（2-3 天）

#### Step 1.1：收集需求

```
参与者：架构师、产品经理、技术负责人

活动：
  □ 理解业务目标和战略
  □ 列出核心的功能需求
  □ 明确主要的用户和使用场景
  □ 识别约束条件（技术、成本、时间）

输出物：
  ├─ 需求文档
  ├─ 约束列表
  └─ 关键问题清单
```

#### Step 1.2：定义质量属性

```
参与者：架构师、质量属性分析师

活动：
  □ 识别关键的非功能需求
  □ 定量化质量属性（性能、可靠性、安全等）
  □ 排序质量属性优先级
  □ 识别可能的冲突

输出物：
  ├─ 质量属性清单
  ├─ 定量化指标
  ├─ 优先级排序
  └─ 冲突分析
```

#### Step 1.3：分析现状

```
如果是现有系统的改造：

参与者：架构师、技术负责人

活动：
  □ 分析当前的系统架构
  □ 识别当前的问题和瓶颈
  □ 评估现有系统的重用价值
  □ 明确改造的范围

输出物：
  ├─ 现状分析文档
  ├─ 问题清单
  └─ 改造范围定义
```

---

### 阶段 2：高层架构设计（3-5 天）

#### Step 2.1：应用边界设计

```
参与者：应用架构师、业务架构师

活动：
  □ 根据业务域划分应用
  □ 定义每个应用的职责
  □ 确定应用的粒度（大小）
  □ 评估应用的独立性

输出物：
  ├─ 应用清单
  ├─ 应用职责描述
  ├─ 应用间的关系图
  └─ 应用边界定义文档
```

#### Step 2.2：应用分组

```
参与者：应用架构师、团队负责人

活动：
  □ 将应用分组（如按业务域、按团队）
  □ 分配应用组给团队
  □ 定义应用组内的通信方式
  □ 规划应用组间的协调机制

输出物：
  ├─ 应用分组清单
  ├─ 应用与团队的映射
  ├─ 应用组间的通信方案
  └─ 团队职责定义
```

#### Step 2.3：集成方案设计

```
参与者：应用架构师、集成设计师

活动：
  □ 分析应用间的通信需求
  □ 评估各种集成模式
  □ 选择最合适的集成模式
  □ 设计应用间的 API 和通信协议

输出物：
  ├─ 应用间通信图
  ├─ 集成模式选择和理由
  ├─ API 规范
  └─ 通信协议文档
```

#### Step 2.4：质量属性平衡

```
参与者：应用架构师、质量属性分析师

活动：
  □ 分析高层设计对质量属性的支持度
  □ 识别可能的冲突
  □ 为每个冲突制定平衡方案
  □ 确保关键属性得到满足

输出物：
  ├─ 质量属性分析报告
  ├─ 冲突识别和平衡方案
  ├─ 关键设计决策记录（ADR）
  └─ 架构权衡分析
```

---

### 阶段 3：详细设计（5-10 天）

#### Step 3.1：应用内部设计

```
参与者：应用团队

活动：
  □ 设计应用的分层（展现层、业务逻辑层、数据层）
  □ 定义应用的模块结构
  □ 设计应用的内部 API
  □ 选择技术栈

输出物：
  ├─ 应用分层架构图
  ├─ 模块设计
  ├─ 内部 API 规范
  └─ 技术栈选择和理由
```

#### Step 3.2：数据架构设计

```
参与者：数据架构师、应用团队

活动：
  □ 设计各个应用的数据模型
  □ 规划数据的分布（哪个应用拥有哪些数据）
  □ 设计跨应用的数据同步
  □ 规划数据库的部署

输出物：
  ├─ 数据模型
  ├─ 数据拓扑图
  ├─ 数据同步方案
  └─ 数据库设计
```

#### Step 3.3：通信和集成细节

```
参与者：集成设计师、应用团队

活动：
  □ 设计具体的 API 接口
  □ 设计错误处理和重试逻辑
  □ 设计故障容错机制
  □ 规划监控和告警

输出物：
  ├─ API 详细设计
  ├─ 错误处理规范
  ├─ 故障容错设计
  └─ 监控方案
```

---

### 阶段 4：验证和审查（2-3 天）

#### Step 4.1：架构审查

```
参与者：架构师、技术负责人、质量部门

活动：
  □ 审查高层设计
  □ 审查应用边界和分组
  □ 审查集成方案
  □ 审查质量属性的支持度
  □ 审查风险评估

输出物：
  ├─ 审查意见清单
  ├─ 需要修改的项目
  └─ 审查通过的确认
```

#### Step 4.2：风险评估

```
参与者：架构师、技术风险专家

活动：
  □ 识别技术风险
  □ 评估每个风险的概率和影响
  □ 制定风险缓解方案
  □ 制定应急预案

输出物：
  ├─ 风险清单
  ├─ 风险等级评估
  ├─ 缓解方案
  └─ 应急预案
```

#### Step 4.3：团队对齐

```
参与者：所有相关团队

活动：
  □ 演示架构设计
  □ 说明设计的理由和权衡
  □ 回答团队的问题
  □ 确保团队理解和同意

输出物：
  ├─ 架构演讲材料
  ├─ Q&A 记录
  └─ 团队的确认
```

---

### 阶段 5：细化和准备实施（3-5 天）

#### Step 5.1：实施计划

```
参与者：架构师、项目经理

活动：
  □ 将架构设计分解为开发任务
  □ 估算工期和成本
  □ 规划实施顺序（关键路径）
  □ 分配资源

输出物：
  ├─ 任务分解
  ├─ 工期和成本估算
  ├─ 实施时间表
  └─ 资源分配
```

#### Step 5.2：标准和规范

```
参与者：架构师

活动：
  □ 定义编码标准
  □ 定义 API 设计规范
  □ 定义部署规范
  □ 定义监控规范

输出物：
  ├─ 编码规范文档
  ├─ API 规范文档
  ├─ 部署规范文档
  └─ 监控规范文档
```

#### Step 5.3：技术栈验证

```
参与者：技术团队

活动：
  □ 验证选定的技术栈是否满足需求
  □ 进行必要的 POC（概念验证）
  □ 识别技术依赖和许可证问题
  □ 准备开发环境

输出物：
  ├─ 技术栈验证报告
  ├─ POC 结果
  ├─ 依赖清单
  └─ 开发环境说明
```

## 时间线示例

```
Week 1:
  ├─ Mon-Tue: 需求收集、质量属性定义
  ├─ Wed: 应用边界设计
  ├─ Thu: 应用分组、集成方案
  └─ Fri: 质量属性平衡、小组评审

Week 2:
  ├─ Mon-Tue: 应用内部设计
  ├─ Wed: 数据架构设计
  ├─ Thu: 通信细节、监控方案
  └─ Fri: 详细设计评审

Week 3:
  ├─ Mon-Tue: 风险评估、架构调整
  ├─ Wed: 正式架构审查
  ├─ Thu: 团队演讲和对齐
  └─ Fri: 实施计划、标准制定

总耗时：3 周（可根据复杂度调整）
```

## 关键决策点

```
决策点 1：应用数量和粒度
  问题：应该划分成多少个应用？应用大小多少合适？
  输入：功能复杂度、团队规模、可维护性目标
  输出：应用列表

决策点 2：集成模式
  问题：应用间应该如何通信？
  输入：应用数量、通信频率、实时性需求
  输出：集成方案

决策点 3：部署策略
  问题：应该用单体还是微服务？
  输入：应用数量、团队规模、运维能力
  输出：部署架构

决策点 4：技术栈
  问题：应该使用什么技术？
  输入：功能需求、团队能力、成本预算
  输出：技术栈选择

决策点 5：SLA 和质量属性
  问题：各个应用的 SLA 应该是多少？
  输入：业务重要性、成本预算
  输出：SLA 定义
```

## 最佳实践

```
1. 早期让所有利益相关方参与
   ❌ "架构师单独设计，最后才演讲"
   ✅ "从需求收集开始邀请所有相关人员"

2. 充分分析权衡
   ❌ "这个方案最优"
   ✅ "这个方案在 X 属性上表现好，但在 Y 上有妥协"

3. 文档化决策
   ❌ "架构只在会议中讨论"
   ✅ "有 ADR（架构决策记录）文档"

4. 风险前置
   ❌ "实施过程中才发现风险"
   ✅ "设计阶段就识别风险并制定方案"

5. 持续改进
   ❌ "设计好就不变"
   ✅ "定期评估和调整设计"
```
