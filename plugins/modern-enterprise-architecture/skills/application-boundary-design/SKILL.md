# 应用边界设计技能

## 概述

应用边界设计是应用架构的基础。清晰的应用边界决定了系统的可维护性、独立性和演进能力。

---

## 核心概念

### 什么是应用边界？

**定义**：应用边界是将相关的功能、数据和逻辑组织在一起的逻辑分组，形成独立的、有清晰职责的系统。

**特征**：
```
应用应该：
  ✓ 有清晰的职责（Responsibility）
  ✓ 有明确的边界（Boundary）
  ✓ 能独立开发（Independent Development）
  ✓ 能独立测试（Independent Testing）
  ✓ 能独立部署（Independent Deployment）
  ✓ 有清晰的接口（Clear Interface）

应用不应该：
  ✗ 职责混乱（混合多个无关的功能）
  ✗ 边界模糊（与其他应用高度耦合）
  ✗ 过度设计（应用过小，管理开销大）
  ✗ 规划不足（应用过大，难以维护）
```

### 应用 vs 服务 vs 模块

```
概念对比：
┌─────────────┬──────────────────┬──────────────────┬──────────────────┐
│ 特征        │ 应用（Application)│ 服务（Service）   │ 模块（Module）   │
├─────────────┼──────────────────┼──────────────────┼──────────────────┤
│ 部署        │ 独立部署          │ 独立部署          │ 随主程序部署     │
│ 通信        │ 网络通信          │ 网络通信          │ 进程内通信       │
│ 开发        │ 独立团队          │ 独立团队          │ 可能共享          │
│ 粒度        │ 中等（100K-1M行） │ 小（10K-100K行）  │ 小（1K-10K行）   │
│ 部署频率    │ 周/月             │ 周                │ 与主程序一致     │
└─────────────┴──────────────────┴──────────────────┴──────────────────┘

选择指导：
  - 应用：最常见的粒度，适合大多数场景
  - 服务：在应用内部，或需要高度独立性时
  - 模块：小的内部组件
```

## 应用边界设计方法

### 方法 1：按业务边界设计（推荐）

**核心思想**：应用的边界应该反映业务的边界。

```
例子：电商系统

业务边界：
  ├─ 订单业务：从用户下单到完成交付
  ├─ 库存业务：库存的管理和预留
  ├─ 支付业务：支付处理和对账
  └─ 配送业务：物流和配送管理

应用设计（应该与业务边界一致）：
  ├─ Order Application（订单应用）
  │  ├─ 订单创建
  │  ├─ 订单修改
  │  ├─ 订单查询
  │  └─ 订单统计
  │
  ├─ Inventory Application（库存应用）
  │  ├─ 库存查询
  │  ├─ 库存预留
  │  ├─ 库存扣减
  │  └─ 库存告警
  │
  ├─ Payment Application（支付应用）
  │  ├─ 支付处理
  │  ├─ 退款
  │  └─ 对账
  │
  └─ Logistics Application（物流应用）
     ├─ 发货管理
     ├─ 配送跟踪
     └─ 异常处理

优势：
  ✓ 业务人员易于理解
  ✓ 团队组织与应用边界对齐
  ✓ 应用演进与业务演进一致
```

### 方法 2：按用户旅程设计

**核心思想**：沿着用户的关键旅程组织应用。

```
例子：电商用户旅程

用户旅程：浏览 → 比较 → 加购 → 支付 → 配送 → 评价

相关的应用：
  ├─ 商品应用：浏览、比较
  ├─ 购物车应用：加购
  ├─ 订单应用：支付、配送管理
  ├─ 支付应用：支付处理
  ├─ 物流应用：配送跟踪
  └─ 评价应用：用户评价

优势：
  ✓ 应用与用户需求对齐
  ✓ 易于理解用户价值
  ✓ 应用的改进直接提升用户体验
```

### 方法 3：按战略重要性分层

**核心思想**：根据业务价值将应用分为不同层级。

```
应用分层：

第 1 层：核心应用（战略性应用）
  ├─ 订单应用：直接贡献收入
  ├─ 库存应用：支撑核心业务
  └─ 推荐应用：提升转化率
  → 最优资源分配、最高质量标准、最频繁的迭代

第 2 层：支撑应用
  ├─ 用户应用：提供基础功能
  ├─ 支付应用：必需但标准化
  ├─ 物流应用：与第三方集成
  └─ 分析应用：数据分析
  → 中等资源分配、标准化支撑、定期优化

第 3 层：平台应用
  ├─ 认证应用：通用、标准化
  ├─ 通知应用：第三方集成
  ├─ 日志应用：基础设施
  └─ 配置应用：系统配置
  → 最少资源分配、尽可能使用现成方案、自动化运维

优势：
  ✓ 资源分配与业务价值对齐
  ✓ 应用治理有层次感
  ✓ 清晰的演进优先级
```

## 应用边界的设计模式

### 模式 1：单体应用（Monolith）

```
特征：
  ├─ 所有功能在一个应用中
  ├─ 共享数据库
  ├─ 进程内通信
  └─ 统一部署

优势：
  ✓ 开发简单
  ✓ 部署简单
  ✓ 通信快速
  ✓ 事务管理简单

劣势：
  ✗ 难以扩展（必须扩展整个应用）
  ✗ 难以独立部署（任何改动都要整体发版）
  ✗ 团队之间容易产生冲突（代码库太大）
  ✗ 技术选择受限（必须统一技术栈）

适用场景：
  ✓ 初创公司（追求快速开发）
  ✓ 小型系统（功能相对简单）
  ✓ 原型验证（快速验证想法）
  ✓ 紧密集成的系统（需要频繁同步）
```

### 模式 2：微服务应用（Microservices）

```
特征：
  ├─ 每个应用一个独立的数据库
  ├─ 应用间通过网络通信
  ├─ 独立部署
  └─ 可以使用不同的技术栈

优势：
  ✓ 独立扩展（可单独扩展关键服务）
  ✓ 独立部署（任何服务改动都可独立发版）
  ✓ 团队独立（每个团队可独立开发）
  ✓ 技术灵活（不同服务可用不同技术）
  ✓ 故障隔离（一个服务故障不影响其他）

劣势：
  ✗ 开发复杂（需要处理分布式系统问题）
  ✗ 部署复杂（需要容器编排、部署流程等）
  ✗ 通信开销（网络通信比进程内通信慢）
  ✗ 数据一致性困难（分布式事务问题）
  ✗ 运维复杂（需要监控多个服务）

适用场景：
  ✓ 大型系统（功能复杂、团队多）
  ✓ 快速迭代（不同功能有不同的迭代速度）
  ✓ 高可用需求（需要故障隔离）
  ✓ 技术多样（不同服务有不同的技术需求）

何时迁移到微服务：
  □ 系统规模达到一定程度（> 50 人团队）
  □ 有明确的应用边界和团队分工
  □ 有成熟的容器和编排技术
  □ 有完善的监控和告警
  □ 有经验丰富的架构和运维团队
```

### 模式 3：模块化单体（Modular Monolith）

```
特征：
  ├─ 逻辑上是多个应用（模块）
  ├─ 物理上是一个应用（共享代码库和部署）
  ├─ 模块间通过接口而非依赖通信
  └─ 可以独立演进模块

优势：
  ✓ 开发相对简单（比微服务简单）
  ✓ 部署简单（单个应用）
  ✓ 通信快速（进程内）
  ✓ 为微服务迁移做准备（清晰的模块边界）

劣势：
  ✗ 部署不够独立（任何模块改动都要整体发版）
  ✗ 扩展不够灵活（必须扩展整个应用）
  ✗ 仍然可能有代码库太大的问题

适用场景：
  ✓ 中等规模系统（功能相对独立但紧密）
  ✓ 团队准备迁移到微服务（过渡阶段）
  ✓ 需要快速迭代但不需要独立部署

架构特点：
  - 应用：1 个
  - 数据库：1 个（或每个模块一个 schema）
  - 通信：进程内接口 + 事件驱动
  - 部署：统一
```

## 设计清单

### Phase 1：识别应用

```
□ 列出所有的业务能力
  ├─ 能力 1：_____________________
  ├─ 能力 2：_____________________
  └─ ...

□ 基于业务边界，初步划分应用
  ├─ 应用 1：______ （包含能力：___, ___）
  ├─ 应用 2：______ （包含能力：___, ___）
  └─ ...

□ 评估应用大小是否合适
  ├─ 太小？（< 10k 行代码）→ 考虑合并
  ├─ 太大？（> 100k 行代码）→ 考虑拆分
  └─ 合适？（10k - 100k 行代码）→ 保持

□ 确认应用能独立开发、测试、部署
  ├─ 应用 1：是/否
  ├─ 应用 2：是/否
  └─ ...
```

### Phase 2：定义应用边界

```
对每个应用，定义：

应用名称：_____________________

□ 职责说明
  这个应用负责什么业务？
  _________________________________

□ 包含的能力
  ├─ 能力 1：_____________________
  ├─ 能力 2：_____________________
  └─ ...

□ 核心概念/实体
  ├─ 实体 1：_____________________
  ├─ 实体 2：_____________________
  └─ ...

□ 数据所有权
  拥有的数据：_____________________
  引用的数据：_____________________

□ 对外接口
  ├─ API 1：_____________________
  ├─ API 2：_____________________
  └─ ...

□ 依赖的其他应用
  ├─ 应用 1：_____________________
  ├─ 应用 2：_____________________
  └─ ...

□ 不负责的内容
  ✗ _____________________
  ✗ _____________________
```

### Phase 3：验证边界

```
对每个应用边界，检查：

□ 内聚性检查
  - 应用内的功能是否相关？
  - 应用是否有单一的核心目的？

□ 耦合度检查
  - 应用间的依赖有多少？
  - 是否有循环依赖？
  - 是否存在紧耦合？

□ 独立性检查
  - 能否独立开发？
  - 能否独立测试？
  - 能否独立部署？
  - 能否独立扩展？

□ 团队对齐检查
  - 是否有对应的团队？
  - 团队大小是否合适？
  - 团队的技能是否匹配？

□ 可维护性检查
  - 应用边界是否清晰？
  - 是否容易理解？
  - 是否容易修改？
  - 是否容易扩展？
```

## 关键建议

1. **从业务开始，而非技术**
   ❌ "我们想用微服务"
   ✅ "业务需要独立的开发和部署，所以我们用微服务"

2. **大小要合适**
   ❌ 应用太小（几千行代码）或太大（超过百万行）
   ✅ 应用 10k-100k 行代码，一个小团队可维护

3. **职责要清晰**
   ❌ 应用职责混乱，包含多个无关的功能
   ✅ 应用有明确的单一目的

4. **边界要稳定**
   ❌ 频繁调整应用边界
   ✅ 定期评估，但不频繁改动

5. **演进要灵活**
   ❌ 初期就用微服务，运维复杂
   ✅ 从单体或模块化单体开始，有需要再迁移

## 关键指标

```
评估应用边界的好坏：

指标 1：应用数量
  目标：3-10 个应用（太多难以协调，太少边界不清）

指标 2：平均应用大小
  目标：20k-50k 行代码

指标 3：应用间依赖数
  目标：平均每个应用依赖 2-3 个其他应用

指标 4：跨应用调用占比
  目标：< 20% 的调用是跨应用的

指标 5：应用发版频率
  目标：不同应用有不同的发版频率（说明独立性好）

指标 6：团队满意度
  目标：团队认为应用边界清晰、职责明确
```
