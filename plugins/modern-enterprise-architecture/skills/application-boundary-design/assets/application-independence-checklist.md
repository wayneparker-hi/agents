# 应用独立性检查清单

本清单帮助您验证应用边界的清晰性和应用的独立性。

## Part 1：应用内聚性检查

### 功能内聚性

```
□ 应用内的所有功能是否相关？
  是 ✅  /  否 ❌

细节检查：
□ 能用一句话清晰地描述应用的目的吗？
  示例：✅ "订单应用管理订单的生命周期"
        ❌ "订单和支付应用"（太模糊）

□ 应用是否包含无关的功能？
  检查点：
  ├─ 是否有多个独立的业务域？
  │  有 ❌ / 无 ✅
  │
  ├─ 是否有"工具类"或"通用模块"不属于核心业务？
  │  有 ❌ / 无 ✅
  │
  └─ 如果有，是否有计划分离它们？
     是 ✅ / 否 ❌

□ 应用的核心概念是否清晰？
  □ 有明确的主要实体吗？（如 Order、OrderItem）
  □ 有明确的业务规则吗？
  □ 有明确的关键流程吗？

功能内聚性评分（1-5）：_____
  1 = 功能混乱，无清晰目的
  5 = 高度内聚，所有功能紧密相关
```

### 数据内聚性

```
□ 应用的数据是否相关？
  是 ✅  /  否 ❌

细节检查：
□ 是否有"孤立"的表与应用核心业务无关？
  示例：❌ 订单应用中有产品推荐表
         ✅ 订单应用中只有订单相关表

□ 数据实体之间是否有很强的关系？
  检查点：
  ├─ 大多数查询涉及多个表吗？
  │  是 ✅ / 否 ❌
  │
  └─ 是否需要复杂的 JOIN？
     是 ✅ / 否 ❌

□ 是否有数据重复或冗余？
  检查点：
  ├─ 是否有同样的数据在多个表中？
  │  是 ❌ / 否 ✅
  │
  ├─ 是否能通过单个查询获得大多数操作需要的数据？
  │  是 ✅ / 否 ❌
  │
  └─ 数据一致性要求是否很高？
     是 ✅ / 否 ❌

数据内聚性评分（1-5）：_____
  1 = 数据混乱，无清晰的所有权
  5 = 高度内聚，数据有清晰的所有权
```

## Part 2：应用间耦合度检查

### 依赖耦合度

```
□ 应用间的依赖数量是多少？

依赖清单：
├─ [ ] 同步依赖（HTTP/RPC 调用）
│  │  应用 1：_________________ 强度：高/中/低
│  │  应用 2：_________________ 强度：高/中/低
│  │  ...
│  └─ 总数：_____ 个
│
├─ [ ] 异步依赖（事件、消息）
│  │  订阅事件：______________ 频率：高/中/低
│  │  发布事件：______________ 订阅者数：_____
│  │  ...
│  └─ 总数：_____ 个
│
├─ [ ] 数据共享依赖（直接访问其他应用的数据库）
│  │  访问的表：______________ 强度：高/中/低
│  │  ...
│  └─ 总数：_____ 个
│
└─ [ ] 代码共享依赖（shared library）
   │  共享库：_________________ 更新频率：高/中/低
   │  ...
   └─ 总数：_____ 个

耦合度评分（1-5）：_____
  1 = 完全独立，无依赖
  2 = 依赖 1-2 个应用
  3 = 依赖 3-5 个应用（中等）
  4 = 依赖 5-10 个应用（高）
  5 = 依赖 10+ 个应用，紧耦合（✗ 应该分割）
```

### 循环依赖检查

```
□ 是否存在循环依赖？

检查方式：
  应用 A → 应用 B → 应用 C → 应用 A（❌ 循环）

检查清单：
□ 直接循环？
  应用 A → 应用 B → 应用 A
  是 ❌ / 否 ✅

□ 间接循环？
  应用 A → 应用 B → 应用 C → 应用 A
  是 ❌ / 否 ✅

□ 通过事件的循环？
  A 发布事件 → B 监听 → B 发布事件 → A 监听
  是 ❌ / 否 ✅

如果存在循环依赖：
  ❌ 这是一个严重的设计问题
  → 立即修复计划
  → 可能需要重新划分应用边界
  → 或引入中介应用
```

### 强耦合检查

```
强耦合的迹象：
□ 应用 A 和 B 的改动经常一起发生？
  经常 ❌ / 偶尔 ⚠️ / 几乎不 ✅

□ 一个应用的改动经常需要另一个应用同时修改代码？
  经常 ❌ / 偶尔 ⚠️ / 几乎不 ✅

□ 两个应用共享相同的代码库或模块？
  是 ❌ / 否 ✅

□ 一个应用依赖另一个应用的内部实现细节？
  是 ❌ / 否 ✅

□ 修改一个应用的 API 会立即影响多个其他应用？
  经常 ❌ / 偶尔 ⚠️ / 几乎不 ✅

强耦合评分（1-5）：_____
  1 = 完全松耦合，可以独立演进
  5 = 高度强耦合，几乎无法分离（✗ 应该合并）
```

## Part 3：应用独立性检查

### 独立开发

```
□ 该应用是否能由一个独立的团队开发？
  是 ✅  /  否 ❌

检查细节：
□ 应用的功能完整吗？
  是 ✅ / 否 ❌
  （不应该依赖其他应用的功能才能实现核心职责）

□ 应用的数据模型完整吗？
  是 ✅ / 否 ❌
  （应该拥有核心数据，而非频繁访问其他应用的数据）

□ 应用的 API 定义清晰吗？
  是 ✅ / 否 ❌
  （其他应用应该通过清晰的 API 调用，而非共享内部模块）

□ 应用是否与特定的团队成员紧密耦合？
  是 ❌ / 否 ✅
  （应该能够被其他团队成员接手）

独立开发评分（1-5）：_____
  1 = 无法独立开发，必须等待其他应用
  5 = 完全独立，随时可以开始开发
```

### 独立测试

```
□ 是否能独立地测试该应用的所有功能？
  是 ✅  /  否 ❌

检查细节：
□ 能否使用 Mock 隔离外部依赖？
  是 ✅ / 否 ❌
  （应该能用 Mock 测试，而不是必须依赖真实的下游应用）

□ 单元测试是否覆盖了大部分代码？
  是 ✅（> 70%）/ 否 ❌（< 50%）

□ 是否能进行端到端测试？
  是 ✅ / 否 ❌
  （应该能在测试环境独立进行完整流程测试）

□ 测试环境是否需要依赖其他应用？
  是 ❌ / 否 ✅
  （如果需要，说明耦合度太高）

□ 是否有专门的测试环境和测试数据？
  是 ✅ / 否 ❌

独立测试评分（1-5）：_____
  1 = 无法独立测试，必须依赖其他系统
  5 = 完全独立，在隔离环境中可测试
```

### 独立部署

```
□ 是否能独立地部署该应用？
  是 ✅  /  否 ❌

检查细节：
□ 应用是否有自己的部署单元（jar、docker image 等）？
  是 ✅ / 否 ❌

□ 部署该应用是否需要同时部署其他应用？
  不需要 ✅ / 需要部分 ⚠️ / 需要很多 ❌

□ 应用的数据库版本是否独立管理？
  是 ✅ / 否 ❌
  （应该有自己的数据库迁移脚本）

□ 应用的配置是否独立管理？
  是 ✅ / 否 ❌
  （应该有自己的配置文件，而不是共享配置）

□ 部署后是否需要其他应用同时发版才能正常工作？
  不需要 ✅ / 需要 ❌
  （如果需要，说明存在硬依赖）

□ 是否能够灰度发布（金丝雀发布）？
  是 ✅ / 否 ❌

独立部署评分（1-5）：_____
  1 = 无法独立部署，必须与其他应用一起
  5 = 完全独立，随时可单独部署
```

### 独立扩展

```
□ 是否能独立地扩展该应用？
  是 ✅  /  否 ❌

检查细节：
□ 应用是否有自己的数据库或数据库 schema？
  是 ✅ / 否 ❌
  （如果共享数据库，扩展会影响其他应用）

□ 应用是否能水平扩展（多实例）？
  是 ✅ / 否 ❌

□ 应用的缓存是否是局部的？
  是 ✅ / 否 ❌
  （分布式缓存会增加复杂性）

□ 是否存在共享的数据库连接池？
  是 ❌ / 否 ✅
  （每个应用应该有自己的连接池）

□ 应用的存储（数据库、缓存）是否能独立扩容？
  是 ✅ / 否 ❌

独立扩展评分（1-5）：_____
  1 = 无法独立扩展
  5 = 完全独立，可单独扩容
```
