# 应用边界设计决策矩阵

本工具帮助您在多个应用边界方案中做出最优决策。

## 应用分割决策矩阵

### 何时应该分割应用？

**评估因素：**

```
评估项               │ 权重 │ 选项 A（保持）│ 选项 B（分割）
────────────────────┼──────┼──────────────┼────────────
当前代码行数         │ 20%  │ < 150k       │ > 150k ✓
                     │      │              │
功能独立性           │ 15%  │ 紧密耦合     │ 相对独立 ✓
                     │      │              │
团队规模             │ 15%  │ < 5 人       │ > 5 人 ✓
                     │      │              │
部署频率差异         │ 15%  │ 相同         │ 差异大 ✓
                     │      │              │
技术栈需求           │ 10%  │ 相同         │ 不同 ✓
                     │      │              │
数据库大小           │ 10%  │ < 10GB       │ > 10GB ✓
                     │      │              │
缺陷率               │ 5%   │ < 5/kloc     │ > 5/kloc ✓
────────────────────┴──────┴──────────────┴────────────
```

**评分方法：**

```
1. 为每一项填写适用分数（1-5）
2. 将分数乘以权重
3. 汇总所有加权分数
4. 根据结果判断

总分解释：
  < 15 分：应该保持合并状态 ✅
  15-20 分：需要评估，可以两种方案
  20-25 分：应该考虑分割
  > 25 分：强烈建议分割 ✅
```

## 应用分割方案对比表

**案例：某电商系统（目前单体，350k 行代码，7 人团队）**

### 方案 1：保持单体

```
结构：
  └─ 电商单体应用（350k 行）
     ├─ 订单模块
     ├─ 库存模块
     ├─ 支付模块
     ├─ 用户模块
     └─ 推荐模块

评估：
  维度                │ 分数 │ 评价
  ──────────────────┼──────┼──────
  开发时间            │ 5    │ 快速
  运维复杂度          │ 5    │ 简单
  部署风险            │ 4    │ 较高（整体部署）
  团队协调            │ 2    │ 困难（多团队共维）
  独立扩展            │ 1    │ 无法扩展
  技术灵活性          │ 2    │ 受限
  ─────────────────────────────────
  总体适用性          │ 19   │ 可以，但有压力

优势：
  ✅ 开发简单
  ✅ 部署简单
  ✅ 运维成本低
  ✅ 事务管理简单

劣势：
  ❌ 多团队冲突频繁
  ❌ 无法快速迭代
  ❌ 无法独立扩展
  ❌ 编译时间长

建议：短期可行，但长期不可持续
```

### 方案 2：按业务域分割（5 个应用）

```
结构：
  ├─ 订单应用（90k，订单团队，2 人）
  ├─ 库存应用（60k，库存团队，1 人）
  ├─ 支付应用（50k，支付团队，1 人）
  ├─ 用户应用（70k，用户团队，2 人）
  └─ 推荐应用（80k，推荐团队，1 人）

评估：
  维度                │ 分数 │ 评价
  ──────────────────┼──────┼──────
  开发时间            │ 3    │ 中等（初期复杂）
  运维复杂度          │ 2    │ 复杂
  部署风险            │ 3    │ 中等（隔离故障）
  团队协调            │ 5    │ 清晰（团队对齐）
  独立扩展            │ 5    │ 完全独立
  技术灵活性          │ 4    │ 良好
  ─────────────────────────────────
  总体适用性          │ 22   │ 推荐

优势：
  ✅ 团队明确对齐
  ✅ 可以独立扩展
  ✅ 快速迭代
  ✅ 故障隔离
  ✅ 技术多样

劣势：
  ❌ 运维成本高
  ❌ 开发复杂度高
  ❌ 需要容器/K8s 经验
  ❌ 数据一致性困难

建议：长期最优，需要投入学习成本
```

### 方案 3：混合方案（3 个应用）

```
结构：
  ├─ 订单与库存应用（150k，1 个 4 人团队）
  │  ├─ 订单模块
  │  └─ 库存模块
  │
  ├─ 支付与用户应用（120k，1 个 2 人团队）
  │  ├─ 支付模块
  │  └─ 用户模块
  │
  └─ 推荐应用（80k，推荐团队，1 人）

评估：
  维度                │ 分数 │ 评价
  ──────────────────┼──────┼──────
  开发时间            │ 4    │ 中等偏快
  运维复杂度          │ 3    │ 中等
  部署风险            │ 4    │ 较低
  团队协调            │ 3    │ 中等（有些模块跨团队）
  独立扩展            │ 3    │ 部分独立
  技术灵活性          │ 3    │ 中等
  ─────────────────────────────────
  总体适用性          │ 20   │ 可以接受

优势：
  ✅ 比单体复杂度低
  ✅ 比完全微服务简单
  ✅ 成本平衡
  ✅ 逐步演进的基础

劣势：
  ❌ 某些应用仍然过大
  ❌ 某些团队跨应用维护
  ❌ 不如完全微服务灵活

建议：过渡方案，为未来分割预留空间
```

## 团队与应用匹配决策表

### 当前团队配置

```
团队组成：
  ├─ 订单团队：3 人（李、王、张）
  ├─ 库存团队：1 人（刘）
  ├─ 支付团队：1 人（陈）
  ├─ 用户团队：1 人（杨）
  └─ 推荐团队：1 人（黄）

团队能力：
  订单团队：
    └─ 熟悉订单业务，可以独立开发

  库存团队：
    └─ 库存专家，但人力有限

  支付团队：
    └─ 支付专家，但人力有限

  用户和推荐团队：
    └─ 个人团队，业务能力强，但维护压力大
```

### 应用分配方案

**方案 A：直接对应（完全微服务）**

```
应用分配：
  ├─ 订单应用 ← 订单团队（3 人）✅
  ├─ 库存应用 ← 库存团队（1 人）⚠️ 人力不足
  ├─ 支付应用 ← 支付团队（1 人）⚠️ 人力不足
  ├─ 用户应用 ← 用户团队（1 人）⚠️ 人力不足
  └─ 推荐应用 ← 推荐团队（1 人）⚠️ 人力不足

问题：
  ❌ 库存、支付、用户应用都是 1 人，风险大
  ❌ 人员离职会导致应用无人维护
  ❌ 无法快速响应突发情况

不推荐此方案
```

**方案 B：合并支撑应用（推荐）**

```
应用分配：
  ├─ 订单应用 ← 订单团队（3 人）✅
  │  ├─ 订单模块
  │  └─ 库存模块（与订单紧密相关）
  │
  ├─ 支付与用户应用 ← 2 人团队
  │  ├─ 支付模块
  │  └─ 用户模块
  │  （需要补充 1 人）
  │
  └─ 推荐应用 ← 推荐团队（1 人）
     └─ 推荐模块
        （视情况补充 1 人或合并）

优势：
  ✅ 团队规模更合理（2-3 人）
  ✅ 可以快速响应
  ✅ 人员风险降低
  ✅ 仍能独立演进

建议：优先采用此方案
```

**方案 C：渐进式微服务化**

```
第 1 阶段（现在）：
  └─ 订单应用（包含库存）← 3 人
  └─ 支付与用户应用 ← 2 人

第 2 阶段（6 个月后，增加 2 人）：
  ├─ 订单应用 ← 2 人
  ├─ 库存应用 ← 1 人
  ├─ 支付应用 ← 1 人
  ├─ 用户应用 ← 1 人
  └─ 推荐应用 ← 1 人

优势：
  ✅ 逐步演进，降低风险
  ✅ 学习微服务运维
  ✅ 人员有时间适应

建议：最平衡的方案
```

## 应用分割检查清单

在实施分割决策前，检查以下项目：

```
□ 架构设计
  ├─ □ 已清晰定义新应用的职责和边界
  ├─ □ 已确认应用间的依赖关系
  ├─ □ 已规划应用间的通信方式（API、事件等）
  ├─ □ 已评估是否有循环依赖
  └─ □ 已制定数据分配计划（每个应用的数据）

□ 团队和组织
  ├─ □ 已分配明确的团队负责人
  ├─ □ 已确认团队规模足够
  ├─ □ 已规划团队沟通机制
  ├─ □ 已进行跨团队协调培训
  └─ □ 已建立清晰的决策流程

□ 技术准备
  ├─ □ 已选择容器化方案（Docker）
  ├─ □ 已选择编排方案（K8s 或类似）
  ├─ □ 已建立 CI/CD 流程
  ├─ □ 已建立监控和告警系统
  ├─ □ 已建立日志聚合系统
  ├─ □ 已建立链路追踪系统
  └─ □ 已建立部署规范

□ 代码准备
  ├─ □ 已重构代码以清晰分离关注点
  ├─ □ 已提取共享代码到独立库
  ├─ □ 已定义清晰的应用 API 契约
  ├─ □ 已实现 API 版本管理
  └─ □ 已完善应用的测试套件

□ 数据库准备
  ├─ □ 已规划数据分割方案
  ├─ □ 已实现数据库迁移工具
  ├─ □ □ 已规划数据同步机制
  ├─ □ 已备份原数据库
  └─ □ 已制定数据一致性验证方案

□ 迁移计划
  ├─ □ 已制定详细的迁移步骤
  ├─ □ 已估算迁移时间
  ├─ □ 已规划灰度迁移方案
  ├─ □ 已制定回滚方案
  └─ □ 已计划验证和测试

□ 风险评估
  ├─ □ 已识别关键风险
  ├─ □ 已制定风险缓解计划
  ├─ □ 已准备应急预案
  └─ □ 已获得高管支持

任何未完成的项目都表示存在风险，应该延期或加速准备。

建议：所有项目都需要完成才能开始分割
```
