# 应用大小评估指南

## 概述

应用大小是应用边界设计的核心指标。应用过小导致管理开销大，应用过大导致难以维护。本文提供科学的评估方法和实践指南。

---

## 应用大小的多维度衡量

### 维度 1：代码行数（Lines of Code）

**经验数据：**

```
代码行数范围     | 应用分类         | 特点
─────────────────┼──────────────────┼─────────────────────────
< 10k            | 微型应用         | 太小，开销大
                 |                  | 例：简单 API 网关
                 |
10k-50k          | 小型应用 ✅      | 最优（一个小团队可维护）
                 |                  | 例：单个业务模块
                 |
50k-100k         | 中型应用 ✅      | 仍然可控（2-3 个小团队）
                 |                  | 例：复杂的业务模块
                 |
100k-500k        | 大型应用         | 开始有压力（开发效率下降）
                 |                  | 编译时间长、测试复杂
                 |
> 500k           | 超大型应用       | 难以维护（应该分解）
                 |                  | IDE 卡顿、冲突频繁
```

**为什么这些数字重要？**

```
应用大小与开发效率的关系（非线性）：

开发效率
   ↑
100%├─────────────────────────────
    │    \
    │     \
    │      \___
80% │          \___
    │              \
    │               \
60% │                \___
    │                    \___
    │
    └────────────────────────────→ 代码行数
    0   10k  50k  100k 200k 500k 1M

观察：
  • 10k-100k：高效（编译快、IDE响应快、容易理解）
  • 100k-300k：开始下降（编译时间 5-10 分钟）
  • 300k-500k：明显下降（编译时间 10-20 分钟）
  • > 500k：大幅下降（IDE 卡顿、频繁 merge 冲突）
```

### 维度 2：功能数量

**功能数量的衡量：**

```
计数方式：
  ├─ 用户故事数：系统中独立的用户需求
  ├─ API 端点数：暴露的接口
  ├─ 业务流程数：核心业务流程
  ├─ 数据实体数：主要的业务对象
  └─ 决策点数：系统中的条件分支

推荐范围：
  ├─ 小应用：5-15 个核心功能
  ├─ 中应用：15-40 个核心功能
  └─ 大应用：40-100+ 个核心功能

超过 50+ 个核心功能，应该考虑分割
```

**案例分析：**

```
订单管理应用 - 功能清单

核心功能（7 个）：
  1. 创建订单
  2. 修改订单
  3. 取消订单
  4. 查询订单
  5. 订单确认
  6. 订单完成
  7. 订单统计

分析：
  ✅ 7 个核心功能
  ✅ 代码量应该在 10k-50k 行
  ✅ 一个小团队（2-3 人）可维护
  ✅ 应用边界清晰

如果再加上：
  + 支付管理（5 个功能）
  + 库存管理（5 个功能）
  + 物流管理（5 个功能）
  + 退货管理（5 个功能）

总计：27 个功能
  ❌ 太多，应该分离为 4-5 个独立应用
```

### 维度 3：团队大小

**Conway's Law：**
> 设计系统的架构与组织结构趋于一致

**应用大小与团队规模的关系：**

```
团队规模     应用大小        规模指标
─────────────────────────────────────
1-2 人      微型应用       10k-20k 行
            （简单应用）

2-3 人      小型应用       20k-50k 行
            （一个业务模块）

3-5 人      中型应用       50k-100k 行
            （复杂业务模块）

5-10 人     大型应用       100k-200k 行
            （多个相关功能）

10+ 人      需要拆分        应该分解为
            （超过此规模    多个应用，每个
             应该拆分）     10+ 人团队

Tip：
  一个应用最多一个团队维护
  一个团队可以维护多个应用
  但不建议多个团队共维一个应用（代码冲突频繁）
```

**为什么团队大小很关键？**

```
根本原因 - 沟通成本：

当一个应用由多个团队维护：
  ├─ 代码 review 需要跨团队沟通
  ├─ 架构决策需要多个团队同意
  ├─ 发版需要协调（谁先提交）
  ├─ bug 责任不清（谁引入的）
  ├─ 性能问题（谁优化）
  └─ 结果：效率低下

示例：一个 200k 行应用由 3 个团队维护
  团队 A：处理订单
  团队 B：处理支付
  团队 C：处理库存

  问题：
    - 订单模块的 import 会用到支付和库存模块
    - 修改订单模块可能影响支付和库存
    - 每个改动都需要 3 个团队 review
    - 发版需要 3 个团队协调
    - 相互责备（这是你们的 bug）
```

### 维度 4：维护成本

**维护成本模型：**

```
维护成本 = 代码复杂度 × 开发人员周转率 × 缺乏文档程度

代码复杂度指标：
  ├─ 圈复杂度（Cyclomatic Complexity）
  │  平均圈复杂度 > 10：应该简化
  │
  ├─ 代码重复率
  │  重复率 > 15%：应该提取公共代码
  │
  ├─ 依赖复杂度
  │  模块间依赖 > N^2：应该解耦
  │
  └─ 代码耦合度
     两个模块的改动相关性 > 30%：应该合并或分离

高维护成本的警告信号：
  ❌ 修改一个小功能需要改多个地方
  ❌ 测试覆盖率低（因为代码难以测试）
  ❌ 频繁出现回归 bug（改这里坏那里）
  ❌ 新功能开发速度慢（需要理解大量代码）
  ❌ 开发者频繁离职（代码难以维护）
```

## 应用大小的评估方法

### 方法 1：计算评分

**三维评估模型：**

```
评分方式：1-5 分（1 = 最小，5 = 最大）

维度 1：代码复杂度
  ├─ 代码行数（20%）
  ├─ 圈复杂度（20%）
  ├─ 依赖复杂度（20%）
  ├─ 测试覆盖率（20%）
  └─ 文档完整度（20%）

维度 2：功能复杂度
  ├─ 功能数量（30%）
  ├─ 业务规则复杂度（30%）
  ├─ 数据模型复杂度（25%）
  └─ 集成点数量（15%）

维度 3：维护压力
  ├─ 团队规模（30%）
  ├─ 开发人员周转率（25%）
  ├─ 代码冲突频率（25%）
  └─ 缺陷率（20%）

总评分 = 维度 1 平均分 + 维度 2 平均分 + 维度 3 平均分

评分结果：
  3-5   分：应用大小合适 ✅
  5-8   分：接近上限，需要优化
  8-12  分：明显过大，应该分割 ❌
  12+   分：严重过大，必须分割 ❌❌
```

### 方法 2：成本收益分析

**何时应该分割应用？**

```
决策框架：

应用当前规模    当前成本（月）  分割后成本       收益
─────────────────────────────────────────────────────
100k 行         $30k          分割为 2 个
(3 人团队)      (沟通、测试    50k 行 ($20k × 2)
                延长)
                               = $40k            ❌ 成本增加

200k 行         $50k          分割为 3 个
(5 人团队)      (开发效率      67k 行
                下降、bug      ($18k × 3)
                多、冲突频繁)  = $54k            ❌ 略差

300k 行         $80k          分割为 4 个
(7 人团队)      (编译慢、      75k 行
                IDE 卡、       ($17k × 4)
                冲突频繁)      = $68k            ✅ 节省 $12k

500k 行         $150k         分割为 5 个
(10+ 人)        (开发效率      100k 行
                严重下降、     ($20k × 5)
                难以协调)      = $100k           ✅ 节省 $50k

结论：
  ├─ 成本 = 沟通 + 开发 + 测试 + 运维 + 人员成本
  ├─ 应用越大，额外成本越高
  ├─ 分割应用的成本包括：架构、部署、运维
  └─ 通常 200k+ 行代码时，分割会降低总成本
```

## 应用大小的优化建议

### 识别过大应用

**检查清单：**

```
□ 代码相关指标
  ├─ 代码行数 > 200k ❌ 过大
  ├─ 最大类 > 1000 行 ❌
  ├─ 平均方法长度 > 30 行 ❌
  ├─ 平均圈复杂度 > 5 ❌
  └─ 单个文件 > 500 行 ❌ （拆分）

□ 功能相关指标
  ├─ 核心业务功能 > 50 个 ❌
  ├─ API 端点数 > 100 ❌
  ├─ 数据表数 > 50 ❌
  └─ 业务规则行数 > 500k ❌

□ 团队和维护指标
  ├─ 多个团队共维 1 个应用 ❌
  ├─ 每月 merge conflict > 10 次 ❌
  ├─ 缺陷率 > 10/kloc ❌
  ├─ 测试覆盖率 < 60% ❌
  ├─ 编译时间 > 10 分钟 ❌
  └─ IDE 启动 > 2 分钟 ❌

□ 部署相关
  ├─ 发版时间 > 1 小时 ❌
  ├─ 回滚时间 > 30 分钟 ❌
  └─ 测试时间 > 2 小时 ❌
```

### 分割应用的方法

**方法 1：按业务边界分割**

```
示例：电商系统（已过大）

当前应用（350k 行）：
  ├─ 商品模块（80k）
  ├─ 订单模块（90k）
  ├─ 库存模块（60k）
  ├─ 支付模块（50k）
  └─ 用户模块（70k）

分割方案：
  应用 1（商品应用）
    └─ 商品模块（80k）

  应用 2（订单应用）
    └─ 订单模块（90k）

  应用 3（库存应用）
    └─ 库存模块（60k）

  应用 4（支付应用）
    └─ 支付模块（50k）

  应用 5（用户应用）
    └─ 用户模块（70k）

结果：5 个应用，每个 50k-90k 行 ✅
```

**方法 2：按稳定性分割**

```
当前应用中，不同模块的变化速度：

订单模块：每周变更 3-5 次（快）
库存模块：每月变更 1-2 次（慢）
推荐模块：每天变更（很快）
支付模块：很少变更（非常慢）

分割方案：
  应用 1（变化快的应用）
    ├─ 订单模块（快速迭代）
    └─ 推荐模块（快速迭代）

  应用 2（变化慢的应用）
    ├─ 库存模块（稳定）
    └─ 支付模块（稳定）

好处：
  ✅ 订单应用可以频繁发版
  ✅ 支付应用稳定，降低风险
  ✅ 不同应用的 SLA 不同
```

## 应用大小的标准化

### 推荐的应用大小范围

**通用标准：**

```
应用规模标准：

代码行数：        20k - 100k 行
  目标：          50k 行（±50%）

功能数量：        10 - 40 个核心功能
  目标：          20 个（±50%）

团队规模：        2 - 5 人
  目标：          3 人（±1）

API 端点数：      20 - 50 个
  目标：          30 个（±30%）

数据表数：        5 - 20 个
  目标：          10 个（±50%）

部署频率：        1 次/周 - 1 次/天
  目标：          2-3 次/周

缺陷率：          < 5 per kloc
  目标：          2-3 per kloc

测试覆盖率：      > 70%
  目标：          80%+
```

### 警告信号和应对方案

```
警告信号                       │ 应对方案
─────────────────────────────┼──────────────────────
代码 > 150k 行                │ 开始分割计划
单个类 > 800 行               │ 拆分类
单个方法 > 50 行              │ 拆分方法
圈复杂度 > 8                 │ 简化逻辑
团队 > 5 人                   │ 分组或分割应用
多个团队维护一个应用          │ 明确归属权或分割
编译 > 10 分钟                │ 考虑分割
缺陷率 > 10 per kloc         │ 提高测试覆盖率或分割
```

---

## 总结

应用大小是架构设计中的关键决策：

```
✅ 最优范围：20k-100k 行代码，一个小团队维护
❌ 过小（< 10k）：管理开销大
❌ 过大（> 150k）：维护成本高，应该分割

当应用超过 200k 行时，分割通常能降低总成本。
```
