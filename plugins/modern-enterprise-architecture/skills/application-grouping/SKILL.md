# 应用分组与协调技能

## 概述

当系统中应用数量增加时，需要将它们进行逻辑分组，形成应用组。这样可以更好地管理复杂性、协调应用间的关系、优化部署和运维。

## 核心概念

### 应用分组的目标

```
1. 降低管理复杂性
   ├─ 从管理 N 个应用 → 管理 K 个应用组（K < N）
   ├─ 应用组是一个更高层的逻辑单元
   └─ 例：电商应用组包含订单、库存、支付应用

2. 明确职责分工
   ├─ 应用组有明确的负责团队
   ├─ 应用组与团队结构对齐
   └─ 便于评估团队绩效

3. 优化部署策略
   ├─ 应用组内的应用通常一起部署
   ├─ 减少部署复杂性
   └─ 便于灾难恢复和备份

4. 规划资源分配
   ├─ 按应用组分配计算资源
   ├─ 评估应用组的成本
   └─ 规划容量和扩展
```

### 应用分组的维度

```
维度 1：按业务域分组
  结果：每个业务域一个应用组
  例：
    ├─ 订单应用组（Order Group）
    │  ├─ Order App
    │  ├─ OrderQuery App
    │  └─ OrderAnalytics App
    ├─ 库存应用组（Inventory Group）
    │  ├─ Inventory App
    │  └─ WarehouseManagement App
    └─ 支付应用组（Payment Group）
       ├─ Payment App
       └─ Settlement App

维度 2：按技术栈分组
  结果：使用相同技术的应用放在一起
  例：
    ├─ Java 应用组
    ├─ Node.js 应用组
    ├─ Python 应用组
    └─ Go 应用组

维度 3：按团队分组
  结果：由同一个团队维护的应用放在一起
  例：
    ├─ 订单团队应用组
    ├─ 库存团队应用组
    └─ 平台团队应用组

维度 4：按基础设施分组
  结果：共享基础设施的应用放在一起
  例：
    ├─ Kubernetes 集群 A（关键应用）
    ├─ Kubernetes 集群 B（普通应用）
    └─ 虚拟机（遗留系统）

推荐：多维度结合
  - 首选：按业务域 + 团队
  - 二选：按业务域 + 技术栈
```

## 应用分组的模式

### 模式 1：以业务为中心的应用组

```
原则：应用组的边界与业务域的边界一致

结构：
  订单应用组
  ├─ 订单管理应用（核心）
  ├─ 订单查询应用（支撑）
  ├─ 订单统计应用（分析）
  ├─ 订单通知应用（沟通）
  └─ 订单支付应用（协作）

优势：
  ✓ 业务人员易于理解
  ✓ 团队与应用组对齐
  ✓ 应用组的演进与业务演进一致

劣势：
  ✗ 应用数量多时管理复杂
  ✗ 某些应用可能属于多个业务域
```

### 模式 2：分层应用组

```
原则：按应用的战略重要性分层

结构：
  第 1 层（核心应用组）
  ├─ 订单应用组
  ├─ 库存应用组
  └─ 推荐应用组
  → 战略性应用，最多投资

  第 2 层（支撑应用组）
  ├─ 用户应用组
  ├─ 支付应用组
  └─ 物流应用组
  → 支撑应用，中等投资

  第 3 层（平台应用组）
  ├─ 认证应用组
  ├─ 通知应用组
  ├─ 日志应用组
  └─ 配置应用组
  → 平台应用，最少投资

优势：
  ✓ 资源分配与重要性对齐
  ✓ 清晰的投资优先级
  ✓ 不同层有不同的 SLA 要求

劣势：
  ✗ 分层标准难以定义
  ✗ 层级可能随时间改变
```

### 模式 3：技术平台应用组

```
原则：按使用的技术或基础设施分组

结构：
  微服务应用组（Kubernetes）
  ├─ Order Microservice
  ├─ Inventory Microservice
  └─ Payment Microservice

  单体应用组（VM + Docker Compose）
  ├─ Legacy Monolith
  └─ Admin System

  Serverless 应用组（AWS Lambda）
  ├─ Data Processing
  └─ Event Handlers

优势：
  ✓ 运维相对统一（同一基础设施）
  ✓ 部署流程一致
  ✓ 技术选择清晰

劣势：
  ✗ 业务边界可能模糊
  ✗ 不利于业务演进
```

## 应用组间的协调

### 协调方式 1：同步调用

```
应用 A 需要立即获得应用 B 的结果

实现：
  ├─ HTTP/REST 调用
  ├─ gRPC 调用
  └─ 数据库查询

适用场景：
  ✓ 响应时间要求高
  ✓ 应用 B 故障容忍度低
  ✓ 调用不频繁

限制：
  ✗ 需要等待，可能降低吞吐量
  ✗ 应用 B 不可用会影响 A
  ✗ 网络延迟会累加
```

### 协调方式 2：异步事件驱动

```
应用 A 发送事件，应用 B 监听并处理

实现：
  ├─ 消息队列（Kafka、RabbitMQ）
  ├─ 事件总线（Event Bus）
  └─ 发布-订阅（Pub/Sub）

适用场景：
  ✓ 可以接受延迟
  ✓ 需要解耦
  ✓ 一个事件可能被多个应用处理

限制：
  ✗ 调试困难
  ✗ 最终一致性
  ✗ 需要补偿机制处理失败
```

### 协调方式 3：共享数据库

```
多个应用共享同一个数据库

实现：
  ├─ 直接 SQL 查询
  ├─ ORM 映射
  └─ 数据库视图

适用场景：
  ✓ 实时性要求高
  ✓ 应用紧密耦合
  ✓ 需要强 ACID 事务

限制：
  ✗ 应用间耦合度高
  ✗ 难以独立部署
  ✗ 数据库成为瓶颈
  ✗ 难以扩展
```

## 设计清单

```
□ 确定应用分组的方式
  ├─ 选择维度：业务、技术、团队
  ├─ 定义分组标准
  └─ 列出所有应用组

□ 对每个应用组定义
  ├─ 名称和描述
  ├─ 包含的应用
  ├─ 负责团队
  ├─ 核心职责
  ├─ 依赖的其他应用组
  └─ SLA 和质量属性目标

□ 规划应用组间的协调
  ├─ 协调方式（同步/异步）
  ├─ 通信协议
  ├─ 数据交换格式
  └─ 故障处理

□ 评估应用组的可操作性
  ├─ 应用组的大小是否合适？
  ├─ 团队是否能有效协调？
  ├─ 是否需要专门的协调角色？
  └─ 如何监控应用组的健康状态？

□ 制定演进计划
  ├─ 当前状态
  ├─ 目标状态
  ├─ 迁移步骤
  └─ 时间和成本估计
```

## 常见陷阱

```
陷阱 1：应用分组过多
  问题：应用组太多，管理复杂度没有降低
  解决：应用组数量应该 < 应用数量 / 3

陷阱 2：应用组划分不清
  问题：应用属于多个应用组，或归属不明确
  解决：明确划分规则，每个应用恰好属于一个应用组

陷阱 3：应用组与团队结构不对齐
  问题：应用组的边界与团队边界不一致，导致沟通困难
  解决：应用组的划分应该反映团队结构

陷阱 4：忽视应用组间的依赖
  问题：应用组间的依赖没有明确定义，导致高耦合
  解决：明确定义应用组间的依赖和通信方式

陷阱 5：应用组过大
  问题：一个应用组包含太多应用，仍然复杂
  解决：应用组内的应用数应该 < 10 个
```

## 关键建议

1. **清晰的分组标准**
   ❌ "这个应用属于哪个应用组？"（无法回答）
   ✅ "我们按业务域分组，所以这个应用属于订单组"

2. **与团队结构对齐**
   ❌ 应用分组与团队结构不一致
   ✅ 一个应用组对应一个小团队

3. **清晰的协调方式**
   ❌ "应用组间可以任意调用"
   ✅ "同步调用只用于关键路径，其他路径用异步"

4. **定期评估**
   ❌ "应用分组方式一成不变"
   ✅ "随着应用增长，定期重新评估分组方式"

5. **文档化**
   ❌ "应用分组方式只在会议中讨论"
   ✅ "有清晰的文档说明应用分组的方式和理由"
