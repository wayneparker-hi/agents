# 架构决策记录（ADR）技能

## 概述

架构决策记录（ADR）是对重要技术决策的系统化文档。它帮助团队透明地做决策、记录决策的原因和权衡，以及追踪决策的演变。

---

## 核心概念

### ADR 的必要性

```
问题：为什么需要 ADR？

情景 1：新成员加入
  ❌ 没有 ADR：新成员问"为什么选择 PostgreSQL？"
              没人能清晰地解释
              决策背景和权衡都忘了
  ✅ 有 ADR：新成员读 ADR-001，立即明白背景和选择理由

情景 2：技术演进
  ❌ 没有 ADR：讨论是否升级 Kafka 版本时，不知道当初为什么选 Kafka
              无法评估升级的风险
  ✅ 有 ADR：查看 ADR-003，知道当初的约束条件和目标

情景 3：架构变更
  ❌ 没有 ADR：替换一个组件时，不知道其他组件为什么依赖它
              可能做出错误的决策
  ✅ 有 ADR：查看相关 ADR，理解整个架构的逻辑
```

### ADR 的标准格式

```
标准 ADR 包含以下部分：

标题：简洁描述决策
  └─ 例：ADR-001: 使用 PostgreSQL 作为主数据库

状态：PROPOSED | ACCEPTED | IMPLEMENTED | SUPERSEDED | DEPRECATED

上下文（Context）：
  ├─ 问题的背景是什么？
  ├─ 为什么这个决策很重要？
  ├─ 有哪些约束条件？
  └─ 谁是关键利益相关者？

决策（Decision）：
  └─ 我们决定了什么？

理由（Rationale）：
  ├─ 为什么选择这个方案？
  ├─ 相比其他方案的优势？
  └─ 如何满足关键需求？

后果（Consequences）：
  ├─ 积极后果
  ├─ 消极后果
  ├─ 风险和缓解方案
  └─ 学习效应

相关决策（Related）：
  ├─ 依赖的 ADR
  ├─ 相关的 ADR
  └─ 相矛盾的 ADR

日期和状态：
  ├─ 提议日期
  ├─ 决议日期
  └─ 最后更新
```

## 常见的架构决策类型

### 基础设施决策

```
ADR 模板：数据库选择

上下文：
  ├─ 应用需要存储和查询用户数据
  ├─ 需要 ACID 保证
  ├─ 预期数据量：100M 行
  ├─ 并发读：10,000 QPS
  ├─ 写入延迟要求：< 100ms
  └─ 团队有 SQL 经验

考虑的方案：
  ├─ MySQL：开源、成熟、有 SQL 经验
  │  ├─ 优点：成熟、生态丰富、运维友好
  │  └─ 缺点：垂直扩展困难，水平扩展复杂
  │
  ├─ PostgreSQL：更强大的 SQL、JSON 支持
  │  ├─ 优点：功能丰富、性能好、扩展性
  │  └─ 缺点：学习曲线陡峭
  │
  └─ NoSQL (MongoDB)：灵活的 schema、高性能
     ├─ 优点：灵活、水平扩展性好
     └─ 缺点：需要应用层处理事务，ACID 保证弱

决策：选择 PostgreSQL
  ├─ 理由：功能完整、性能好、社区活跃
  ├─ 权衡：需要花时间学习 PostgreSQL 特性
  └─ 后续：制定 PostgreSQL 最佳实践规范
```

### 应用架构决策

```
ADR 模板：单体 vs 微服务

上下文：
  ├─ 新系统，需要快速上线
  ├─ 现有团队 20 人
  ├─ 需要支持快速迭代
  ├─ 需要支持模块化部署

考虑的方案：
  ├─ 单体应用：快速开发、简单部署、但扩展困难
  ├─ 微服务：灵活、可独立扩展、但运维复杂
  └─ 模块化单体：折中方案

决策：模块化单体
  ├─ 理由：
  │  ├─ 快速上线（不需要复杂的微服务基础设施）
  │  ├─ 易于部署（单个可执行文件）
  │  ├─ 易于调试（本地开发简单）
  │  └─ 支持未来演进为微服务
  │
  ├─ 后续：
  │  ├─ 明确模块边界
  │  ├─ 使用明确的接口通信
  │  └─ 为未来的微服务化准备
  │
  └─ 取代计划：当单个模块需要独立扩展时，可分离为微服务
```

## ADR 的生命周期管理

### 阶段 1：建议阶段（PROPOSED）

```
何时：有重要技术决策需要做时

执行：
  Step 1：起草 ADR
    ├─ 清晰描述背景和问题
    ├─ 列举可选方案
    ├─ 进行初步分析
    └─ 预估后果

  Step 2：技术讨论
    ├─ 在技术会议上介绍
    ├─ 邀请反馈和建议
    ├─ 讨论权衡和风险
    └─ 整理意见

  Step 3：修订 ADR
    ├─ 根据讨论结果修订
    ├─ 补充反对意见
    ├─ 完善分析
    └─ 准备决议
```

### 阶段 2：接受阶段（ACCEPTED）

```
何时：达成共识，决定采纳此方案时

执行：
  Step 1：正式评审
    ├─ 由技术委员会进行评审
    ├─ 检查 ADR 的完整性
    ├─ 确认没有遗漏的考虑
    └─ 评估风险

  Step 2：投票确认（可选）
    ├─ 技术委员会投票
    ├─ 需要多数同意
    └─ 记录投票结果

  Step 3：标记为接受
    ├─ 更新 ADR 状态为 ACCEPTED
    ├─ 记录决议日期
    ├─ 通知所有相关人员
    └─ 发布到 ADR 库
```

### 阶段 3：实施阶段（IMPLEMENTED）

```
何时：在实际项目中实施了这个决策时

执行：
  Step 1：追踪实施
    ├─ 监督决策在项目中的实施
    ├─ 记录实施过程的关键决定
    ├─ 收集团队的反馈
    └─ 评估是否有改进机会

  Step 2：更新 ADR
    ├─ 添加实施的具体细节
    ├─ 记录实际的性能指标
    ├─ 补充学习和经验
    └─ 更新状态为 IMPLEMENTED

  Step 3：知识转移
    ├─ 确保所有相关人员都了解决策
    ├─ 更新相关的技术文档
    ├─ 在代码中添加 ADR 引用
    └─ 为新成员提供上下文
```

### 阶段 4：演进阶段（SUPERSEDED / DEPRECATED）

```
何时：需要改变或升级某个决策时

执行：
  Step 1：评估需要改变
    ├─ 分析当前决策的局限
    ├─ 评估新方案的优势
    ├─ 评估迁移成本
    └─ 决定是否改变

  Step 2：创建新 ADR
    ├─ 如果完全取代，创建新 ADR
    ├─ 在新 ADR 中说明取代关系
    ├─ 评估迁移计划
    └─ 定义兼容期

  Step 3：更新旧 ADR
    ├─ 将旧 ADR 标记为 SUPERSEDED
    ├─ 链接到新 ADR
    ├─ 保留完整的历史（便于理解演变）
    └─ 记录过时的日期

  Step 4：制定迁移计划
    ├─ 确定受影响的系统
    ├─ 规划迁移步骤
    ├─ 定义兼容期
    └─ 分阶段实施迁移
```

## ADR 最佳实践

### 1. 及时记录

```
✅ 好：决策做出后立即创建 ADR，即使内容不够完整
❌ 坏：等到实施完成后再写 ADR，已经忘记许多细节

时机原则：
  ├─ 一旦做出决策 → 创建 ADR（PROPOSED）
  ├─ 获得同意 → 更新为 ACCEPTED
  ├─ 开始实施 → 追踪并记录
  └─ 实施完成 → 总结成果，标记为 IMPLEMENTED
```

### 2. 包含不同观点

```
✅ 好：记录为什么选择了这个而不是那个
  ├─ 说明被拒绝方案的缺点
  ├─ 说明权衡和折衷
  ├─ 记录讨论中的反对意见

❌ 坏：只记录最终决策，隐藏讨论过程
  └─ 新人看不到为什么做这个选择
```

### 3. 保持可读性

```
✅ 好：
  ├─ 控制在 1-2 页（A4）
  ├─ 用清晰简洁的语言
  ├─ 使用表格和图表
  ├─ 避免技术行话

❌ 坏：
  ├─ 冗长的技术论文
  ├─ 充满复杂的术语
  ├─ 难以理解的描述
  └─ 需要读 10 页才能理解决策
```

### 4. 版本控制和可查证性

```
✅ 好：
  ├─ ADR 存储在 Git 中
  ├─ 与代码一起进行版本管理
  ├─ 可以查看 ADR 的修改历史
  ├─ 可以看到谁在什么时候做的决策

❌ 坏：
  ├─ ADR 存储在 Word/PDF 中
  ├─ 难以追踪修改历史
  ├─ 容易丢失
  └─ 无法链接到代码
```

### 5. 定期审视

```
执行：
  ├─ 每个季度审视一次历史 ADR
  ├─ 识别过时的决策
  ├─ 评估是否需要更新
  ├─ 记录新的学习
  └─ 考虑是否需要超级 ADR

输出：
  ├─ 标记过时的 ADR
  ├─ 创建升级 ADR
  ├─ 更新相关文档
  └─ 分享学习
```

## ADR 编写模板

```markdown
# ADR-001: 使用 PostgreSQL 作为主数据库

## 状态
ACCEPTED

## 上下文
- 应用需要存储关键业务数据，需要 ACID 保证
- 预期数据规模：100M 行
- 并发要求：10,000 QPS 读，1,000 QPS 写
- 团队有 SQL 经验，无 NoSQL 经验

## 决策
我们使用 PostgreSQL 作为主数据库。

## 理由
- 功能完整：支持 JSON、全文搜索等
- 性能：满足我们的性能需求
- 可靠性：成熟稳定，企业级支持
- 社区：活跃的社区，问题易解决

## 后果

### 正面
- 强一致性和 ACID 保证
- 灵活的查询能力
- 易于维护和调试

### 负面
- 学习成本（某些高级特性）
- 垂直扩展的限制

## 相关决策
- ADR-002: 使用 Redis 作为缓存层
- ADR-003: 数据库备份策略
```

## ADR 的度量和评估

```
定期评估 ADR 的有效性：

指标 1：覆盖率
  ├─ 关键决策有 ADR 吗？> 90%
  ├─ 高风险决策都记录了吗？100%
  └─ 非关键决策是否也应该记录？根据情况

指标 2：更新频率
  ├─ ADR 多久更新一次？至少每个季度
  ├─ 是否有过时的 ADR？应该标记
  └─ 新决策多久后会有 ADR？应该 < 1 周

指标 3：使用度
  ├─ 新成员使用 ADR 来理解决策吗？
  ├─ 在设计讨论中是否参考 ADR？
  ├─ 代码中是否链接到 ADR？
  └─ 目标：大多数技术问题都能从 ADR 中找到答案

指标 4：质量
  ├─ ADR 是否完整？所有部分都有
  ├─ ADR 是否清晰？新人能理解
  └─ ADR 是否准确？与实际实施一致
```

## 最佳实践总结

```
1. 及时记录 ✅
   └─ 决策做出后立即创建 ADR

2. 包含权衡 ✅
   └─ 说明为什么选择这个而不是那个

3. 简洁清晰 ✅
   └─ 1-2 页，避免冗长的技术论文

4. 版本控制 ✅
   └─ 在 Git 中维护，与代码一起

5. 定期审视 ✅
   └─ 每季度评估一次，更新或标记过时

6. 团队参与 ✅
   └─ ADR 评审要有多个人参与

7. 链接到代码 ✅
   └─ 代码中引用 ADR，便于理解实现
```
