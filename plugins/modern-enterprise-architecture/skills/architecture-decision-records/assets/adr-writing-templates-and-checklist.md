# ADR 编写模板和检查清单

## 第一部分：标准 ADR 模板

### 最小化模板（用于小的决策）

```markdown
# ADR-XXX: [简短的标题]

## 状态
提议中 / 已接受 / 已实施 / 已取代 / 已弃用

## 背景
[简短描述导致这个决策的背景和问题]

## 决策
[我们决定做什么]

## 理由
[为什么做这个决策]

## 后果
[这个决策的影响和权衡]
```

**示例**：
```markdown
# ADR-003: 使用 JSON 作为 API 响应格式

## 状态
已接受

## 背景
API 当前有多种响应格式（XML、JSON、CSV），导致维护复杂。

## 决策
所有新 API 仅使用 JSON 格式。

## 理由
- JSON 是行业标准
- 所有客户端都原生支持
- 开发和维护成本最低

## 后果
- 现有 XML/CSV 客户端需要迁移
- API 维护简化
```

## 第二部分：ADR 编写检查清单

### 内容检查

```
□ 标题
  □ 清晰简洁（< 10 个字）
  □ 以"决策"而非"问题"命名
  □ 避免模糊词汇（如"改进"、"优化"）

□ 背景
  □ 解释为什么要做这个决策
  □ 包含具体的问题陈述
  □ 包含数据或证据支撑
  □ 不超过 2-3 段

□ 决策
  □ 明确陈述"我们决定..."
  □ 使用祈使语气和主动声态
  □ 具体，可以指导实施
  □ 一页以内

□ 理由
  □ 解释为什么做这个决策（不是"如何做"）
  □ 每个理由单独成段
  □ 包含替代方案对比
  □ 承认权衡和缺点

□ 后果
  □ 描述决策的影响
  □ 包括正面和负面影响
  □ 包括短期和长期影响
  □ 诚实地承认缺点

□ 状态
  □ 清晰标明当前状态
  □ 包括日期
  □ 如果后来改变，更新状态

□ 格式和组织
  □ 使用清晰的标题和小标题
  □ 使用列表而非段落（易读）
  □ 包含表格进行对比
  □ 长度适中（2-4 页）
```

### 质量检查

```
□ 清晰性
  □ 新人能理解这个决策吗？
  □ 是否有模糊或多义的句子？
  □ 是否需要进一步解释专业术语？

□ 完整性
  □ 是否涵盖了所有相关维度？
  □ 是否有明显的遗漏？
  □ 是否描述了所有重要的权衡？

□ 平衡性
  □ 是否只描述了优点，忽视了缺点？
  □ 是否公平地对待了替代方案？
  □ 是否承认了决策的局限性？

□ 可行性
  □ 这个决策能被实施吗？
  □ 是否有明确的实施路径？
  □ 是否考虑了实施成本？

□ 时效性
  □ 这个决策在当前条件下仍然有效吗？
  □ 是否考虑了未来可能的变化？
  □ 是否定义了何时应该重新评估？
```

### 过程检查

```
□ 充分讨论
  □ 是否与相关团队讨论过？
  □ 是否听取了不同的观点？
  □ 是否记录了重要的讨论点？
  □ 是否有反对意见被记录？

□ 决策权清晰
  □ 谁做的最终决策？
  □ 是否是正确的决策者？
  □ 是否得到了高层批准（如需要）？

□ 文档完整
  □ 是否有 ADR 编号和版本？
  □ 是否有日期和作者信息？
  □ 是否清晰标明状态？
  □ 是否有链接到相关文档？

□ 可访问性
  □ ADR 存放在团队能找到的地方吗？
  □ 是否有 ADR 列表或索引？
  □ 新人能找到相关的 ADR 吗？
```

## 第三部分：ADR 项目模板

当开始使用 ADR 时，创建一个初始的 ADR 项目来建立团队的实践。

### ADR-001：建立 ADR 实践

```markdown
# ADR-001: 采用 Architecture Decision Records 实践

## 状态
已接受

## 背景
我们的架构决策分散在邮件、会议记录和某人的脑子里。
这导致：
- 新人加入时无法了解设计决策的历史
- 无法评估旧决策是否仍然适用
- 重复讨论已经做过的决策

## 决策
采用 Architecture Decision Records（ADR）来记录所有重要的架构决策。

## 理由
1. **知识保留**：决策和理由被记录下来
2. **团队对齐**：所有人都能看到决策理由
3. **未来审视**：可以定期评估决策是否仍然适用
4. **新人入职**：新人能快速了解架构演变过程

## 实施

### ADR 存储位置
```
/docs/adr/
  ├─ ADR-001.md
  ├─ ADR-002.md
  ├─ ...
  └─ README.md（索引和说明）
```

### ADR 编号规则
- 顺序编号：001, 002, 003...
- 更新同一决策时新增编号（不覆盖旧的）

### 何时编写 ADR
以下情况必须编写 ADR：
- 新的技术选择（数据库、框架等）
- 架构的重大改变
- 权衡显著的设计决策
- 可能影响多个系统的决策

以下情况不需要 ADR：
- 日常的代码编写决策
- 小的配置改动
- 临时的解决方案

### ADR 评审流程
1. 起草者编写初稿
2. 与相关人讨论和改进
3. 建立共识（不是所有人都同意，但都被听取了意见）
4. 技术负责人批准
5. 合并到 ADR 库

### 定期审视
每季度审视一次 ADR：
- 哪些决策仍然有效？
- 哪些决策需要调整或取代？
- 是否有新的约束条件？
```

## 第四部分：ADR 演变和更新

### ADR 状态转换

```
提议中（Proposed）
  ↓
已接受（Accepted）
  ↓
已实施（Implemented）
  ↓
已取代（Superseded）或
已弃用（Deprecated）

说明：
- 提议中：讨论中，未最终确定
- 已接受：团队已同意，但可能未实施
- 已实施：已在生产环境中运行
- 已取代：被新的 ADR 取代了
- 已弃用：曾经被采用，但现在不再推荐
```

### 当需要更新决策时

**情况 1：部分更新（条件改变，但决策方向不变）**

```markdown
# ADR-042v2: [标题]

## 状态
已接受（更新）

## 说明
这是 ADR-042 的更新版本。
更新原因：[简短描述什么改变了]

## 改动说明
- 改动 1：[什么改了，为什么]
- 改动 2：[什么改了，为什么]
```

**情况 2：重大改变（需要新决策）**

```markdown
# ADR-050: [新的决策标题]

## 状态
已接受

## 背景
先前我们在 ADR-042 中决定了 [旧决策]。
现在由于 [新的原因]，需要改变这个决策。

## 决策
[新的决策]

## 为什么取代 ADR-042
[详细解释为什么旧决策不再适用]

---

在 ADR-042 中，添加以下内容：

## 后续发展
此决策已被 ADR-050 取代。参见 ADR-050：[标题]
```

## 第五部分：ADR 最佳实践

```
1. 及时编写
   ✅ 决策做出时就写，不要等后来补写
   ✅ 趁还记得为什么，写得更清楚
   ❌ 延迟编写，会遗漏重要信息

2. 讨论优先
   ✅ 先讨论，再在 ADR 中记录共识
   ✅ ADR 是讨论的成果，不是讨论的替代
   ❌ 单独闭门写 ADR，然后强行推行

3. 简洁清晰
   ✅ 长度 2-4 页（一般情况）
   ✅ 易于快速扫读
   ✅ 关键信息在前
   ❌ 冗长、学术风格的文档

4. 诚实承认限制
   ✅ 说出决策的缺点和权衡
   ✅ 说出什么条件下这个决策不适用
   ❌ 只说优点，隐瞒缺点

5. 定期审视
   ✅ 每季度回顾一次 ADR
   ✅ 评估决策是否仍然有效
   ❌ 写完就扔，不再看

6. 学习和传承
   ✅ 新人加入时，让他们阅读相关 ADR
   ✅ 定期分享 ADR 讨论架构
   ❌ 决策只存在某个人脑子里
```

这个模板和检查清单应该能帮助你和团队编写高质量的 ADR。
