# ADR 决策框架和反面模式

## 概述

本文档提供决策框架来帮助做出更好的架构决策，并说明常见的反面模式（anti-patterns）来避免。

---

## 第一部分：决策框架

### 框架 1：RACI 决策模型

当做出重要的架构决策时，明确谁负责是很重要的。

```
角色定义：
  R（Responsible）：执行者，具体完成工作的人
  A（Accountable）：负责人，最终对决策负责
  C（Consulted）：咨询对象，提供专业意见和建议
  I（Informed）：知情者，需要被通知但不参与决策
```

**示例：选择微服务架构决策**

```
决策：是否采用微服务架构

角色分配：
  ├─ A（负责人）：技术负责人 / CTO
  │    └─ 最终拍板
  ├─ R（执行者）：架构师团队
  │    └─ 执行迁移计划
  ├─ C（咨询）：
  │    ├─ 应用开发团队
  │    ├─ 运维和 DevOps 团队
  │    ├─ 数据库团队
  │    └─ 安全团队
  └─ I（知情）：
       ├─ 产品和业务团队
       ├─ 项目经理
       └─ 其他开发人员

决策流程：
  1. 架构师起草提案
  2. 咨询各相关方（1-2 周）
  3. CTO 综合意见做决策
  4. 通知知情者和利益相关方
  5. 执行实施计划
```

### 框架 2：决策矩阵评分

**适用于**：需要对比多个选项的决策

```
维度定义（以"是否采用新的数据库"为例）：

关键度     | 权重 | 含义
────────┼────┼─────────────────────
必须满足   | 2x  | 不满足就不能选（PASS/FAIL）
应该满足   | 1.5x| 重要，但有替代方案
最好有     | 1x  | 锦上添花，不满足也可以

评分标准（1-10分）：
  10 = 完美无缺
  8 = 很好，有少量缺陷
  6 = 可以接受
  4 = 有明显不足
  2 = 严重问题
  1 = 完全不满足
```

**案例：选择 API 网关**

```
评估维度        | 权重  | Kong | Nginx | Spring | AWS API GW
────────────────┼──────┼─────┼──────┼──────┼─────────
高性能         | 2x   | 9   | 10   | 6    | 7
路由灵活性     | 1.5x | 9   | 6    | 8    | 7
认证和安全     | 1.5x | 9   | 5    | 8    | 8
易于运维       | 1x   | 6   | 7    | 7    | 9
成本           | 1.5x | 7   | 10   | 9    | 5
学习曲线       | 1x   | 6   | 8    | 9    | 8
────────────────┼──────┼─────┼──────┼──────┼─────────
加权总分        |      | 77  | 72   | 74   | 69

排名：Kong > Spring GW > Nginx > AWS

分析：
  Kong 得分最高的原因：
  - 路由灵活性和认证安全性最好（权重最大）
  - 性能也很好
  - 成本合理

  Nginx 低分的原因：
  - 认证和安全功能弱（需要额外工具）
  - 路由灵活性差

  AWS API GW 低分的原因：
  - 成本高
  - 与现有的 Java 技术栈集成度差
```

### 框架 3：风险评估模型

**适用于**：识别决策中的关键风险

```
风险评估公式：
  风险度 = 影响程度 × 发生概率

影响程度（Impact）：
  5 = 灾难性（系统宕机，业务停止）
  4 = 严重（严重的功能故障）
  3 = 中等（重要功能部分受影响）
  2 = 轻微（边际功能影响）
  1 = 可忽略（基本无影响）

发生概率（Likelihood）：
  5 = 很高（> 80%）
  4 = 高（60-80%）
  3 = 中等（40-60%）
  2 = 低（20-40%）
  1 = 很低（< 20%）
```

**案例：采用新的开源库的风险**

```
风险 1：技术支持的长期可用性
  ├─ 影响：4（如果库停止维护会很困难）
  ├─ 概率：2（大多数流行库持续维护）
  ├─ 风险度：4 × 2 = 8（中等-高）
  └─ 缓解方案：
       └─ 选择成熟且活跃的库（检查 GitHub stars, 更新频率）

风险 2：安全漏洞
  ├─ 影响：5（安全漏洞可能很严重）
  ├─ 概率：3（任何代码都可能有漏洞）
  ├─ 风险度：5 × 3 = 15（高）
  └─ 缓解方案：
       ├─ 使用安全扫描工具（OWASP Dependency Check）
       ├─ 定期更新依赖
       └─ 订阅安全公告

风险 3：性能不满足需求
  ├─ 影响：3（可能需要替换）
  ├─ 概率：2（通常可以通过基准测试提前验证）
  ├─ 风险度：3 × 2 = 6（低-中）
  └─ 缓解方案：
       └─ 做 POC 验证性能

风险矩阵：
  高危（需要立即缓解）：风险度 > 12
  中危（需要关注）：风险度 8-12
  低危（可以接受）：风险度 < 8
```

### 框架 4：决策树

**适用于**：一系列顺序的、相互影响的决策

```
决策：是否迁移到云？

决策树：
  ├─ 成本是否是主要考虑？
  │  ├─ 是（成本敏感）
  │  │  ├─ 当前有专有数据中心吗？
  │  │  │  ├─ 是 → 混合云（保持现有投资）
  │  │  │  └─ 否 → 公有云（成本最低）
  │  │  │
  │  │  └─ 预期增长很快吗？
  │  │     ├─ 是 → 完全迁移到云（灵活扩展）
  │  │     └─ 否 → 保持现状
  │  │
  │  └─ 否（其他因素更重要）
  │     ├─ 需要全球覆盖吗？
  │     │  ├─ 是 → 多地域云部署
  │     │  └─ 否 → 单地域可以
  │     │
  │     └─ 需要最高可用性吗？
  │        ├─ 是（99.99%+）→ 云的 HA 方案
  │        └─ 否 → 自建可以

最终建议：
  成本敏感 + 快速增长 → 完全迁移到公有云
  成本敏感 + 增长缓慢 → 保持自建
  成本次要 + 全球覆盖 → 多地域云
  成本次要 + 需要 HA → 云端 HA 方案
```

## 第二部分：反面模式

### 反面模式 1："因为 Twitter 用，所以我们也用"

**问题描述**：

不考虑自身特点和需求，盲目跟风采用大公司使用的技术。

```
场景：
  "Netflix 使用微服务架构，所以我们也应该用微服务"
  "Google 用 Kubernetes，所以我们也应该用"
  "Facebook 使用 GraphQL，所以我们也应该用"

为什么这是反面模式：
  ├─ Netflix 的规模（几千台服务器）≠ 你的规模（100 台）
  ├─ Netflix 的团队（数千人）≠ 你的团队（20 人）
  ├─ Netflix 的成本预算（亿级）≠ 你的预算（百万级）
  └─ Netflix 的问题 ≠ 你的问题

结果：
  ├─ 过度工程（采用远超需要的复杂方案）
  ├─ 成本爆炸（使用高成本的工具和人力）
  ├─ 团队疲劳（学习陡峭的技术）
  └─ 没有收益（解决不了你的问题）

如何避免：
  ✅ 理解你面临的具体问题
  ✅ 理解大公司采用该技术的背景和规模
  ✅ 评估技术是否适合你的规模和能力
  ✅ 做 POC 验证是否真的有帮助
```

### 反面模式 2："永不决策模式"

**问题描述**：

无限期地延迟决策，总是说"还需要更多信息"或"再等等看"。

```
表现形式：
  "我们再研究一下，下个月再决定"（反复一年都没决定）
  "再等等看有没有更好的方案出现"（技术在快速发展）
  "我们需要看看 Gartner 魔力象限"（过度依赖外部权威）

后果：
  ├─ 项目停滞，团队沮丧
  ├─ 技术债堆积，问题越来越严重
  ├─ 竞争对手已经用新技术获得优势
  └─ 决策成本越来越高

根本原因：
  ├─ 完美主义：追求"最优"决策，忽视"够好"
  ├─ 风险厌恶：害怕做错决策
  ├─ 权力平衡：各方意见不一致，无法推进
  └─ 信息不足：错误地认为更多信息能保证更好决策

如何避免：
  ✅ 理解"好的决策 > 完美的决策"
  ✅ 设定决策截止日期（不能无限延迟）
  ✅ 建立清晰的决策权（谁是最终拍板者）
  ✅ 承认不确定性（决策本来就是在不确定下做的）
  ✅ 实施 ADR：记录假设，后续可以调整
```

### 反面模式 3："教条式设计"

**问题描述**：

严格遵循某个设计原则或架构模式，即使它不适应当前情况。

```
例子：
  "微服务的最佳实践说服务应该有独立数据库，
   所以我们 5 个微服务分别创建 5 个数据库，
   导致跨服务查询和一致性问题严重"

  "SOLID 原则说应该高内聚低耦合，
   所以我们把代码分解成 50+ 个类和接口，
   导致代码难以理解和维护"

  "我们严格遵循 12-factor 应用原则，
   导致一些单体应用变得不必要的复杂"

为什么这是反面模式：
  ├─ 设计原则是指导而非法律
  ├─ 所有指导都有上下文和边界条件
  ├─ 盲目遵循会导致过度设计
  └─ 成本-收益不匹配

如何避免：
  ✅ 理解设计原则背后的目的
  ✅ 了解适用的上下文和限制条件
  ✅ 灵活应用，而不是教条式遵循
  ✅ 在代码审查中提出"这遵循原则但解决了什么问题？"
```

### 反面模式 4："黑箱决策"

**问题描述**：

架构师做出决策，但不解释理由或记录决策过程。

```
表现形式：
  "我们决定用微服务架构"（为什么？）
  "我们选择了 MongoDB"（比其他什么？）
  "所有服务都必须用 gRPC"（有什么好处？）

后果：
  ├─ 团队不理解决策理由
  ├─ 无法评估决策的正确性
  ├─ 下一个架构师无法维护或调整决策
  ├─ 当需求变化时无法评估影响
  └─ 浪费时间反复讨论已决定的问题

根本原因：
  ├─ 架构师没有时间或不愿意解释
  ├─ 认为"因为我说了"就够了
  ├─ 没有建立决策记录的文化
  └─ 认为"这是架构师的工作，不需要团队理解"

如何避免：
  ✅ 每个重要决策都要写 ADR
  ✅ ADR 中解释清楚为什么和如何
  ✅ 与团队讨论决策，听取意见
  ✅ 定期评审决策，考虑是否需要调整
```

### 反面模式 5："过度重构"

**问题描述**：

不断地重构已有的系统，导致高成本而收益不足。

```
场景：
  第 1 年：用 Monolith + MySQL
  第 2 年："要用微服务"，花 6 个月重构成微服务
  第 3 年：组织扩大，"要用 Event Sourcing"，又重构
  第 4 年：不同服务使用不同 DB，"要统一用 NoSQL"，再重构
  第 5 年：技术债堆积，团队疲倦

结果：
  ├─ 每年 1-2 个月的工程能力用于重构
  ├─ 新功能开发速度变慢
  ├─ 团队离职（疲劳和沮丧）
  ├─ 问题没有真正解决

根本原因：
  ├─ 没有明确的改造目标（只是"想用新技术"）
  ├─ 没有评估改造成本和收益
  ├─ 没有优先级排序（什么最重要）
  └─ 架构师跟风新技术

如何避免：
  ✅ 明确的业务目标（重构为了什么？解决什么问题？）
  ✅ 量化的收益预期（性能提升多少？成本降低多少？）
  ✅ 影响评估（会影响哪些系统？需要多长时间？）
  ✅ 优先级排序（按收益 ROI 排序）
  ✅ 渐进式改造（不是一次性全部重构）
  ✅ 定期评审（真的达到目标了吗？）
```

### 反面模式 6："不记录决策"

**问题描述**：

重要的架构决策没有被记录，只存在于某个人的头脑中。

```
后果：
  ├─ 新人加入时无法了解设计历史
  ├─ 如果决策者离职，知识全部丢失
  ├─ 每当有新人加入都要重复解释
  ├─ 无法评估决策是否仍然适用
  ├─ 容易重复讨论已经解决的问题
  └─ 团队信任度下降

如何避免：
  ✅ 写 ADR（特别是重要决策）
  ✅ 维护架构设计文档
  ✅ 在代码中添加注释解释"为什么这样设计"
  ✅ 分享知识（技术分享、wiki）
  ✅ 建立知识库
```

### 反面模式 7："一刀切"

**问题描述**：

所有问题都用同一个解决方案，不考虑差异化需求。

```
例子：
  "所有服务都用微服务"
    → 对大型服务可能过度工程，小型服务不需要
  "所有 API 都用 REST"
    → 有些场景 GraphQL 更好，有些场景 gRPC 更好
  "所有数据都用 MySQL"
    → 有些数据用 NoSQL 或时序数据库更合适

后果：
  ├─ 某些系统设计不优雅（强行适应）
  ├─ 性能不最优（不是为该场景优化的）
  ├─ 维护成本高（学习和维护同样不合适的技术）
  └─ 团队沮丧（"为什么我们要这样做"）

根本原因：
  ├─ 追求简化和一致性
  ├─ 避免团队学习多种技术
  ├─ 缺乏架构治理，无法评估多技术栈
  └─ "不需要选择，我们已经决定了"

如何避免：
  ✅ 理解"适应问题的架构 > 一致但不适应"
  ✅ 允许技术多样性（但有限制）
  ✅ 建立技术评审委员会（评估新技术是否需要）
  ✅ 定期审视技术栈（是否仍然合适）
```

## 第三部分：决策评估清单

做出或审视架构决策时，可以使用以下清单：

```
□ 问题理解
  □ 我们明确理解了要解决的问题吗？
  □ 问题的根本原因是什么？
  □ 是否只是症状而非根本问题？

□ 目标明确
  □ 解决这个问题的具体目标是什么？
  □ 目标是可衡量的吗？
  □ 目标在 1-5 年内可达成吗？

□ 替代方案
  □ 我们评估了至少 3 个替代方案吗？
  □ 包括"维持现状"的选项吗？
  □ 包括"简单方案"吗？

□ 对比分析
  □ 我们用相同的标准对比了所有方案？
  □ 是否有量化的对比数据？
  □ 是否考虑了所有维度（性能、成本、复杂性等）？

□ 风险评估
  □ 我们识别了主要风险吗？
  □ 为每个风险制定了缓解方案吗？
  □ 是否有备选方案以防主方案失败？

□ 权衡透明
  □ 选定方案的优点和缺点都清楚吗？
  □ 我们承认了权衡吗？
  □ 是否有人对选择有异议？如果有，记录了吗？

□ 实施可行性
  □ 我们有实施这个决策的能力吗？
  □ 是否需要额外的培训或人力？
  □ 成本在预算范围内吗？

□ 反馈机制
  □ 我们定义了成功指标吗？
  □ 我们定义了何时重新评估吗？
  □ 如果目标未达成，我们会调整吗？

□ 文档记录
  □ 是否写了 ADR？
  □ ADR 中是否清楚地解释了为什么？
  □ 团队能理解这个决策吗？
```

## 总结

好的架构决策流程：
1. **明确理解问题**和业务目标
2. **探索多个替代方案**，而不是单一选择
3. **系统地评估**每个方案的优缺点
4. **诚实地承认**权衡和风险
5. **记录决策**和决策理由（ADR）
6. **定期评审**决策是否仍然有效
7. **敢于改变**当条件变化时

避免的反面模式：
- ❌ 盲目跟风
- ❌ 无限期延迟
- ❌ 教条式遵循
- ❌ 黑箱决策
- ❌ 过度重构
- ❌ 不记录决策
- ❌ 一刀切

记住：**好的决策不是完美的决策，而是在已知信息下的最佳选择，并有灵活调整的能力。**
