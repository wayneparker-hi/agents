# Capability Modeling

将业务能力结构化为**三层体系**（L1 业务域 → L2 核心能力 → L3 细粒度组件），为应用分解、服务拆分、组织结构奠定基础。

## When to Use This Skill

- 🏢 **企业架构规划**：从能力视角审视整个企业
- 🏗️ **应用分解**：将业务能力直接映射为应用/微服务
- 👥 **组织设计**：根据能力设计团队结构
- 🔄 **能力演进**：规划新能力的增加和现有能力的优化
- 📊 **能力差距分析**：识别缺失的能力

## Core Concepts

### 1. L1 业务域（Business Domain）
**定义**：最高层的业务分类，通常对应企业的主要价值流。

**特征**：
- 3-10 个左右
- 相对稳定，不经常变化
- 可能对应一个部门或事业线

**例子（电商平台）**：
```
1. 用户与账户 - 负责用户身份和账户管理
2. 商品与库存 - 负责商品信息和库存管理
3. 订单与支付 - 负责订单处理和支付
4. 物流与履约 - 负责发货和物流
5. 风险与合规 - 负责风险控制和合规
```

### 2. L2 核心能力（Capability）
**定义**：业务域内部的一个具体的、可独立衡量的能力。

**特征**：
- 每个 L1 下 5-15 个
- 相对稳定，但可能需要改进
- 通常对应一个团队或应用

**例子（用户与账户 域）**：
```
L1: 用户与账户
├─ L2.1 身份认证 - 支持多种登录方式（密码、短信、二维码）
├─ L2.2 账户管理 - 创建、编辑、注销账户
├─ L2.3 权限管理 - 定义和验证用户权限
├─ L2.4 用户资料 - 管理用户基本信息和偏好
└─ L2.5 安全设置 - 两步验证、设备管理等
```

### 3. L3 细粒度组件（Component）
**定义**：能力内部的最小的、独立可部署的功能单元。

**特征**：
- 最细粒度，数量较多
- 频繁变化
- 可能对应一个微服务或代码模块

**例子（身份认证 能力）**：
```
L2: 身份认证
├─ L3.1 邮箱验证 - 发送邮件链接进行验证
├─ L3.2 短信验证 - 发送验证码到手机
├─ L3.3 二次认证 - 在敏感操作时要求重新验证
├─ L3.4 会话管理 - 管理登录状态和 Token
└─ L3.5 设备指纹 - 检测异常登录
```

### 4. 能力矩阵（Capability Matrix）
**定义**：一个展示能力分布的矩阵，用于识别缺口和重复。

**用途**：
- 可视化能力地景
- 识别缺失的能力
- 识别重复的能力
- 规划资源分配

## Step-by-Step Guide

### Step 1: 确定 L1 业务域
从整个企业或产品出发，识别 3-10 个最高层的业务分类。

**方法**：
- 与业务部门讨论：不同的业务部门或事业线
- 分析价值链：从客户来看，企业主要做什么
- 参考行业标准：同行怎么划分

**模板**：
```
我们的主要业务域：
1. ________________ - [简要描述]
2. ________________ - [简要描述]
3. ________________ - [简要描述]
...
```

### Step 2: 分解 L2 核心能力
对每个 L1 业务域，识别 5-15 个核心能力。

**方法**：
- 从 Event Storming 的聚合出发
- 问"实现这个域需要什么能力？"
- 参考流程模型

**模板**：
```
L1: 商品与库存
├─ 商品管理 - 商品信息的创建、编辑、下架
├─ 库存管理 - 库存的增加、扣除、预占
├─ SKU 管理 - 不同规格的商品管理
├─ 分类管理 - 商品分类和标签
├─ 搜索服务 - 商品的快速搜索和过滤
└─ 推荐引擎 - 基于算法的商品推荐
```

### Step 3: 标记能力属性
为每个 L2 能力标记关键属性：

**能力成熟度**：
- 1 星：手工、低效
- 2 星：半自动化
- 3 星：自动化、成熟
- 4 星：优化、高效
- 5 星：业界领先

**战略重要性**：
- 核心：直接带来竞争优势
- 重要：支撑核心业务
- 支撑：基础设施类
- 通用：行业通用，不具差异性

**例子**：
```
能力: 用户身份认证
- 成熟度: 3 星（自动化）
- 战略性: 核心（直接关系到用户体验和安全）
- 团队: 账户平台团队
```

### Step 4: 设计 L3 细粒度组件
对每个关键的 L2 能力，进一步分解为 L3 组件。

**方法**：
- 从流程模型的步骤出发
- 考虑"可独立复用的最小单位是什么"
- 考虑"将来可能会单独演进或替换的部分"

**模板**：
```
L2: 商品搜索
├─ L3.1 全文搜索 - 基于 Elasticsearch 的文本搜索
├─ L3.2 精细过滤 - 按分类、价格、销量过滤
├─ L3.3 排序算法 - 综合排序（销量、评价、新品）
├─ L3.4 搜索建议 - 基于用户历史和热词的建议
└─ L3.5 搜索分析 - 统计和分析搜索行为
```

### Step 5: 建立能力矩阵
用矩阵方式展示能力分布，便于识别缺口。

**矩阵维度**：
- 纵轴：各个 L1 域
- 横轴：各个关键能力
- 格子：成熟度、是否需要改进

**用途**：
- 一眼看出能力缺口
- 识别重复投资的地方
- 规划改进的优先级

### Step 6: 定义能力接口
对每个 L2 能力定义清晰的接口（API 或契约）。

**模板**：
```
能力: 用户身份认证

接口 1: 发送验证码
输入: 邮箱或手机
输出: 验证码已发送（1分钟内有效）

接口 2: 验证验证码
输入: 验证码、用户标识
输出: 成功 / 验证码错误 / 已过期

接口 3: 创建会话
输入: 用户ID
输出: JWT Token + 过期时间
```

## Best Practices

1. **自上向下分解**：从 L1 开始逐级分解，避免混乱
2. **限制广度**：L1 最多 10 个，L2 最多 15 个，避免过度细化
3. **语言一致**：用业务语言而非技术术语命名
4. **定期评审**：能力模型要定期更新，反映组织的演进
5. **与组织对齐**：能力结构应该对应到团队结构（康威定律）
6. **支持演进**：能力模型要支持新能力的增加和现有能力的优化

## Common Pitfalls

- **❌ 能力太多**：列了 50+ 个能力，难以管理
  → **✅ 解决**：聚合相关能力到 L2，严格限制数量

- **❌ 层级混乱**：L1、L2、L3 的定义模糊
  → **✅ 解决**：清晰定义每层的特征和标准

- **❌ 技术驱动**：用技术术语命名能力
  → **✅ 解决**：用业务语言，从客户角度思考

- **❌ 一成不变**：定了之后就不更新
  → **✅ 解决**：定期评审和演进

## Key Questions

- 我们有哪些核心的业务域？
- 每个域的关键能力有哪些？
- 这些能力之间有什么依赖关系？
- 哪些能力需要改进？
- 组织结构应该如何调整来支持这个能力模型？
