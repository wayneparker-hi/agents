# 能力矩阵与评估

## 能力矩阵的用途

能力矩阵用于：
1. **清晰展示**：所有业务能力及其特征
2. **对标评估**：与竞争对手或行业标准对比
3. **投资规划**：决定哪些能力需要投资
4. **人员分配**：指导团队资源分配
5. **成熟度追踪**：监控能力演进

---

## 矩阵 1：能力的四象限分析

### 重要性 vs 成熟度

```
                   高成熟度
                      ↑
                      │
投          III        │      I
资        (优化)       │   (保持)
度          │          │      │
          │          │      │
   ────────┼──────────┼──────────
          │          │      │
投          │          │      │
资    IV   │      II   │
价        (提升)       │   (建设)
值          │          │      │
          │          │      │
                      ↓
                   低成熟度

I 象限（高重要性 + 高成熟度）：保持优势
  - 订单创建、库存检查、支付处理
  - 策略：持续优化、性能提升、成本降低

II 象限（高重要性 + 低成熟度）：重点建设
  - 用户画像、商品推荐、风险控制
  - 策略：投入资源、加快开发、提升成熟度

III 象限（低重要性 + 高成熟度）：适度优化
  - 订单统计、数据报告
  - 策略：维持现状、适度优化、考虑自动化

IV 象限（低重要性 + 低成熟度）：评估淘汰
  - 过时功能、试验性功能
  - 策略：评估是否继续投资、考虑下线
```

### 绘制矩阵步骤

```
第 1 步：列出所有能力
  - 订单创建
  - 库存检查
  - 支付处理
  - 用户认证
  - ...

第 2 步：评估重要性（1-10 分）
  - 10 = 核心竞争力、收入直接相关
  - 5 = 基础功能、必需但非差异化
  - 1 = 可选功能、边缘价值

第 3 步：评估成熟度（1-10 分）
  - 10 = 成熟稳定、自动化程度高、最佳实践内化
  - 5 = 相对成熟、有一定流程、可继续优化
  - 1 = 初期阶段、流程混乱、问题众多

第 4 步：绘制在 2x2 矩阵中
  - X 轴：成熟度（1-10）
  - Y 轴：重要性（1-10）
  - 点的大小：团队规模或投资金额
```

### 评分标准

**重要性评分标准**：
```
10 分：核心竞争力
  - 直接贡献收入
  - 与战略目标高度相关
  - 例：订单创建、支付处理

8-9 分：重要业务能力
  - 支持主要业务流程
  - 影响用户体验
  - 例：库存检查、订单查询

6-7 分：基础能力
  - 必需但非差异化
  - 行业通用
  - 例：用户认证、数据查询

4-5 分：支持能力
  - 辅助主业务
  - 优化但非关键
  - 例：订单统计、数据分析

1-3 分：可选能力
  - 边缘价值
  - 可选功能
  - 例：过时功能、试验功能
```

**成熟度评分标准**：
```
9-10 分：优化阶段
  - 自动化程度 > 80%
  - 完全的监控和告警
  - 文档完整
  - 例：订单创建系统

7-8 分：定义阶段
  - 流程清晰
  - 有文档和测试
  - 相对稳定
  - 例：库存检查、支付处理

5-6 分：受管理阶段
  - 有基本流程
  - 文档不完整
  - 需要继续优化
  - 例：订单查询、用户认证

3-4 分：初期阶段
  - 流程混乱
  - 文档缺乏
  - 问题众多
  - 例：商品推荐、用户画像

1-2 分：概念阶段
  - 刚刚开始
  - 无清晰方向
  - 问题未知
  - 例：新功能、试验性功能
```

## 矩阵 3：能力的跨域依赖矩阵

### 依赖关系表

```
        │ 订单 │ 库存 │ 支付 │ 用户 │ 商品 │ 物流
────────┼──────┼──────┼──────┼──────┼──────┼──────
订单    │  -   │  ✓   │  ✓   │  ✓   │  ✓   │  -
库存    │  -   │  -   │  -   │  -   │  ✓   │  -
支付    │  -   │  -   │  -   │  ✓   │  -   │  -
用户    │  -   │  -   │  -   │  -   │  -   │  -
商品    │  -   │  -   │  -   │  -   │  -   │  -
物流    │  ✓   │  -   │  -   │  ✓   │  -   │  -

✓ = 有依赖
- = 无依赖

分析：
- 订单能力依赖 4 个其他域 → 高耦合，需要简化
- 库存、支付、用户、商品、物流中有些可以独立 → 低耦合，可独立演进
```

### 依赖复杂度评估

```
耦合度 = (依赖的其他域数) / (总域数)

订单域：
  依赖数 = 4
  总域数 = 6
  耦合度 = 4/6 = 67% → 高耦合，需要解耦

用户域：
  依赖数 = 0
  总域数 = 6
  耦合度 = 0/6 = 0% → 完全独立

目标：
  - 核心域耦合度 < 50%
  - 支持域耦合度 < 70%
  - 通用域耦合度 < 30%
```

### 识别组织与能力的不对齐

```
问题 1：能力负责人不清
  症状：订单查询能力由 2 个团队维护
  影响：响应慢、重复工作
  解决：指定一个团队负责

问题 2：团队跨域过多
  症状：订单团队需要直接调用 5 个其他域的能力
  影响：耦合度高、难以独立演进
  解决：通过 API 或事件驱动解耦

问题 3：能力缺失
  症状：商品推荐能力重要但无人维护
  影响：功能不完整、用户体验差
  解决：新增团队或资源分配
```

## 关键建议

1. **定期评估**：每个季度重新评估能力矩阵
2. **透明共享**：与所有团队分享矩阵，保持对齐
3. **数据驱动**：用度量指标支撑评分
4. **行动计划**：每个象限都应该有明确的行动计划
5. **优先级明确**：不同象限采用不同的投资策略
6. **持续跟踪**：定期更新进度，监控成熟度演进
