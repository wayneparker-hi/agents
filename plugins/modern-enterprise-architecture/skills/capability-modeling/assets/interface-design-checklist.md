# 接口设计检查清单

## 为什么接口设计很重要？

好的接口设计能让：
- 使用者快速理解和使用
- 维护者容易扩展和演进
- 系统高效通信和协作

---

## 接口设计检查清单

### 第 1 部分：基础设计

```
□ 接口有清晰的职责吗？
  - 接口应该做一件事，且做好它
  - 反例：OrderService 有 10+ 个无关的方法

□ 方法名清晰吗？
  - 使用祈使式动词 (create, find, update, delete)
  - 使用业务术语，而不是技术术语
  - 反例：process() 太模糊 → validate(), approve() 更清晰

□ 参数个数合适吗？
  - 建议：≤ 3 个参数
  - 过多参数：考虑用对象包装
  ✅ Good: void approve(Order order, ApprovalContext context)
  ❌ Bad: void approve(String orderId, String approvalType, String reason, ...)

□ 参数命名有意义吗？
  - 使用完整的名字，避免缩写
  - ✅ Good: void approve(Order order)
  - ❌ Bad: void approve(O o)

□ 返回值有意义吗？
  - 返回值应该包含足够信息
  - 避免返回 null
  - 考虑返回 Optional 或 Result 对象
  ✅ Good: Optional<Order> findById(OrderId id)
  ❌ Bad: Order findById(OrderId id)  // 什么时候返回 null？

□ 异常定义清晰吗？
  - 列出所有可能的异常
  - 每个异常都有含义
  ✅ Good: throws OrderNotFoundException, InsufficientStockException
  ❌ Bad: throws Exception
```

### 第 2 部分：一致性

```
□ 同类操作命名一致吗？
  - 创建：create, make, build
  - 查询：find, get, query, search
  - 更新：update, modify, change
  - 删除：delete, remove, cancel
  选一种并坚持使用

□ 参数顺序一致吗？
  - 建议：主对象 → 条件 → 选项
  ✅ Good: find(criteria, filters, options)
  ❌ Bad: find(options, criteria, filters)

□ 返回值类型一致吗？
  - 单个对象用单数：Order, User
  - 多个对象用列表：List<Order>, List<User>
  - 避免混用 List 和 Set 来表示同一个概念

□ 错误处理方式一致吗？
  - 统一用异常或返回 Result 对象
  - 不要两种方式混用
```

### 第 3 部分：API 层接口（HTTP/REST）

```
□ 请求方法正确吗？
  - GET：查询，无副作用
  - POST：创建，有副作用
  - PUT：完全替换
  - PATCH：部分修改
  - DELETE：删除
  ✅ Good: POST /orders, GET /orders/123
  ❌ Bad: GET /orders?action=create

□ URL 路径清晰吗？
  - 使用名词，不用动词：/orders 而非 /getOrders
  - 使用单数还是复数：选一种并坚持
  ✅ Good: /orders, /orders/123
  ❌ Bad: /order, /getOrder/123

□ 请求体结构清晰吗？
  - 只包含必要的字段
  - 有明确的字段含义
  - 考虑版本化：{version: "v1", data: {...}}

□ 响应体结构清晰吗？
  - 一致的响应格式
  - 包含足够的元数据（状态、错误信息等）
  ✅ Good:
    {
      "code": 0,
      "message": "success",
      "data": {...},
      "timestamp": "2024-11-10T10:00:00Z"
    }
  ❌ Bad: 返回值格式随意变化

□ 状态码正确吗？
  - 200：成功
  - 201：创建成功
  - 400：请求错误
  - 401：未认证
  - 403：无权限
  - 404：不存在
  - 500：服务器错误
```

### 第 4 部分：面向对象接口（Class/Interface）

```
□ 接口是否符合 SOLID 原则？
  - S (Single)：单一职责
  - O (Open)：开闭原则
  - L (Liskov)：里氏替换原则
  - I (Interface)：接口隔离原则
  - D (Dependency)：依赖反转原则

□ 是否有继承层次过深？
  - 建议：≤ 3 层
  - 过深导致理解困难

□ 是否有多继承或复杂的接口组合？
  - 容易导致名字冲突
  - 难以理解

□ 方法是否都被实现类使用？
  - 移除未使用的方法
  - 如果很多方法未使用，考虑分离接口

□ 接口的大小合适吗？
  - 建议：3-8 个方法
  - 过多：考虑分离为多个接口
```

### 第 5 部分：可扩展性

```
□ 接口支持版本化吗？
  - 新增字段不应破坏旧客户端
  - 考虑：v1, v2 版本共存
  ✅ Good: /api/v1/orders, /api/v2/orders
  ❌ Bad: /api/orders (版本无法管理)

□ 可以添加新参数而不破坏旧调用吗？
  - 新参数应该有默认值
  ✅ Good:
    def approve(order, context=None, reason=""):
  ❌ Bad:
    def approve(order, context, reason):  // 添加参数就破坏旧调用

□ 可以添加新返回字段而不破坏旧客户端吗？
  - 客户端应该忽略不认识的字段
  ✅ Good: 客户端使用 field.getOrDefault()
  ❌ Bad: 客户端直接访问不存在的字段

□ 是否支持向后兼容的扩展？
  - 使用 decorator 模式添加新功能
  - 使用 strategy 模式支持新策略
```

### 第 6 部分：文档和示例

```
□ 是否有清晰的文档？
  - 方法签名
  - 参数说明
  - 返回值说明
  - 异常说明
  - 使用示例

□ 文档示例是否完整？
  - 基本用法
  - 错误处理
  - 边界情况
  - 最佳实践

□ 文档是否是最新的？
  - 接口变更时更新文档
  - 标记已弃用的接口

□ 接口变更是否有迁移指南？
  - 从旧接口到新接口的步骤
  - 何时需要升级
  - 可能的陷阱
```

### 第 7 部分：性能和安全性

```
□ 接口性能是否可接受？
  - 平均响应时间 < 1s
  - P95 响应时间 < 5s
  - 吞吐量满足业务需求

□ 是否有合适的超时设置？
  - 避免无限等待
  - 超时时间考虑网络延迟

□ 接口是否安全？
  - 认证：确认身份
  - 授权：确认权限
  - 输入验证：防止注入攻击
  - 日志记录：便于审计

□ 是否有速率限制？
  - 防止滥用
  - 保护服务可用性

□ 敏感信息是否被隐藏？
  - 不在日志中暴露密钥
  - 不在错误信息中暴露系统细节
```

### 第 8 部分：可测试性

```
□ 接口是否易于测试？
  - 无副作用或副作用清晰
  - 无隐藏依赖
  - 易于 mock 和 stub

□ 是否有测试覆盖？
  - 快乐路径：✅ 成功case
  - 异常路径：✅ 异常case
  - 边界情况：✅ 边界值

□ 测试是否稳定？
  - 不依赖外部服务（除非集成测试）
  - 不依赖时间或随机数据

□ 错误消息是否便于测试？
  - 错误信息清晰
  - 错误类型明确
  - 易于断言
```

## 常见错误

| 错误 | 症状 | 修正 |
|------|------|------|
| 职责混乱 | 接口有 10+ 个无关方法 | 分离为多个接口 |
| 参数过多 | 调用时要传 5+ 个参数 | 用对象包装参数 |
| 返回 null | 使用者需要频繁 null check | 返回 Optional 或 Result |
| 异常过泛 | 只抛 Exception | 定义具体异常类 |
| 文档不全 | 使用者经常问怎么用 | 补充文档和示例 |
| 版本混乱 | v1 和 v2 调用混合 | 明确版本控制策略 |
| 性能差 | 响应时间 > 10s | 性能优化或异步处理 |

---

## 关键建议

1. **接口优先**：在实现前设计接口
2. **从简开始**：最简单的接口满足需求即可
3. **考虑使用者**：换位思考，设计易用的接口
4. **定期评审**：收集反馈，逐步改进
5. **向后兼容**：扩展接口时不要破坏旧调用
6. **完善文档**：好文档抵得上 100 行代码
