# 能力层次设计指南

## 三层能力模型

能力层次从粗到细分为三层，每层有明确的职责和复用范围。

---

## 第一层：L1 业务域（Business Domain）

### 定义

最粗粒度的业务能力划分，对标 DDD 中的"子域（Subdomain）"。代表企业的主要业务领域。

### 特征

```
粒度：粗
数量：通常 3-8 个
覆盖范围：整个公司或事业部
生命周期：较长（通常 1+ 年）
所有者：域团队负责人
复用范围：跨部门
```

### 示例

**电商公司的 L1 业务域**：

```
┌─────────────────────────────────────────────────────────┐
│ 电商企业                                                │
├──────────────────┬──────────────────┬──────────────────┤
│ 订单域           │ 库存域           │ 支付域           │
│ (Order Domain)   │ (Inventory)      │ (Payment)        │
├──────────────────┼──────────────────┼──────────────────┤
│ 商品域           │ 用户域           │ 营销域           │
│ (Product)        │ (User)           │ (Marketing)      │
├──────────────────┼──────────────────┼──────────────────┤
│ 售后域           │ 物流域           │                  │
│ (Aftersales)     │ (Logistics)      │                  │
└──────────────────┴──────────────────┴──────────────────┘
```

### 识别 L1 的问题清单

```
□ 这个域有独立的业务价值吗？
□ 这个域是否有独立的团队或人员负责？
□ 这个域的数据模型是独立的吗？
□ 这个域是否有明确的边界和职责？
□ 这个域的变更周期是否独立？
```

---

## 第二层：L2 业务能力（Business Capability）

### 定义

中等粒度的能力，代表为了支持某个业务流程或用户目标，系统需要提供什么。

### 特征

```
粒度：中
数量：L1 下通常 5-10 个
覆盖范围：单个业务域内
生命周期：中等（通常 3-12 个月）
所有者：功能团队或 Scrum Master
复用范围：域内复用或少量跨域
```

### 示例

**订单域下的 L2 业务能力**：

```
订单域 (L1)
├─ 订单生命周期管理 (L2)
│  ├─ 订单创建
│  ├─ 订单修改
│  └─ 订单取消
├─ 订单处理流程 (L2)
│  ├─ 订单审核
│  ├─ 库存检查
│  └─ 发货
├─ 订单查询与分析 (L2)
│  ├─ 订单查询
│  ├─ 订单统计
│  └─ 订单分析
└─ 订单规则与策略 (L2)
   ├─ 优惠券规则
   ├─ 限制规则
   └─ 超时规则
```

### 识别 L2 的问题清单

```
□ 这个能力对应一个或几个具体的业务流程吗？
□ 这个能力是否有明确的输入和输出？
□ 这个能力的实现是否依赖多个 L3 组件？
□ 这个能力对用户来说是否有业务意义？
□ 这个能力是否有独立的 API 或接口？
```

### L2 的分类

**按流程分类**：
- 核心能力：支持主要流程（如订单创建、支付）
- 支持能力：支持核心能力（如用户认证、日志记录）
- 管理能力：管理和优化（如数据分析、性能监控）

**按价值分类**：
- 战略能力：核心竞争力，直接贡献收入
- 基础能力：必需但非差异化（如用户管理）
- 通用能力：行业通用（如支付、物流）

---

## 第三层：L3 技术组件（Technical Component）

### 定义

最细粒度的能力，代表具体的技术实现模块。一个 L2 能力可能由多个 L3 组件实现。

### 特征

```
粒度：细
数量：L2 下通常 2-5 个
覆盖范围：单个 L2 能力内
生命周期：短（通常 1-3 个月）
所有者：开发团队或模块负责人
复用范围：组件内复用或特定能力复用
```

### 示例

**"订单创建"L2 能力下的 L3 组件**：

```
订单创建 (L2)
├─ OrderValidator (L3)
│  └─ 验证订单信息
├─ InventoryChecker (L3)
│  └─ 检查库存可用性
├─ PricingCalculator (L3)
│  └─ 计算订单价格
├─ OrderRepository (L3)
│  └─ 持久化订单数据
└─ OrderEventPublisher (L3)
   └─ 发布订单事件
```

### 识别 L3 的问题清单

```
□ 这个组件是否可以独立开发、测试和部署？
□ 这个组件的接口是否清晰且稳定？
□ 这个组件是否有明确的数据模型？
□ 这个组件是否可以被多个 L2 能力使用？
□ 这个组件的职责是否单一？
```

## 三层间的关系

### 关系图

```
L1: 业务域
├─ 覆盖：公司级业务分类
├─ 所有者：域团队（多人）
└─ 稳定性：高
     ↓
     ├─ 包含
     ↓
L2: 业务能力
├─ 覆盖：流程级或功能级
├─ 所有者：功能团队（5-15 人）
└─ 稳定性：中
     ↓
     ├─ 依赖
     ↓
L3: 技术组件
├─ 覆盖：模块级或服务级
├─ 所有者：开发团队（2-5 人）
└─ 稳定性：低
```

### 依赖方向

**正确**：
- L3 组件只依赖 L3 组件
- L2 能力依赖 L3 组件
- L1 域包含 L2 能力
```
L1 ← 包含 ← L2 ← 依赖 ← L3
```

**错误**：
- ❌ L2 能力跨越 L1 边界直接依赖其他 L1 的 L2
- ❌ L3 组件依赖 L2 能力
- ❌ L1 直接依赖 L3 组件
```
L2 ← 不应该跨 L1 边界 → L2 (❌)
L3 ← 不应该依赖 → L2 (❌)
```

## 跨层通信

### L2 之间的通信

**同 L1 内**：可以直接调用
```
订单域中：订单查询能力 → 订单管理能力 ✅ 直接调用
```

**跨 L1**：必须通过事件或 API
```
订单域 → 库存域：OrderCreated Event → InventoryCheck ✅ 事件驱动
```

### L3 组件的通信

**最小通信原则**：
- 组件间通过接口通信
- 避免跨能力的组件直接调用
- 复杂的跨组件调用应该在 L2 能力层协调

### 通信模式对比

```
┌────────────────┬──────────────┬──────────────────┬─────────────────┐
│ 通信模式       │ 场景         │ 优势             │ 劣势            │
├────────────────┼──────────────┼──────────────────┼─────────────────┤
│ 同步调用       │ L3 组件间    │ 实时性强         │ 强耦合          │
│ (函数调用)     │ 同 L1 内     │ 实现简单         │ 扩展性差        │
├────────────────┼──────────────┼──────────────────┼─────────────────┤
│ 事件驱动       │ 跨 L1        │ 低耦合           │ 最终一致性      │
│ (发布-订阅)    │ 异步处理     │ 高复用性         │ 调试困难        │
├────────────────┼──────────────┼──────────────────┼─────────────────┤
│ 接口/API       │ L2 对外      │ 边界清晰         │ 多轮往返        │
│ (HTTP/gRPC)    │ 跨服务       │ 版本控制容易     │ 性能开销        │
└────────────────┴──────────────┴──────────────────┴─────────────────┘
```

## 能力的演进

### 从 L3 到 L2 再到 L1

```
早期：
├─ 订单查询模块 (L3) ← 单个组件
│   ↓
中期：
├─ 订单查询模块 (L3)
├─ 订单分析模块 (L3)
├─ 订单导出模块 (L3)
│   ↓
│   聚合为 → 订单查询与分析能力 (L2)
│   ↓
晚期：
├─ 订单查询与分析 (L2)
├─ 订单创建处理 (L2)
├─ 订单管理 (L2)
│   ↓
│   聚合为 → 订单域 (L1)
```

### 标志

**需要提升粒度**：
- 该层的实体数过多（L2 > 15 个，L3 > 20 个）
- 存在天然的分组或分类
- 多个实体有共同的所有者或团队
- 需要跨越该层设置边界

**需要细化粒度**：
- 单个实体的职责过重（>1000 行代码）
- 存在多个清晰的子模块
- 需要独立扩展或优化
- 可以独立开发和测试

---

## 关键建议

1. **从 L1 开始**：先划分业务域，再设计 L2 和 L3
2. **不要跳层**：L1 应该通过 L2 来包含 L3，不要直接跳过 L2
3. **定期评审**：随着业务发展，定期重新评审各层的划分
4. **文档化**：创建能力地图，让所有人理解三层关系
5. **工具支持**：使用工具（如 ArchiMate）可视化能力层次
