# 数据一致性需求定义模板

## 目的

本模板帮助团队系统地定义和文档化数据一致性需求，为架构设计提供清晰的指导。

### 1.2 一致性需求分析

```
□ 数据 1: 库存数量

业务含义：
  └─ 仓库中可销售的商品数量

强一致性的业务后果：
  ├─ 不足：商品可能超卖，导致无法履行订单
  ├─ 影响：客户投诉、退单、赔偿
  ├─ 成本评估：1 个超卖订单赔偿 100 元
  └─ 风险等级：高

不一致的可接受范围：
  ├─ 短期不一致：允许（< 1 分钟）
  ├─ 长期不一致：不允许（> 10 分钟）
  ├─ 最大延迟：5 分钟
  └─ 可接受的超卖比例：< 0.1%

一致性需求：最终一致性 + 预留机制
  ├─ 下单时预留库存（强一致）
  ├─ 库存更新异步同步
  ├─ 定期对账校正


□ 数据 2: 账户余额

业务含义：
  └─ 用户可用的资金

强一致性的业务后果：
  ├─ 不足：用户可能透支
  ├─ 影响：财务损失、法律风险
  ├─ 成本评估：每笔透支平均损失 1000 元
  └─ 风险等级：很高

不一致的可接受范围：
  ├─ 短期不一致：不允许
  ├─ 任何不一致都不可接受
  └─ 必须强一致

一致性需求：强一致性
  ├─ 每次转账必须原子性
  ├─ 使用分布式事务保证
```

## 第二部分：一致性级别选择

### 2.1 一致性模型评估

```
□ 候选模型评估

模型：强一致性
  ├─ 定义：所有副本实时一致
  ├─ 性能影响：TPS 从 10000 降到 1000
  ├─ 可用性影响：任何副本故障都阻塞
  ├─ 实现成本：高（需要分布式事务）
  ├─ 维护成本：高
  └─ 推荐等级：⭐⭐（仅用于关键数据）

模型：最终一致性
  ├─ 定义：最终会一致，中间可能不一致
  ├─ 性能影响：基本无影响
  ├─ 可用性影响：无影响
  ├─ 实现成本：中（需要同步机制）
  ├─ 维护成本：中
  └─ 推荐等级：⭐⭐⭐（推荐大多数场景）

模型：会话一致性
  ├─ 定义：同一会话内一致
  ├─ 性能影响：低
  ├─ 可用性影响：无
  ├─ 实现成本：低
  ├─ 维护成本：低
  └─ 推荐等级：⭐⭐⭐（用于会话数据）

□ 选择推荐

关键数据（库存、余额）：
  └─ 选择：最终一致性 + 预留/冻结机制

非关键数据（用户昵称、等级）：
  └─ 选择：最终一致性（简单异步）

会话数据（用户配置、购物车）：
  └─ 选择：会话一致性或最终一致性
```

### 2.2 一致性延迟定义

```
□ 定义可接受的延迟

数据类型              | 可接受延迟 | 监控告警阈值
──────────────────────┼──────────┼─────────────
库存数量              | < 5 分钟  | > 2 分钟
账户余额              | 实时      | > 10 秒
用户信息              | < 1 小时  | > 30 分钟
订单状态              | < 1 分钟  | > 30 秒
用户等级              | < 1 天    | > 6 小时
产品推荐              | < 6 小时  | > 2 小时

延迟定义：
  ├─ 是指数据在所有系统中达成一致的最长时间
  ├─ 包括传输延迟、处理延迟、等待延迟
```

## 第三部分：同步机制设计

### 3.1 数据同步方案

```
□ 选择同步方式

数据源                | 目标系统 | 同步方式 | 同步频率 | 优先级
──────────────────────┼──────────┼────────┼────────┼────────
库存数据（WMS）       | 电商     | 消息队列 | 实时   | 高
订单数据              | CRM      | CDC    | 准实时 | 高
用户数据              | BI系统   | 批量   | 每天   | 低

同步方式选择：

实时同步（消息队列/事件驱动）
  ├─ 场景：库存、订单、支付等关键数据
  ├─ 延迟：< 1 秒
  ├─ 成本：中等
  └─ 复杂度：中等

准实时同步（CDC）
  ├─ 场景：需要完整变更历史的数据
  ├─ 延迟：< 1 分钟
  ├─ 成本：中等
  └─ 复杂度：中等

批量同步（定时任务）
  ├─ 场景：非关键数据，可以接受延迟
  ├─ 延迟：小时到天级别
  ├─ 成本：低
  └─ 复杂度：低

□ 可靠性保证

是否需要保证消息不丢失？□ 是 □ 否
  └─ 是：需要消息队列持久化和事务

是否需要保证消息不重复处理？□ 是 □ 否
  └─ 是：需要幂等性处理

是否需要保证顺序性？□ 是 □ 否
  └─ 是：需要有序的消息队列或分布式锁
```

### 3.2 同步工具选择

```
□ 技术选型

关键数据（库存）的同步：
  └─ 推荐：消息队列（Kafka、RabbitMQ）
  │   ├─ 优点：高可靠性、高吞吐量
  │   ├─ 缺点：不支持完整历史
  │   └─ 用于：实时事件驱动

历史完整的数据（订单）的同步：
  └─ 推荐：CDC（Debezium、Canal）
  │   ├─ 优点：捕捉所有变更、可以回溯
  │   ├─ 缺点：成本高、配置复杂
  │   └─ 用于：完整审计日志

非关键数据的同步：
  └─ 推荐：定时批量任务
  │   ├─ 优点：简单、成本低
  │   ├─ 缺点：延迟大
  │   └─ 用于：统计分析
```

## 第四部分：冲突和异常处理

### 4.1 冲突检测

```
□ 识别可能的冲突场景

场景 1：并发更新冲突
  ├─ 描述：两个系统同时更新同一条数据
  ├─ 例子：库存在 WMS 和电商系统同时扣减
  ├─ 检测方法：版本号、时间戳对比
  └─ 概率：___ % 的订单会遇到

场景 2：网络分区冲突
  ├─ 描述：系统 A 和 B 网络中断，各自更新数据
  ├─ 例子：库存在两个分区中不同步增加
  ├─ 检测方法：最终对账时发现
  └─ 恢复时间：___ 分钟

场景 3：消息丢失
  ├─ 描述：数据更新消息丢失
  ├─ 例子：库存减 1 的消息未到达电商系统
  ├─ 概率：___ %（根据中间件设置）
  └─ 恢复：定期对账

□ 冲突解决策略

冲突时的决策规则：
  ├─ 保留最新的版本：使用 MAX(timestamp)
  ├─ 保留最大值：MAX(value)（用于库存）
  ├─ 保留最小值：MIN(value)（用于余额）
  ├─ 人工介入：记录冲突，告警给管理员
  └─ 其他规则：_________
```

### 4.2 一致性检查与修复

```
□ 定义一致性检查规则

检查 1：库存对账
  ├─ 对账频率：每小时
  ├─ 对账规则：WMS 库存 = 电商库存（允许差异 < 1%）
  ├─ 发现不一致时：
  │  ├─ 查看消息日志，找出差异原因
  │  ├─ 如是消息丢失：手动同步
  │  ├─ 如是并发冲突：以 WMS 为准，重置电商库存
  │  └─ 记录事件供后续分析
  └─ 告警规则：差异 > 5% 时即时告警

检查 2：订单对账
  ├─ 对账频率：每天
  ├─ 对账范围：前一天的所有订单
  ├─ 对账规则：订单系统订单数 = CRM 订单数
  └─ 告警规则：差异 > 0% 时即时告警

□ 修复流程

发现不一致时：
  Step 1：检查根本原因
    └─ 消息丢失？网络问题？应用 bug？

  Step 2：选择修复策略
    ├─ [ ] 重新发送数据
    ├─ [ ] 回滚并重新处理
    ├─ [ ] 应用补偿逻辑
    ├─ [ ] 以权威系统为准进行数据同步
    └─ [ ] 人工处理

  Step 3：验证修复
    └─ 修复后进行对账确认

  Step 4：分析和改进
    ├─ 为什么会发生？
    ├─ 如何防止再次发生？
    └─ 更新同步规则或工具配置
```

## 第五部分：监控与告警

### 5.1 监控指标

```
□ 定义关键监控指标

指标 1：数据延迟
  ├─ 定义：数据从源系统到目标系统的时间
  ├─ 测量方法：
  │  ├─ 源系统的修改时间戳
  │  ├─ 目标系统的接收时间戳
  │  └─ 差值 = 延迟
  ├─ 正常范围：< ___ 秒
  ├─ 警告阈值：> ___ 秒
  └─ 严重阈值：> ___ 秒

指标 2：同步成功率
  ├─ 定义：成功同步的消息数 / 总消息数
  ├─ 正常范围：> 99.99%
  ├─ 警告阈值：< 99.95%
  └─ 严重阈值：< 99%

指标 3：一致性检查通过率
  ├─ 定义：对账检查通过的比例
  ├─ 正常范围：100%
  ├─ 警告阈值：< 99.5%
  └─ 严重阈值：< 99%

指标 4：冲突检测率
  ├─ 定义：每天检测到的冲突数
  ├─ 正常范围：< ___ 个
  ├─ 警告阈值：> ___ 个
  └─ 严重阈值：> ___ 个

□ 建立监控仪表板

关键指标汇总表：
  ├─ 实时显示数据延迟
  ├─ 显示同步成功率趋势
  ├─ 显示最近的冲突/异常
  └─ 显示对账结果
```

### 5.2 告警规则

```
□ 高优先级告警（立即处理）

告警 1：同步失败
  ├─ 触发条件：连续 3 条消息同步失败
  ├─ 通知方式：电话 + 钉钉 + 邮件
  ├─ 对应人员：值班工程师
  └─ 响应时间：10 分钟

告警 2：数据延迟过大
  ├─ 触发条件：延迟 > 严重阈值
  ├─ 通知方式：电话 + 钉钉
  ├─ 对应人员：技术负责人
  └─ 响应时间：5 分钟

□ 中优先级告警（1 小时内处理）

告警 3：一致性检查失败
  ├─ 触发条件：检查通过率 < 99%
  ├─ 通知方式：钉钉 + 邮件
  ├─ 对应人员：数据团队
  └─ 响应时间：1 小时

□ 低优先级告警（日常处理）

告警 4：冲突过多
  ├─ 触发条件：每小时冲突 > 阈值
  ├─ 通知方式：邮件
  ├─ 对应人员：数据团队
  └─ 处理时间：下班前
```
