# 数据分层架构技能

## 概述

数据分层是大数据和数据仓库中的核心概念。合理的数据分层能够提升数据质量、提高查询性能、便于数据治理。

---

## 核心概念

### 为什么要分层？

```
单一数据库的问题：
  ├─ 原始数据混乱，难以使用
  ├─ 重复计算，浪费资源
  ├─ 修改原始数据有风险
  ├─ 难以追踪数据血缘
  └─ 无法快速支持新的分析需求

分层的好处：
  ✅ 清晰的数据流
  ✅ 逻辑分离
  ✅ 便于质量管理
  ✅ 提升查询性能
  ✅ 便于数据治理
```

### 经典的数据分层

```
业务系统          ↓
└─ OLTP 数据库（业务系统的数据）

  ↓ ETL（提取、转换、加载）

ODS 层（原始数据层）
└─ 结构接近源系统，做最少的转换

  ↓ ETL

DW 层（数据仓库层）
  ├─ DIM 层（维度）：维度表，如时间、产品、客户
  ├─ FACT 层（事实）：事实表，聚合指标
  └─ AGG 层（聚合）：汇总数据，供报表使用

  ↓ 数据提取

ADS 层（应用数据层）
└─ 直接供应用使用的数据
```

## 各层设计

### ODS 层（Operational Data Store）

**目的**：保存原始数据，最小化处理

**特点**：
- 结构和源系统相同或相近
- 保留完整的历史数据
- 不做复杂业务逻辑处理
- 作为数据质量的第一道防线

**包含的表**：
```
ODS 层表名约定：ods_[业务域]_[表名]

示例：
  └─ ods_order_order（订单表）
  └─ ods_order_order_item（订单项表）
  └─ ods_inventory_inventory（库存表）
  └─ ods_customer_customer（客户表）

特殊列：
  ├─ dw_insert_time：数据插入时间
  ├─ dw_update_time：数据更新时间
  ├─ is_delete：逻辑删除标记
  └─ dw_batch_id：数据批次 ID（用于追踪）
```

**设计原则**：
1. 尽量保持原始结构
2. 添加技术列（更新时间、删除标记等）
3. 保留完整的历史数据
4. 不做复杂的业务逻辑处理

### DIM 层（维度层）

**目的**：管理维度数据

**维度类型**：

```
缓慢变化维度（SCD）：

类型 1：覆盖（不保留历史）
  例：产品价格从 100 改为 120
  处理：直接更新，不保留历史
  风险：无法分析历史价格

类型 2：添加新行（保留完整历史）
  例：产品价格从 100 改为 120
  处理：添加新行，标记生效日期
  数据：
    product_id  price  start_date  end_date
    1           100    2024-01-01  2024-06-30
    1           120    2024-07-01  9999-12-31
  优势：能追踪完整历史
  劣势：行数增加

类型 3：添加历史列（保留前一个值）
  例：产品价格从 100 改为 120
  处理：添加新列保留旧值
  数据：
    product_id  current_price  previous_price
    1           120           100
  适用：只关心当前和前一个值
```

**维度表设计**：

```
维度表命名：dim_[维度名]

示例：
  └─ dim_date：日期维度
  └─ dim_product：产品维度
  └─ dim_customer：客户维度
  └─ dim_region：地区维度

特点：
  ├─ 主键唯一
  ├─ 宽表设计（包含丰富的属性）
  ├─ 变化频率低
  ├─ 支持钻取分析
  └─ 通常规模较小（可以全量加载到内存）
```

### FACT 层（事实层）

**目的**：存储业务过程中的可度量的事件

**事实表设计**：

```
事实表命名：fact_[过程名]

示例：
  └─ fact_order：订单事实表
  └─ fact_payment：支付事实表
  └─ fact_inventory_change：库存变化事实表

结构：
  ├─ 维度外键：order_id, customer_id, product_id, date_id
  ├─ 度量值：order_amount, quantity, discount
  ├─ 时间戳：order_date, update_date
  └─ 其他：status, flag

粒度定义：
  └─ 事实表的最细粒度是什么？
  └─ 例：订单事实表的粒度是一条订单，还是一个订单项？

增量 vs 全量：
  └─ 增量：只加载新增或变化的数据
  └─ 全量：每次加载所有数据
  └─ 优点：增量更高效，全量更简单
```

### AGG 层（聚合层）

**目的**：提供预计算的聚合指标，加快查询速度

**设计**：

```
聚合表命名：agg_[维度组合]_[指标]

示例：
  └─ agg_customer_day_order_count：每个顾客每天的订单数
  └─ agg_region_month_sales：每个地区每月销售额
  └─ agg_product_category_day_pv：每个产品类别每天的页面访问

内容：
  ├─ 维度列：customer_id, date, ...
  ├─ 聚合指标：order_count, total_sales, unique_visitors
  └─ 时间戳：created_at, updated_at

更新策略：
  ├─ 定时更新（每小时/每天）
  ├─ 实时更新（使用流计算）
  └─ 按需更新（用户查询时触发）
```

### ADS 层（应用数据层）

**目的**：直接支持应用和前端展示

**特点**：
- 与应用紧密结合
- 可能是聚合表、视图或专题数据
- 更新频率根据应用需求而定
- 数据已经处理到可直接使用的形式

**示例**：

```
销售看板的 ADS 表：
  └─ ads_daily_sales_summary
     ├─ date
     ├─ total_sales
     ├─ order_count
     ├─ average_order_value
     └─ region_breakdown

推荐系统的 ADS 表：
  └─ ads_user_recommendations
     ├─ user_id
     ├─ recommended_product_id
     ├─ score
     └─ reason
```

## 数据分层设计清单

```
□ 确定分层策略
  ├─ ODS → DW → ADS（三层）
  ├─ ODS → DIM + FACT + AGG → ADS（五层）
  └─ 或自定义分层

□ ODS 层设计
  ├─ 定义 ODS 表清单
  ├─ 定义技术列
  ├─ 定义数据清洗规则
  └─ 定义初始加载和增量加载策略

□ DIM 层设计
  ├─ 定义所有维度
  ├─ 确定维度的 SCD 类型
  ├─ 定义维度属性和层级
  └─ 定义维度的更新频率

□ FACT 层设计
  ├─ 定义事实表
  ├─ 确定事实表粒度
  ├─ 定义度量值
  ├─ 关联维度外键
  └─ 定义增量更新策略

□ AGG 层设计
  ├─ 定义常用的聚合维度组合
  ├─ 定义聚合指标
  ├─ 确定更新频率
  └─ 评估存储成本 vs 查询速度的权衡

□ ADS 层设计
  ├─ 与应用团队沟通数据需求
  ├─ 设计应用所需的数据结构
  ├─ 定义数据更新 SLA
  └─ 定义数据质量指标

□ 数据质量管理
  ├─ 定义每层的数据质量规则
  ├─ 建立监控告警
  ├─ 定义异常数据处理流程
  └─ 建立数据血缘追踪

□ 文档和沟通
  ├─ 绘制数据流图
  ├─ 创建数据字典
  ├─ 记录设计决策
  └─ 与数据使用者沟通
```

## 常见的数据分层错误

```
错误 1：分层过多或过少
  问题：要么层级太多导致复杂，要么太少导致数据混乱
  解决：根据实际需求设计，通常 3-5 层足够

错误 2：维度和事实表混乱
  问题：维度表太大，或事实表混入维度属性
  解决：严格按照维度和事实的定义设计

错误 3：聚合表设计不当
  问题：聚合粒度不对，或覆盖的场景不全
  解决：与数据用户沟通，了解常用的查询模式

错误 4：忽视数据质量
  问题：分层虽然完成，但数据质量堪忧
  解决：在每一层都加入数据质量校验

错误 5：分层后无法回源
  问题：数据加工过程中丢失信息，无法追溯原始数据
  解决：保留数据血缘，建立从 ADS 到源系统的追踪
```

## 最佳实践

```
1. 从业务需求出发
   ✅ 理解数据使用者的需求
   ✅ 根据需求设计分层

2. 保持简洁
   ✅ 分层数量合理（3-5 层）
   ✅ 每层的职责清晰

3. 数据质量第一
   ✅ 在 ODS 层做好清洗
   ✅ 每层都有质量检查

4. 文档完整
   ✅ 清晰的分层说明
   ✅ 详细的数据字典
   ✅ 数据血缘追踪

5. 定期评估
   ✅ 评估分层的有效性
   ✅ 根据业务变化调整
   ✅ 收集用户反馈
```
