# ODS 层设计模式与最佳实践

## 概述

ODS（Operational Data Store）层作为数据仓库的第一层，是原始数据与业务应用的桥梁。好的 ODS 设计直接影响整个数据仓库的质量。

---

## ODS 层的核心职责

### 1. 数据抽取与保存

```
业务系统 → ETL 抽取 → ODS 层保存
  │
  └─ 结构接近源系统
  └─ 保留完整历史数据
  └─ 最少的业务逻辑处理
```

**关键特点：**
- 保留源系统的原始结构（便于追踪）
- 保存全量数据（为后续处理提供完整信息）
- 最小化处理（保持数据纯净）

### 2. 数据质量的第一道防线

```
ODS 层的质量检查：
  ├─ 数据完整性检查
  │  ├─ 必填字段不为空
  │  ├─ 关键字段有效性验证
  │  └─ 数据范围检查
  │
  ├─ 数据一致性检查
  │  ├─ 关键字段值在预期范围内
  │  ├─ 相关字段的逻辑关系检查
  │  └─ 与源系统的对账
  │
  └─ 数据规范性检查
     ├─ 字段编码规范
     ├─ 日期格式统一
     └─ 数字精度检查
```

### 3. 数据血缘追踪

ODS 层必须支持完整的数据血缘追踪：

```
原始数据源 → ODS → DIM/FACT → AGG → ADS → 前端应用
     │                                         │
     └─────── 数据血缘链路 ──────────────────┘
```

## ODS 表设计模式

### 模式 1：全量覆盖 + 变化捕捉

**场景：** 源系统数据变化频繁，需要完整历史

```sql
-- ODS 表结构
CREATE TABLE ods_order_order (
  -- 原始字段（来自源系统）
  order_id          BIGINT PRIMARY KEY,
  customer_id       BIGINT,
  order_amount      DECIMAL(10,2),
  order_status      VARCHAR(20),
  created_date      DATE,
  updated_date      DATE,

  -- 技术列（数据仓库特有）
  dw_insert_time    TIMESTAMP,      -- 插入到 ODS 的时间
  dw_update_time    TIMESTAMP,      -- 更新时间
  dw_batch_id       VARCHAR(32),    -- 批次 ID，用于追踪
  is_delete         TINYINT,        -- 逻辑删除标记
  source_system     VARCHAR(50),    -- 源系统标识

  INDEX idx_customer (customer_id),
  INDEX idx_created (created_date)
);
```

**更新策略：**

```
首次加载：插入所有数据
后续更新：
  ├─ 增量更新：只加载新增/变化的数据
  ├─ 全量覆盖：定期全量重加（清空后重新加载）
  └─ 增量/全量混合：根据数据量选择
```

### 模式 2：按时间分区

**场景：** 数据量大，需要按时间进行分区

```sql
-- 按日期分区的 ODS 表
CREATE TABLE ods_event_log (
  event_id       BIGINT,
  user_id        BIGINT,
  event_type     VARCHAR(50),
  event_data     JSON,
  event_time     TIMESTAMP,
  dw_insert_time TIMESTAMP,
  dw_batch_id    VARCHAR(32)
)
PARTITIONED BY (event_date DATE);

-- 分区示例
-- ods_event_log_20240101
-- ods_event_log_20240102
-- ...
```

**优势：**
- 提升查询性能（只查询相关分区）
- 便于数据清理（删除过期分区）
- 支持并行处理

### 模式 3：临时表 + 增量合并

**场景：** 需要进行复杂的增量处理和数据校验

```
步骤 1：抽取数据到临时表
  └─ tmp_order_order_[batch_id]

步骤 2：数据校验和清洗
  └─ 检查数据质量
  └─ 处理异常数据

步骤 3：增量合并到 ODS
  └─ 新增：INSERT
  └─ 更新：UPDATE（如果存在）
  └─ 删除：标记 is_delete=1

步骤 4：清理临时表
  └─ DROP tmp_order_order_[batch_id]
```

**好处：**
- 支持事务性操作
- 可以回滚
- 错误恢复机制完善

## ODS 表的命名规范

### 标准命名格式

```
ods_[业务域]_[实体名]

示例：
  ├─ ods_order_order            -- 订单表
  ├─ ods_order_order_item       -- 订单项表
  ├─ ods_customer_customer      -- 客户表
  ├─ ods_customer_address       -- 客户地址表
  ├─ ods_inventory_warehouse    -- 仓库表
  ├─ ods_inventory_stock        -- 库存表
  └─ ods_payment_transaction    -- 交易表
```

### 技术列命名规范

```
dw_insert_time    -- 数据插入时间（首次加载时设置）
dw_update_time    -- 数据更新时间（每次更新都更新）
dw_batch_id       -- 批次 ID（用于追踪同一批次的数据）
dw_source_sys     -- 源系统（标识数据来源）
is_delete         -- 逻辑删除标记（0=未删除，1=已删除）
```

## ODS 层的数据清洗规则

### 1. 空值处理

```
规则：根据字段类型和业务意义处理空值

数值字段：
  └─ 空值 → 0（或其他合理的默认值）

字符字符：
  └─ 空值 → 'UNKNOWN'（或指定的默认值）

日期字段：
  └─ 空值 → NULL（保持空值，便于后续处理）

关键字段（不允许空值）：
  └─ 空值 → 数据质量告警，记录到错误表
```

### 2. 数据类型转换

```
源系统可能使用不同的数据类型：
  ├─ 字符串数字 → 数值类型
  ├─ 混合格式日期 → 标准日期格式
  ├─ 布尔值 → TINYINT（0/1）
  └─ JSON → VARCHAR（保存原始 JSON）
```

### 3. 字符编码处理

```
统一编码标准：
  ├─ 检测源系统编码
  ├─ 转换为 UTF-8
  ├─ 处理乱码和特殊字符
  └─ 记录转换过程
```

### 4. 重复数据去重

```
处理重复数据：
  ├─ 完全重复：DELETE（保留一条）
  ├─ 部分重复：更新时间戳，保留最新
  ├─ 逻辑重复：根据业务规则判断
  └─ 记录所有去重操作
```

## ODS 层的增量更新策略

### 策略 1：基于时间戳的增量

```
原理：
  └─ 获取上次更新时间
  └─ 查询源系统中 updated_time > 上次更新时间的数据
  └─ 加载到 ODS

优势：
  ├─ 高效（只加载新增和变化的数据）
  ├─ 适合大多数场景
  └─ 源系统必须有 updated_time 字段

劣势：
  └─ 如果时钟不同步会有问题
```

### 策略 2：基于序列号的增量

```
原理：
  └─ 为每条记录分配递增的序列号
  └─ 记录上次加载的最大序列号
  └─ 加载大于该序列号的所有数据

优势：
  ├─ 不依赖时间戳
  ├─ 可靠性高
  └─ 支持并发处理

劣势：
  └─ 需要源系统支持序列号机制
```

### 策略 3：基于变更数据捕捉（CDC）

```
原理：
  └─ 使用 CDC 工具（如 Debezium）捕捉源系统的变更
  └─ 实时推送变更事件到 ODS

优势：
  ├─ 近实时同步
  ├─ 捕捉所有变更（INSERT/UPDATE/DELETE）
  ├─ 支持事务一致性
  └─ 不影响源系统性能

劣势：
  ├─ 需要额外的 CDC 工具和基础设施
  ├─ 学习曲线陡峭
  └─ 初期投入较大
```

## ODS 层的质量监控

### 监控指标

```
1. 数据完整性指标
   ├─ 每日加载的行数
   ├─ 加载成功率
   ├─ 缺失数据百分比
   └─ 与源系统的行数差异

2. 数据一致性指标
   ├─ 数据校验失败率
   ├─ 异常数据百分比
   ├─ 与源系统的数据差异
   └─ 重复率

3. 性能指标
   ├─ 加载时间
   ├─ 查询响应时间
   ├─ 存储空间使用
   └─ CPU/内存使用率
```

### 告警规则

```
高优先级告警：
  ├─ 加载失败（0% 成功率）
  ├─ 关键字段缺失 > 5%
  ├─ 数据延迟 > 1 小时
  └─ 存储空间不足

中优先级告警：
  ├─ 加载成功率 < 95%
  ├─ 数据延迟 > 30 分钟
  ├─ 异常数据 > 1%
  └─ 加载时间 > 正常时间 2 倍

低优先级告警：
  ├─ 加载时间 > 预期时间
  ├─ 存储空间使用率 > 80%
  └─ 其他性能指标异常
```

## ODS 层的常见问题

### 问题 1：ODS 表过多，难以维护

**原因：** 为每个源系统都创建 ODS 表

**解决方案：**
- 按业务域进行分组（ods_order_*，ods_inventory_*）
- 定期审视 ODS 表的使用情况
- 合并不必要的 ODS 表

### 问题 2：ODS 数据量过大，存储成本高

**原因：** 保留所有历史数据，没有数据生命周期策略

**解决方案：**
```
实施分层存储：
  ├─ 热数据（最近 3 个月）→ SSD
  ├─ 温数据（3-12 个月）→ HDD
  ├─ 冷数据（> 1 年）→ 归档存储
  └─ 定期清理过期数据
```

### 问题 3：ODS 数据质量参差不齐

**原因：** 缺乏统一的数据质量标准和检查机制

**解决方案：**
- 制定数据质量规范
- 在 ODS 层建立自动化的质量检查
- 建立数据质量评分体系
- 定期审计和改进

### 问题 4：无法追踪数据血缘

**原因：** 没有记录数据来源和处理过程

**解决方案：**
- 添加 dw_batch_id，追踪同一批次的数据
- 记录 ETL 流程执行日志
- 建立数据血缘追踪系统
- 定期审计数据血缘

## ODS 层的最佳实践总结

```
1. 表结构设计
   ✅ 保持接近源系统的结构
   ✅ 添加必要的技术列（时间戳、批次 ID 等）
   ✅ 使用一致的命名规范
   ✅ 定义清晰的主键和索引

2. 数据加载
   ✅ 使用分阶段的加载策略（临时表 → 校验 → 合并）
   ✅ 实现增量加载以提升效率
   ✅ 支持错误恢复和回滚
   ✅ 记录加载过程日志

3. 数据质量
   ✅ 在 ODS 层进行第一道数据清洗
   ✅ 建立自动化的质量检查
   ✅ 为异常数据创建隔离表
   ✅ 定期分析数据质量指标

4. 监控告警
   ✅ 监控加载成功率和性能
   ✅ 建立告警规则
   ✅ 及时发现和处理问题
   ✅ 定期分析和改进

5. 文档和沟通
   ✅ 维护 ODS 表的数据字典
   ✅ 记录表的使用情况和依赖关系
   ✅ 与源系统团队保持沟通
   ✅ 定期评估 ODS 层的设计
```
