# 数据建模与设计技能

## 概述

数据建模是将业务需求转化为具体数据结构的过程。好的数据模型能够准确反映业务现实，支持高效的查询和分析。

## 核心概念

### 建模方法

```
概念建模：ER 图
  ├─ 识别实体和属性
  ├─ 定义关系
  ├─ 业务视图

逻辑建模：关系模型
  ├─ 应用范式化
  ├─ 定义约束
  ├─ 技术独立

物理建模：数据库实现
  ├─ 选择数据库类型
  ├─ 优化存储
  ├─ 索引设计
```

### 范式化 vs 反范式化

```
范式化（正规化）：
  优点：数据一致，避免冗余
  缺点：查询需要多表 JOIN，性能差
  适用：OLTP（事务型）系统

反范式化：
  优点：查询快速，数据简单
  缺点：数据冗余，一致性问题
  适用：OLAP（分析型）系统

权衡：
  ├─ 关键数据用范式化
  ├─ 分析数据适度反范式化
  └─ 定期评估和优化
```

## 设计方法

### Step 1：需求分析

```
□ 理解业务流程
  ├─ 核心业务过程
  ├─ 关键实体和属性
  └─ 业务规则和约束

□ 收集数据需求
  ├─ 哪些数据需要存储
  ├─ 数据查询模式
  ├─ 性能需求
  └─ 并发场景

□ 确定数据粒度
  ├─ 最细的数据单位
  ├─ 聚合维度
  └─ 时间粒度
```

### Step 2：概念建模

```
□ 创建 ER 图
  ├─ 列出所有实体
  ├─ 定义属性
  ├─ 标记主键
  └─ 定义关系

□ 业务规则
  ├─ 完整性约束
  ├─ 默认值
  └─ 枚举值
```

### Step 3：逻辑建模

```
□ 应用范式化
  ├─ 第 1 范式：原子性
  ├─ 第 2 范式：完全函数依赖
  └─ 第 3 范式：无传递依赖

□ 定义约束
  ├─ 主键约束
  ├─ 外键约束
  └─ 唯一约束

□ 冗余分析
  ├─ 是否有重复数据
  ├─ 是否可以反范式化以提升性能
  └─ 权衡分析
```

### Step 4：物理建模

```
□ 数据类型选择
  ├─ VARCHAR vs CHAR
  ├─ INT vs BIGINT
  ├─ DECIMAL vs FLOAT
  └─ 日期类型

□ 索引设计
  ├─ 主键索引
  ├─ 外键索引
  ├─ 查询字段索引
  └─ 复合索引

□ 分区和分片
  ├─ 按时间分区
  ├─ 按范围分片
  └─ 哈希分片

□ 存储优化
  ├─ 压缩算法
  ├─ 列式存储（OLAP）
  └─ 行式存储（OLTP）
```

## 维度建模（Data Warehouse）

### 维度表设计

```
维度表特点：
  ├─ 宽表（包含丰富属性）
  ├─ 变化缓慢
  ├─ 规模小
  └─ 支持层级钻取

常见维度：
  ├─ 时间维度（dim_date）
  ├─ 地理维度（dim_location）
  ├─ 产品维度（dim_product）
  ├─ 客户维度（dim_customer）
  └─ 组织维度（dim_organization）
```

### 事实表设计

```
事实表特点：
  ├─ 细粒度
  ├─ 规模大
  ├─ 包含度量值（可聚合的数值）
  └─ 包含维度外键

事实表类型：
  ├─ 事务事实表（每个事务一行）
  ├─ 周期快照事实表（定期状态快照）
  ├─ 累积快照事实表（过程各阶段）
  └─ 无事实事实表（维度关联）
```

## 常见的数据模型模式

### 订单系统

```
dim_customer（客户维度）
  └─ customer_id, name, age, gender, ...

dim_product（产品维度）
  └─ product_id, name, category, price, ...

dim_date（日期维度）
  └─ date_id, date, month, quarter, year, ...

fact_order（订单事实表）
  ├─ order_id, customer_id, product_id, date_id
  ├─ amount, quantity, discount
  ├─ order_status
  └─ created_date, updated_date
```

### 流量分析

```
dim_user（用户维度）
dim_page（页面维度）
dim_device（设备维度）
dim_time（时间维度）

fact_pageview（页面访问事实表）
  ├─ user_id, page_id, device_id, time_id
  ├─ duration, action
  └─ attributes (JSON)
```

## 数据字典

必须创建详细的数据字典

```
模板：

表名：customer
说明：客户信息

列      │ 类型    │ 可空 │ 说明
────────┼─────────┼──────┼──────────
id      │ BIGINT  │ N    │ 主键
name    │ VARCHAR │ N    │ 客户名
email   │ VARCHAR │ Y    │ 邮箱
status  │ ENUM    │ N    │ 状态(ACTIVE/INACTIVE)
created │ DATETIME│ N    │ 创建时间

约束：
  PRIMARY KEY (id)
  UNIQUE (email)
  CHECK (status IN ('ACTIVE', 'INACTIVE'))
```

## 最佳实践

```
1. 从业务需求出发
   ✅ 理解业务规则
   ✅ 与业务人员沟通
   ✅ 验证模型正确性

2. 平衡范式化和性能
   ✅ 关键数据范式化
   ✅ 适度反范式化以提升性能
   ✅ 定期评估

3. 设计清晰的主键
   ✅ 选择合适的主键类型
   ✅ 避免复合主键过复杂
   ✅ 保持数据的唯一性

4. 完整的约束定义
   ✅ 定义所有约束
   ✅ 防止数据异常
   ✅ 保证数据完整性

5. 详细的文档
   ✅ 创建数据字典
   ✅ 记录设计决策
   ✅ 保留评审记录
```

## 评估数据模型

```
检查清单：

□ 完整性
  ├─ 是否包含所有必需的数据？
  ├─ 是否遗漏了关键属性？
  └─ 是否正确反映了业务需求？

□ 一致性
  ├─ 是否避免了数据冗余？
  ├─ 是否满足范式化要求？
  └─ 是否有数据异常？

□ 性能
  ├─ 查询性能是否满足需求？
  ├─ 索引设计是否合理？
  └─ 是否需要反范式化？

□ 可维护性
  ├─ 模型是否易于理解？
  ├─ 文档是否完整？
  ├─ 是否易于扩展？
  └─ 是否有清晰的约束？
```
