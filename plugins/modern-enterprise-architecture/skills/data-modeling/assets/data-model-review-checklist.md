# 数据模型评审检查清单

## 目的

本清单用于在数据模型设计完成后进行全面的评审，确保模型质量。

---

## 第一部分：概念模型评审

### 1.1 实体识别

```
□ 所有关键业务实体都被识别
  ├─ [ ] Customer（客户）
  ├─ [ ] Product（产品）
  ├─ [ ] Order（订单）
  ├─ [ ] ________
  └─ [ ] ________

□ 验证每个实体都代表一个业务对象
  ├─ 不是操作或事件
  ├─ 是相对独立的
  └─ 在整个业务周期内持续存在

□ 没有遗漏关键实体
  └─ 与业务人员确认：这些是所有关键实体吗？
```

### 1.2 属性完整性

```
□ 每个实体的属性都完整

实体：Customer
  ├─ 唯一标识：customer_id ✅
  ├─ 描述性属性：name, email, phone ✅
  ├─ 业务属性：vip_level, lifetime_value ✅
  ├─ 时间属性：created_date, updated_date ✅
  └─ 状态属性：status (active/inactive) ✅

□ 属性不包含重复或相关属性
  └─ 例如：不需要同时有 full_name 和 first_name + last_name

□ 属性命名清晰
  ├─ 避免缩写（如 cust_id → customer_id）
  ├─ 命名一致（如 created_date 和 updated_date）
  └─ 有清晰的业务含义
```

### 1.3 关系定义

```
□ 所有关键关系都被定义

Customer - Order
  ├─ 基数：1 对 N（一个客户可以有多个订单）
  ├─ 强制性：强制（订单必须有客户）
  ├─ 标签：places（客户下单）
  └─ 验证：合理吗？是

Order - Product
  ├─ 基数：N 对 N（通过 OrderItem 实现）
  ├─ 强制性：强制
  ├─ 标签：contains（订单包含产品）
  └─ 验证：合理吗？是

□ 没有多对多关系的歧义
  └─ 所有 N-N 关系都通过中间表（关联实体）实现

□ 关系的强制性和可选性清晰
  ├─ 强制关系：必须存在父记录
  ├─ 可选关系：可以没有父记录
  └─ 已确认：合理吗？
```

### 1.4 业务规则和约束

```
□ 主要业务规则都被表示为约束

规则 1：订单金额不能为负
  └─ 约束：amount >= 0

规则 2：订单状态只能是枚举值
  └─ 约束：status IN ('pending', 'confirmed', 'shipped', 'delivered')

规则 3：一个订单至少要有一个订单项
  └─ 约束：OrderItem.order_id IS NOT NULL

□ 约束的完整性和准确性
  └─ 是否涵盖了所有的业务规则？
```

## 第二部分：逻辑模型评审

### 2.1 范式化分析

```
□ 检查是否满足第一范式（1NF）
  应该：每个字段都是原子性的

  例子：customer_phones 字段存储多个电话号码（✅ 违反 1NF）
  解决：分离为独立的 phone 表或分字段

  ✅ 通过 1NF 检查

□ 检查是否满足第二范式（2NF）
  应该：非主键字段完全依赖于主键

  例子：order_customer_name（客户名称）出现在 order 表中（⚠️ 违反 2NF）
  原因：customer_name 依赖 customer_id，不完全依赖 order_id
  解决：移到 customer 表中，order 表只保留 customer_id

  ✅ 通过 2NF 检查

□ 检查是否满足第三范式（3NF）
  应该：非主键字段之间没有传递依赖

  例子：order 表包含 customer_id 和 customer_city（⚠️ 违反 3NF）
  原因：customer_city 依赖 customer_id，而 customer_id 是外键
  解决：city 应该在 customer 表中

  ✅ 通过 3NF 检查

□ 规范化的总体评估
  ├─ 是否进行了过度规范化？
  ├─ 是否存在必要的反规范化？
  └─ 总体评价：良好 / 需要改进
```

### 2.2 主键和外键设计

```
□ 主键设计

每个表都有清晰的主键：

表名         | 主键类型  | 主键字段
──────────────┼─────────┼──────────────
customer     | 代理键   | customer_id (INT, AUTO_INCREMENT)
product      | 代理键   | product_id (INT)
order        | 代理键   | order_id (BIGINT)
order_item   | 组合键   | (order_id, product_id) 或 代理键

评估：
  ├─ [ ] 所有表都有主键
  ├─ [ ] 主键具有唯一性
  ├─ [ ] 主键不会改变（选择合适的）
  ├─ [ ] 避免使用业务数据作为主键（除非是自然键）
  └─ [ ] 大型表优先使用代理键

□ 外键设计

关键外键关系：

FROM 表    | FK 字段       | TO 表     | PK 字段
─────────────┼──────────────┼───────────┼─────────
order       | customer_id  | customer  | customer_id
order_item  | order_id     | order     | order_id
order_item  | product_id   | product   | product_id

评估：
  ├─ [ ] 外键都指向有效的主键
  ├─ [ ] 外键支持级联删除（如适用）
  ├─ [ ] 没有循环引用
  └─ [ ] 外键约束是否启用？
```

### 2.3 索引策略

```
□ 主键索引
  └─ [ ] 所有主键都自动有索引 ✅

□ 外键索引
  └─ [ ] 所有外键字段都有索引（便于 JOIN）
     ├─ order.customer_id ✅
     ├─ order_item.order_id ✅
     ├─ order_item.product_id ✅

□ 查询字段索引
  需要根据实际查询需求创建

  常见查询：SELECT * FROM order WHERE customer_id=? AND status=?
  索引：
    ├─ idx_customer_id (customer_id)
    ├─ idx_status (status)
    ├─ 复合索引 idx_customer_status (customer_id, status) ⭐ 最优
    └─ 已创建：✅

□ 覆盖索引（如适用）
  └─ 是否有热查询可以通过覆盖索引加速？

□ 索引总体评估
  ├─ 索引数量是否合理？（不要过多，影响写入性能）
  ├─ 是否有未使用的索引？
  └─ 是否遗漏了关键索引？
```

### 2.4 数据类型选择

```
□ 验证数据类型选择的合理性

字段           | 选择的类型 | 评估
────────────────┼──────────┼─────────────────────
customer_id    | BIGINT   | ✅ 合理（支持大数据）
customer_name  | VARCHAR  | ⚠️ 长度？建议 VARCHAR(200)
email          | VARCHAR  | ⚠️ 长度？建议 VARCHAR(100)
amount         | DECIMAL  | ✅ 合理（金融数据）
created_date   | DATETIME | ✅ 合理
is_active      | BOOLEAN  | ✅ 合理（或 TINYINT）

□ 避免以下常见错误
  ❌ VARCHAR 长度太短（导致数据截断）
  ❌ 整数类型不够大（导致溢出）
  ❌ 用 FLOAT 存储金额（精度问题）
  ❌ 用 VARCHAR 存储日期（性能和排序问题）
  ❌ 用 JSON 存储结构化数据（查询困难）
```

## 第三部分：物理设计评审

### 3.1 表名和字段名规范

```
□ 表名规范
  ├─ [ ] 单数形式（customer，不是 customers）
  ├─ [ ] 小写（不用 UPPERCASE）
  ├─ [ ] 避免关键字
  ├─ [ ] 有业务含义
  └─ [ ] 命名一致（ods_customer, fact_order）

□ 字段名规范
  ├─ [ ] 小写且使用下划线分隔
  ├─ [ ] customer_id（不是 CustomerId）
  ├─ [ ] 避免缩写
  ├─ [ ] 时间字段统一（created_date, updated_date）
  └─ [ ] 布尔字段以 is_ 或 has_ 开头
```

### 3.2 约束和校验

```
□ 非空约束
  ├─ customer_id: NOT NULL ✅
  ├─ customer_name: NOT NULL ✅
  ├─ email: NULLABLE（可能没有邮箱）
  └─ 验证：是否正确反映业务要求？

□ 唯一约束
  ├─ email: UNIQUE（防止重复）✅
  ├─ customer_no: UNIQUE（业务号唯一）✅
  └─ 验证：是否遗漏了唯一约束？

□ 检查约束
  ├─ amount >= 0
  ├─ age >= 0 AND age <= 150
  ├─ status IN ('pending', 'confirmed', ...)
  └─ 验证：是否覆盖了所有业务规则？

□ 外键约束
  ├─ [ ] 所有外键都有约束
  ├─ [ ] 级联删除已配置（如适用）
  └─ [ ] 验证：是否遗漏了外键约束？
```

### 3.3 默认值和触发器

```
□ 默认值设置
  ├─ created_date DEFAULT CURRENT_TIMESTAMP ✅
  ├─ is_active DEFAULT 1 ✅
  ├─ status DEFAULT 'pending' ✅
  └─ 验证：所有需要默认值的字段都有吗？

□ 触发器和自动计算
  ├─ updated_date: 自动更新 ✅
  ├─ total_amount: 订单项金额求和
  └─ 验证：是否会导致性能问题或维护困难？
```

## 第四部分：与应用层的兼容性

### 4.1 ORM 映射

```
□ 模型是否易于被 ORM（如 Hibernate、SQLAlchemy）映射
  ├─ [ ] 表名和类名能清晰对应
  ├─ [ ] 字段名能清晰对应
  ├─ [ ] 主外键关系清晰
  └─ [ ] 没有循环引用或复杂的关系
```

### 4.2 查询模式

```
□ 验证常见查询能被有效执行

查询 1：根据客户 ID 查找订单
  SQL: SELECT * FROM order WHERE customer_id = ?
  索引：idx_customer_id ✅

查询 2：查询所有已发货的订单
  SQL: SELECT * FROM order WHERE status = 'shipped'
  索引：idx_status ✅

查询 3：查询某客户在某日期范围的订单
  SQL: SELECT * FROM order
       WHERE customer_id = ?
         AND created_date BETWEEN ? AND ?
  索引：idx_customer_date ✅

□ 是否有不能被有效执行的查询？
  └─ 如有，需要优化模型或添加索引
```

### 4.3 事务支持

```
□ 模型是否支持必要的业务事务

事务 1：转账（涉及两个账户）
  ├─ 关键：必须强一致
  ├─ 约束：用外键保证引用完整性
  └─ 验证：是否有足够的约束？

事务 2：创建订单（涉及多个实体）
  ├─ 关键：订单和订单项原子性
  ├─ 约束：外键级联
  └─ 验证：是否正确配置？
```

## 附录：常见问题和改进建议

```
Q: 表结构是否过于复杂？
  → 考虑分解为更小的表
  → 考虑反规范化以简化查询

Q: 是否会遇到性能瓶颈？
  → 创建必要的索引
  → 考虑分区或分片
  → 使用物化视图

Q: 是否容易扩展？
  → 预留扩展字段
  → 使用版本化的外键
  → 避免硬编码业务逻辑

Q: 是否足够灵活？
  → 考虑 EAV（实体-属性-值）模式
  → 考虑使用 JSON 字段存储灵活数据
  → 但要平衡查询性能
```
