# 部署架构技能

## 概述

部署架构定义了应用如何在生产环境中部署、扩展和维护。一个好的部署架构能够提升系统的可用性、可扩展性和运维效率。

---

## 部署模式

### 模式 1：传统虚拟机部署

```
架构：
  应用 → 虚拟机（每个虚拟机运行整个应用）
        → 负载均衡器
        → 数据库

优点：
  ✅ 简单，易于理解
  ✅ 运维工具成熟
  ✅ 成本可控

缺点：
  ❌ 资源利用率低（虚拟机间隔离）
  ❌ 扩展缓慢（需要启动新虚拟机）
  ❌ 部署和更新较慢
```

### 模式 2：容器化部署（Docker）

```
架构：
  应用 → 容器（轻量级隔离）
       → 容器编排（Docker Compose）
       → 数据库

优点：
  ✅ 资源利用率高
  ✅ 部署快速（秒级）
  ✅ 环境一致性好
  ✅ 易于迭代

缺点：
  ❌ 需要学习容器技术
  ❌ 网络管理复杂
  ❌ 存储管理困难
```

### 模式 3：Kubernetes 编排

```
架构：
  应用 → 容器
       → Kubernetes 集群（Pod、Service、Deployment）
       → 数据库（可选 StatefulSet）

优点：
  ✅ 自动扩展和故障转移
  ✅ 声明式部署
  ✅ 灵活的网络和存储
  ✅ 多云和混合云部署

缺点：
  ❌ 学习曲线陡峭
  ❌ 运维复杂性增加
  ❌ 小团队可能过度工程
```

### 模式 4：Serverless 部署

```
架构：
  用户请求 → API Gateway → Lambda 函数 → 数据库

优点：
  ✅ 自动扩展
  ✅ 按使用付费
  ✅ 无需管理基础设施
  ✅ 快速迭代

缺点：
  ❌ 冷启动延迟
  ❌ 受供应商限制
  ❌ 调试困难
  ❌ 成本可能高（高流量场景）
```

## 高可用部署

### 多可用区部署

```
架构：
  用户
    ├─ 地域 1
    │  ├─ 可用区 1A：应用 + 数据库
    │  └─ 可用区 1B：应用 + 数据库
    │
    └─ 地域 2
       ├─ 可用区 2A：应用 + 数据库
       └─ 可用区 2B：应用 + 数据库

优点：
  ✅ 单个可用区故障时可用
  ✅ 可处理数据中心级故障

缺点：
  ❌ 数据一致性难度增加
  ❌ 延迟增加
  ❌ 成本翻倍
```

### 主备部署

```
架构：
  用户 → 负载均衡 → 主服务器（处理所有读写）
                    └─ 异步复制到 → 备服务器

故障处理：
  ├─ 主故障 → 备自动升为主 → 继续服务
  └─ 备故障 → 自动修复或替换

RTO：< 1 分钟
RPO：可能丢失部分数据（取决于复制延迟）
```

### 多活部署

```
架构：
  用户 → 负载均衡
        ├─ 区域 1：应用 + 数据库（实时同步）
        └─ 区域 2：应用 + 数据库（实时同步）

优点：
  ✅ 完全消除单点故障
  ✅ 可处理整个区域故障

缺点：
  ❌ 数据一致性困难
  ❌ 冲突解决复杂
  ❌ 运维复杂度最高
```

## 灰度发布

### 金丝雀发布（Canary Release）

```
步骤：
  Step 1：向 1% 的用户发布新版本
         观察错误率、延迟等指标

  Step 2：如果指标正常，扩大到 5% 的用户

  Step 3：继续扩大到 25%、50%、100%

  Step 4：全量覆盖，完成发布

优点：
  ✅ 风险最小（只有少量用户受影响）
  ✅ 可快速回滚

缺点：
  ❌ 需要完善的监控
  ❌ 需要支持多个版本共存
```

### 蓝绿发布（Blue-Green Deployment）

```
步骤：
  初始状态：Blue（旧版本，处理所有流量）

  Step 1：在 Green（新环境）部署新版本

  Step 2：运行测试和验证

  Step 3：切换负载均衡器，流量转向 Green

  Step 4：监控新版本，如有问题立即切回 Blue

  Step 5：确认无误后，关闭 Blue 环境

优点：
  ✅ 零停机时间
  ✅ 快速回滚（只需切换负载均衡）

缺点：
  ❌ 需要 2 倍的资源
  ❌ 数据同步复杂
```

## CI/CD 流程

### 流程图

```
开发者推送代码
    ↓
自动构建（编译、单元测试）
    ↓
自动测试（集成测试、E2E 测试）
    ↓
代码审查
    ↓
自动部署到 Staging（测试环境）
    ↓
手动测试和验证
    ↓
手动触发生产部署
    ↓
灰度发布（金丝雀或蓝绿）
    ↓
监控和验证
    ↓
完成
```

### 工具链

```
版本控制：Git
  └─ GitHub、GitLab、Gitea

CI 工具：自动构建和测试
  └─ GitHub Actions、GitLab CI、Jenkins、CircleCI

制品库：存储构建产物
  └─ Docker Registry、Artifactory、Nexus

部署工具：自动部署
  └─ Terraform、Ansible、CloudFormation

监控：观察部署效果
  └─ Prometheus、Grafana、DataDog
```

## 容灾和恢复

### RTO 和 RPO

```
RTO（Recovery Time Objective）：恢复时间目标
  ├─ 定义：从故障发生到系统恢复的最长时间
  ├─ 示例：RTO = 1 分钟（故障后 1 分钟内恢复）
  └─ 成本：RTO 越短，成本越高

RPO（Recovery Point Objective）：恢复点目标
  ├─ 定义：可以接受的最大数据丢失量
  ├─ 示例：RPO = 1 小时（可以接受丢失 1 小时的数据）
  └─ 与备份频率相关：更频繁的备份 → 更小的 RPO → 更高的成本
```

### 备份策略

```
完全备份（Full Backup）：
  ├─ 定义：备份所有数据
  ├─ 频率：每周 1 次
  ├─ 时间：长（可能需要数小时）
  └─ 恢复时间：最快

增量备份（Incremental Backup）：
  ├─ 定义：只备份上次备份后变化的数据
  ├─ 频率：每天 1 次或更频繁
  ├─ 时间：短
  └─ 恢复时间：需要完全备份 + 多个增量备份

差异备份（Differential Backup）：
  ├─ 定义：备份上次完全备份后所有变化的数据
  ├─ 频率：每周多次
  ├─ 时间：中等
  └─ 恢复时间：完全备份 + 1 个差异备份
```

### 灾备计划

```
RPO/RTO 目标
  ├─ 关键系统（支付）：RTO = 分钟级，RPO = 秒级
  ├─ 重要系统（订单）：RTO = 小时级，RPO = 分钟级
  └─ 普通系统（日志）：RTO = 天级，RPO = 小时级

备份存储位置
  ├─ 本地备份：快速恢复
  ├─ 异地备份：防止数据中心故障
  ├─ 云备份：便宜且可靠
  └─ 多副本备份：提升可靠性

恢复步骤
  ├─ 故障检测（自动或手动）
  ├─ 启动恢复流程
  ├─ 从备份恢复（选择合适的备份点）
  ├─ 验证数据完整性
  └─ 恢复应用和服务

定期演练
  ├─ 每个季度进行一次灾备演练
  ├─ 验证备份的可用性
  ├─ 评估恢复时间
  └─ 发现和修复问题
```

## 部署架构决策框架

```
Q1：应用的规模和增长潜力？
  → 小型应用：虚拟机 + Docker 足够
  → 中大型应用：Kubernetes
  → 超大规模：Kubernetes + 多地域

Q2：可用性要求？
  → 99.9%：单点 + 自动恢复足够
  → 99.99%：多可用区 + 主备
  → 99.999%：多活部署

Q3：成本预算？
  → 紧张：虚拟机部署
  → 中等：容器化 + 小规模 K8s
  → 充足：完整的 K8s + 多地域

Q4：团队能力和规模？
  → 小团队（< 10 人）：简单部署
  → 中等团队（10-50 人）：Kubernetes + CI/CD
  → 大团队（> 50 人）：完整的 DevOps 体系

Q5：运维复杂度的容忍度？
  → 低：选择托管服务（云厂商处理运维）
  → 中：自建 + 自动化工具
  → 高：完整自建，接受运维复杂度
```
