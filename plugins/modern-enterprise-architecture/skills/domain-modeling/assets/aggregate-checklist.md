# 聚合设计检查清单

## 聚合边界检查

### 聚合 1: [聚合名]

#### 基础检查
- [ ] 聚合有明确的根实体吗？
- [ ] 聚合的名字清晰表达了它的职责吗？
- [ ] 聚合包含的对象都是必须强一致性的吗？
- [ ] 聚合与其他聚合的关系是通过 ID 引用吗？

#### 一致性检查
- [ ] 聚合的所有不变性规则都在聚合代码中强制吗？
- [ ] 聚合的大小合理吗？（不太大，不太小）
- [ ] 是否有对象应该分离到另一个聚合？
- [ ] 是否有对象被其他聚合直接引用？（应该改为 ID）

#### 命令和事件检查
- [ ] 聚合根的所有命令都已定义吗？
- [ ] 聚合产生的所有事件都已定义吗？
- [ ] 命令的输入参数完整吗？
- [ ] 事件的数据足以被其他聚合响应吗？

#### 实体 vs 值对象检查
- [ ] 聚合中每个对象的类型（实体或值对象）都正确吗？
- [ ] 所有值对象都是不可变的吗？
- [ ] 实体都有身份 ID 吗？
- [ ] 没有冗余的实体定义吗？

#### 状态转换检查（如果适用）
- [ ] 所有合法的状态转换都已定义吗？
- [ ] 非法的状态转换会被拒绝吗？
- [ ] 状态机图是否清晰？

## 完整的领域模型审查清单

### 第 1 部分：聚合识别

- [ ] 从 Event Storming 中识别出的所有聚合都已建模？
- [ ] 是否漏掉了什么聚合？
- [ ] 聚合的粒度合适吗（不太粗，不太细）？
- [ ] 聚合的边界清晰吗？

### 第 2 部分：不变性规则

对每个聚合：
- [ ] 列出了所有的核心不变性规则？
- [ ] 规则在代码中被强制吗？
- [ ] 规则是否冗余或矛盾？
- [ ] 规则的优先级是否明确？

### 第 3 部分：命令设计

- [ ] 每个聚合都有合适的命令吗？
- [ ] 命令的名字用祈使式吗？
- [ ] 命令的参数完整且最小化吗？
- [ ] 命令返回值是否恰当？
- [ ] 命令是否会产生事件？

### 第 4 部分：事件设计

- [ ] 事件用过去式命名吗？
- [ ] 事件包含了足够的数据供订阅者使用吗？
- [ ] 事件有时间戳吗？
- [ ] 事件有版本吗？（便于升级）
- [ ] 事件是否包含了重要的业务数据（不仅是 ID）？

### 第 5 部分：聚合间关系

- [ ] 聚合间都是通过 ID 引用，而非直接对象引用？
- [ ] 跨聚合的操作都通过事件驱动吗？
- [ ] 是否有不必要的聚合依赖？
- [ ] 是否有循环依赖？

### 第 6 部分：存储一致性

- [ ] 每个聚合都有明确的存储库（Repository）吗？
- [ ] 聚合的加载和保存逻辑是原子的吗？
- [ ] 是否考虑了并发修改（乐观锁、版本号）？
- [ ] 事件的持久化和聚合的持久化是原子的吗？

### 第 7 部分：业务规则验证

- [ ] 是否遗漏了任何业务规则？
- [ ] 规则是否在正确的层级（聚合而非应用层）？
- [ ] 是否有规则冗余检查（同样的规则多次验证）？
- [ ] 错误消息是否清晰且有业务含义？

## 常见问题排查

**问题**：聚合太大，加载时间长
```
症状：每次加载 Order 都要加载 100+ OrderLines
解决：考虑懒加载或分离 OrderLines
```

**问题**：两个聚合之间频繁通信
```
症状：Order.confirm() 需要调用 Payment.create()
解决：用事件驱动，Order 产生 OrderConfirmedEvent，Payment 异步监听
```

**问题**：聚合间有循环依赖
```
症状：Order 引用 Payment，Payment 引用 Order
解决：明确依赖方向，或两个都通过 ID 引用，用事件通信
```

**问题**：不变性规则无法强制
```
症状：amount 设置为 -100（不应该），但代码允许
解决：在构造函数和修改方法中添加验证，使用值对象
```

## 改进建议

如果审查发现问题，按优先级修复：

| 优先级 | 问题类型 | 修复方式 |
|--------|---------|---------|
| 🔴 高 | 聚合边界不清 | 重新划分聚合 |
| 🔴 高 | 不变性规则无法强制 | 将规则移到聚合 |
| 🟡 中 | 聚合太大 | 拆分为多个聚合 |
| 🟡 中 | 聚合间循环依赖 | 调整依赖方向 |
| 🟢 低 | 命名不清 | 重命名 |
| 🟢 低 | 事件数据不完整 | 补充事件字段 |
