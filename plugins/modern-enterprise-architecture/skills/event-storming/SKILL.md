# Event Storming

Event Storming 是一种快速、可视化的业务流程建模方法，由 Alberto Brandolini 创立。它通过让所有利益相关者围绕一块大白板，用便签纸标记核心的**业务事件**，在 3-4 小时内完成复杂的域建模。

**核心价值**：
- ⚡ 快速：3-4 小时完成，而不是数周的需求分析
- 🎯 准确：所有参与者在同一个房间，实时沟通，避免误解
- 📊 可视：产生可用于后续设计的可视化产物
- 🤝 协作：打破部门墙，建立共同语言

## When to Use This Skill

- 🆕 **新项目启动**：快速理解业务需求和流程
- 🔍 **业务分析**：在需求分析前期明确业务逻辑
- 🏗️ **架构设计**：为应用架构提供输入（识别聚合、界定应用边界）
- 🔄 **流程优化**：识别业务流程中的瓶颈和可变点
- 📱 **新业务线**：拓展到新的业务领域时，快速梳理

## Core Concepts

### 1. 业务事件（Domain Event）
**定义**：在业务中发生的、有业务意义的事件。通常用**过去式**命名。

**例子**：
- "账户已开设" （不是 "开设账户"）
- "订单已下单"
- "支付已完成"
- "发货已确认"

**为什么用过去式？**
- 事件是已发生的事实，不是意图
- 强调 CQRS 中的命令→事件的流向

### 2. 命令（Command）
**定义**：用户或系统做出的意图、指令。

**例子**：
- "开设账户" → "账户已开设"
- "下单" → "订单已下单"
- "确认支付" → "支付已完成"

**关键点**：命令可能失败，事件一旦发生就不会改变。

### 3. 聚合（Aggregate）
**定义**：处理命令、产生事件的业务对象，也是数据一致性的边界。

**例子**：
- "订单" 聚合：处理 "下单" 命令，产生 "订单已下单" 事件
- "账户" 聚合：处理 "开设账户" 命令，产生 "账户已开设" 事件

### 4. 外部系统（External System / Actor）
**定义**：与当前域交互的外部参与者。

**例子**：
- 支付网关
- 邮件服务
- 短信服务
- 第三方风控平台

### 5. 策略（Policy）/ 业务规则（Business Rule）
**定义**：在某个事件发生后自动触发的其他行为。

**例子**：
- "账户已开设" → 自动发送欢迎邮件
- "支付已完成" → 自动发送发货指令

## Step-by-Step Guide

### 阶段 1：准备（第 1-2 步）

#### Step 1: 准备工作坊
**时间**：至少 1 周前开始

**关键活动**：
- ✏️ **邀请正确的人**：产品经理、业务分析师、技术架构师、前端/后端开发代表、测试、运维等
- 📍 **选择合适的场地**：大房间、一面大白板或白墙、充足的便签纸和马克笔
- ⏰ **安排时间**：3-4 小时的完整时间块，避免中断
- 📋 **明确目标**：定义本次 Event Storming 的边界（是整个系统还是某个流程？）

**材料清单**：
- 宽幅白板或白墙（推荐 3m x 1.5m）
- 3 种颜色的便签纸（推荐：黄色=事件、蓝色=命令、红色=政策）
- 粗头马克笔（多色）
- 胶带或粉笔
- 参考模板（见 assets）

#### Step 2: 介绍 Event Storming
**时间**：10-15 分钟

**流程**：
1. 解释核心概念（事件、命令、聚合、外部系统）
2. 展示示例（最好是与参与者相关的业务示例）
3. 强调游戏规则：
   - 不评判、不讨论、先贴便签
   - 一个事件一个便签
   - 有疑问的地方标记出来，之后讨论
   - 时间紧张，重点优先

### 阶段 2：建模（第 3-5 步）

#### Step 3: 找出所有事件
**时间**：30-45 分钟

**流程**：
1. 问参与者："在我们的业务中，会发生哪些重要的事件？"
2. 每个参与者把想到的事件写在黄色便签上，按时间顺序贴在白板上
3. 不要评判，快速记录，宽松管理
4. 结果：一条从左到右的事件流

**示例（电商平台）**：
```
商品已浏览 → 商品已添加到购物车 → 购物车已清空 → 订单已下单 →
支付已完成 → 库存已扣除 → 发货已确认 → 包裹已发出 →
包裹已送达 → 订单已评价
```

#### Step 4: 找出触发这些事件的命令
**时间**：30-45 分钟

**流程**：
1. 问参与者："什么样的用户行为或系统操作会触发这些事件？"
2. 在每个事件的左边贴上蓝色便签（命令）
3. 强调：一个命令可能失败，一个事件一定已发生

**示例**：
```
浏览商品 → [商品已浏览] → 添加购物车 → [商品已添加到购物车]
```

#### Step 5: 识别外部系统和策略
**时间**：20-30 分钟

**流程**：
1. 红色便签标记 "策略"（自动触发的行为）
2. 橙色便签标记 "外部系统"
3. 在相应的事件旁边标记

**示例**：
```
[订单已下单] → 红色便签："自动发送订单确认邮件" → 橙色便签：邮件系统
         → 红色便签："自动扣库存" → 库存系统
         → 红色便签："创建支付指令" → 支付网关
```

### 阶段 3：分析（第 6-7 步）

#### Step 6: 识别聚合
**时间**：30-45 分钟

**流程**：
1. 用虚线框圈出相关的事件和命令
2. 问参与者："哪些对象是紧耦合的，必须保持一致？"
3. 给每个框取名，这就是聚合根

**示例**：
```
┌─ 购物车聚合 ─────────────────┐
│ 浏览商品 → [商品已浏览]      │
│ 添加购物车 → [商品已添加]    │
│ 清空购物车 → [购物车已清空]  │
└───────────────────────────────┘

┌─ 订单聚合 ──────────────────────────────────┐
│ 下单 → [订单已下单]                         │
│      → [订单总额已计算]                     │
│      → [订单项已确认]                       │
└──────────────────────────────────────────────┘
```

#### Step 7: 发现问题和可变点
**时间**：20-30 分钟

**关键问题**：
1. ❓ **疑问**：哪些地方不清楚或有争议？（用 "?" 标记）
2. 🔄 **可变点**：哪些流程在不同场景会不同？（如 VIP 用户、促销活动等）
3. 🚫 **限制**：有哪些系统或业务限制影响流程？
4. ⚠️ **异常**：可能的失败场景和补偿操作是什么？

**记录**：
- 为每个问题指定所有者，列出需要进一步讨论的项
- 这些会成为后续深化设计的输入

## Best Practices

1. **邀请对的人**：必须有业务专家、技术代表和用户代表
2. **空出足够时间**：不要赶工，3-4 小时的集中时间能产生 10 倍的效果
3. **从头梳理一遍**：最后用 15 分钟从头走一遍整个流程，确保逻辑连贯
4. **及时记录问题**：用不同的便签颜色标记不确定的地方，等工作坊后讨论
5. **照相或拍视频**：工作坊后可能需要还原，最好记录成照片或短视频
6. **后续立即转化**：在 1 周内将 Event Storming 的结果转化为文档或代码
7. **重复使用**：一旦确定了核心事件流，可用来培训新成员

## Common Pitfalls

- **❌ 过度关注 UI**：Event Storming 是业务流程，不是 UI 流程
  → **✅ 解决**：关注业务操作，而非点击流

- **❌ 陷入细节讨论**：工作坊中容易纠缠某个细节，浪费时间
  → **✅ 解决**：标记为 "?" 问题，工作坊后讨论

- **❌ 忽视外部系统**：没有标记第三方系统的依赖
  → **✅ 解决**：用不同颜色区分内部流程和外部系统

- **❌ 无法识别聚合**：事件映射清楚了，但不知道怎么分聚合
  → **✅ 解决**：问 "这些事件必须保持强一致性吗？" 来判断聚合边界

- **❌ 工作坊结束就完事**：没有后续的文档化和设计
  → **✅ 解决**：工作坊后立即转化为领域模型、流程图、API 设计等

## Key Questions

- 核心业务流程是什么样的？（从第一个操作到最终完成）
- 哪些聚合之间需要保持强一致性？
- 哪些操作可以异步化？
- 失败后的补偿操作是什么？
- 有哪些业务规则（策略）在不同场景下会不同？
