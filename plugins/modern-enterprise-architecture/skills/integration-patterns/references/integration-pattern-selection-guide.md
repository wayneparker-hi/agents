# 集成模式选择和实现指南

本指南帮助您为不同的场景选择合适的集成模式，并提供实现建议。

---

## 集成模式选择决策树

```
您需要集成哪两个应用？

应用间有什么关系？
├─ 一个应用读取另一个应用的数据
│  └─ 需要实时最新数据吗？
│     ├─ 是（< 1 秒）→ 同步调用（HTTP / gRPC）
│     └─ 否（可以延迟）→ 缓存 + 异步更新
│
├─ 一个应用触发另一个应用的操作
│  └─ 需要立即确认吗？
│     ├─ 是 → 同步调用（HTTP / gRPC）
│     │        或者 发送请求后等待响应
│     │
│     └─ 否 → 发布事件 / 发送消息（异步）
│
├─ 两个应用共享数据
│  └─ 有多个应用需要访问吗？
│     ├─ 是 → 发布-订阅（Pub/Sub）
│     └─ 否 → 直接 HTTP 调用或共享库
│
└─ 需要协调多个应用的操作
   └─ 是否所有操作必须要么全成功要么全失败？
      ├─ 是 → Saga 模式（分布式事务补偿）
      └─ 否 → 发布事件，各应用独立处理
```

## 集成模式实现检查清单

### 同步 REST API 调用

```
何时使用：
  ✓ 需要立即获得响应
  ✓ 应用间关系简单
  ✓ 数据量小（< 1MB）
  ✓ 应用数少（< 5）

实现检查清单：
□ API 设计
  ├─ API 遵循 RESTful 原则吗？
  ├─ 是否有清晰的版本管理策略？
  ├─ 错误响应是否定义清晰（HTTP status code）？
  └─ 是否有 API 文档（OpenAPI/Swagger）？

□ 可靠性
  ├─ 是否实现了重试逻辑？
  ├─ 重试次数和退避策略是什么？
  ├─ 超时时间是多少（推荐 5-30 秒）？
  └─ 是否有降级方案（熔断、降级）？

□ 性能
  ├─ API 响应时间是否满足目标？
  ├─ 是否使用了连接池？
  ├─ 是否有缓存策略？
  └─ 是否会有 N+1 调用问题？

□ 安全
  ├─ 是否使用 HTTPS？
  ├─ 是否有身份验证（API Key / JWT）？
  ├─ 是否有速率限制？
  └─ 是否记录了调用日志？

□ 运维
  ├─ 是否有监控（成功率、响应时间）？
  ├─ 是否有告警？
  ├─ 故障排查是否有指南？
  └─ 是否有降级脚本？
```

### 异步事件驱动集成

```
何时使用：
  ✓ 可以接受延迟（分钟级）
  ✓ 一个事件可能有多个订阅者
  ✓ 应用间耦合度要求低
  ✓ 应用数多（> 5）

实现检查清单：
□ 事件设计
  ├─ 事件名称是否明确（如 OrderCreated）？
  ├─ 事件数据是否自包含（不依赖其他信息）？
  ├─ 是否有事件版本控制？
  ├─ 是否有事件 schema 定义？
  └─ 是否有事件总线或消息队列选择？

□ 可靠性
  ├─ 事件是否会丢失（持久化）？
  ├─ 是否支持至少一次投递？
  ├─ 如何处理重复事件（幂等性）？
  ├─ 是否有死信队列处理失败消息？
  └─ 是否有事件重放机制？

□ 顺序性
  ├─ 是否需要保证事件顺序？
  ├─ 如果需要，是否使用分片/分区？
  └─ 是否记录了事件时间戳？

□ 监控
  ├─ 是否监控事件发布时间？
  ├─ 是否监控订阅者处理时间？
  ├─ 是否监控消息队列深度？
  └─ 是否有告警（消息堆积、处理延迟）？

□ 工具选择
  ├─ 使用 Kafka / RabbitMQ / Pub-Sub？
  ├─ 是否满足吞吐量需求？
  ├─ 是否满足延迟需求？
  └─ 是否有运维团队经验？
```

### API 网关集成

```
何时使用：
  ✓ 多个应用需要统一的入口
  ✓ 需要统一的认证/授权
  ✓ 需要统一的限流和监控
  ✓ 需要 API 版本管理

实现检查清单：
□ 网关功能
  ├─ 是否实现了路由？
  ├─ 是否实现了认证（OAuth2 / JWT）？
  ├─ 是否实现了授权？
  ├─ 是否实现了限流？
  ├─ 是否实现了日志?
  └─ 是否实现了 API 聚合？

□ 性能
  ├─ 网关是否成为瓶颈？
  ├─ 响应时间是否满足目标？
  ├─ 是否使用了缓存？
  └─ 是否支持水平扩展？

□ 可用性
  ├─ 网关是否有高可用部署？
  ├─ 网关故障是否影响所有应用？
  ├─ 是否有快速故障转移？
  └─ 是否有备用网关？

□ 安全
  ├─ 是否验证了所有请求？
  ├─ 是否防护了常见攻击（SQL 注入、XSS）？
  ├─ 是否实现了速率限制？
  └─ 是否记录了安全事件？

□ 工具选择
  ├─ 使用 Kong / NGINX / AWS API Gateway？
  ├─ 是否支持需要的协议？
  ├─ 运维团队是否有经验？
  └─ 成本是否可接受？
```

## 常见集成问题和解决方案

### 问题 1：处理应用故障

```
场景：A 应用调用 B 应用的 API，B 应用变慢或故障

解决方案：

1. 重试
   └─ 临时故障可能会恢复
   └─ 策略：指数退避（1s, 2s, 4s, 8s）
   └─ 风险：如果 B 应用真的故障了，重试浪费时间

2. 超时
   └─ 不要无限期等待
   └─ 设置合理的超时（5-30 秒）
   └─ 超时后立即返回错误，尝试降级

3. 断路器
   └─ 如果连续多次失败，打开断路器
   └─ 之后的请求立即返回错误，不再尝试
   └─ 定期检查是否恢复，半开状态
   └─ 恢复后关闭断路器

4. 降级
   └─ 无法调用真实服务时，返回缓存或默认值
   └─ 例：推荐服务故障时，显示热门商品

5. 熔断
   └─ 与断路器类似，但更激进
   └─ 一旦检测到故障，立即熔断
   └─ 避免级联故障
```

### 问题 2：保证数据一致性

```
场景：订单创建需要同时更新库存、支付、通知三个系统

解决方案：

1. 分布式事务（成本高，不推荐）
   └─ 使用两阶段提交（Prepare + Commit）
   └─ 性能差，可扩展性差
   └─ 网络分区时容易失败

2. Saga 模式（推荐）
   └─ 订单创建（本地事务）
   └─ 异步调用库存预留
   └─ 如果失败，补偿订单删除
   └─ 异步调用支付
   └─ 如果失败，补偿库存释放和订单删除
   └─ 异步发送通知
   └─ 最终每个应用的本地数据是一致的

3. 事件溯源
   └─ 记录所有事件
   └─ 从事件重放可以恢复状态
   └─ 支持审计和调试

4. 最终一致性
   └─ 接受暂时的不一致
   └─ 定期数据对账，发现不一致自动修复
   └─ 适合非关键数据
```

## 集成成本对比

```
集成方式      │ 开发成本 │ 运维成本 │ 性能 │ 可靠性 │ 扩展性
──────────────┼─────────┼─────────┼──────┼────────┼────────
REST API      │ 低      │ 低      │ 高   │ 中     │ 中
gRPC          │ 中      │ 中      │ 极高 │ 中     │ 高
事件驱动      │ 高      │ 高      │ 中   │ 高     │ 高
API 网关      │ 中      │ 中      │ 中   │ 高     │ 高
服务网格      │ 极高    │ 极高    │ 中   │ 高     │ 极高

推荐选择：
  初期：REST API（简单快速）
  增长期：REST + 事件驱动（分离读写）
  成熟期：混合方案（每个应用用最合适的方式）
  大规模：可考虑服务网格（需要专业团队）
```

## 集成安全清单

```
□ 身份验证
  ├─ 使用 API Key 还是 OAuth2 / JWT？
  ├─ Token 是否定期更新？
  └─ 失败的认证是否被拒绝？

□ 授权
  ├─ 是否验证了调用者有权限？
  ├─ 是否限制了每个应用的权限？
  └─ 是否记录了访问控制决策？

□ 通信安全
  ├─ 是否使用 HTTPS / TLS？
  ├─ 是否验证了服务器证书？
  └─ 是否使用了足够强的加密？

□ 数据保护
  ├─ 是否在传输中加密敏感数据？
  ├─ 是否在存储中加密敏感数据？
  └─ 是否有密钥管理机制？

□ 审计
  ├─ 是否记录了所有 API 调用？
  ├─ 是否记录了认证/授权决策？
  ├─ 日志保留时间是多久？
  └─ 是否定期审计日志？
```

## 总结：选择指南

```
应用数少（< 5）：
  → REST API 同步调用
  → 简单快速，够用

应用数中等（5-20）：
  → REST API + 事件驱动的混合
  → 关键路径同步，其他异步
  → 加上 API 网关做统一管理

应用数多（> 20）：
  → 以事件驱动为主，必要时同步
  → 必须有 API 网关
  → 考虑服务网格来统一管理

关键原则：
  ✅ 从简单开始，随着规模演进
  ✅ 同步用于关键路径，异步用于非关键
  ✅ 尽可能解耦，最小化跨应用依赖
  ✅ 做好监控和降级，为故障做准备
```
