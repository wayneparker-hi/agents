# Process Modeling

基于 Event Storming 识别的事件序列，进一步分析**业务流程**的结构、变化和扩展点。关键目标是找出**通用的流程骨架**和**可变的部分**。

## When to Use This Skill

- 📊 **流程设计**：系统化地描述复杂的业务流程
- 🔄 **流程优化**：识别流程中的浪费、瓶颈、可并行化的部分
- 🎯 **应用分解**：流程模型直接指导应用的责任划分
- 📱 **配置化系统**：识别可配置的变化点，设计灵活的系统
- 🧪 **测试**：清晰的流程模型便于测试场景设计

## Core Concepts

### 1. 核心流程（Happy Path）
**定义**：最常见的、理想场景下的业务流程。

**特征**：
- 没有异常、延迟、等待
- 代表主要的业务价值实现
- 应该被优化和加速

**例子**：
```
订单核心流程：
下单 → 支付 → 库存扣除 → 发货 → 送达 → 确认收货
```

### 2. 可变点（Variation Point）
**定义**：同一个业务流程，在不同的条件下会有不同的处理方式。

**例子**：
- 订单金额大于 1000 元需要审批，小于则直接进行
- VIP 用户免除运费，普通用户需要计算
- 国内订单和国际订单的发货流程不同

**为什么重要？**
- 帮助你设计灵活的系统
- 指导配置和参数化设计
- 避免过度工程化

### 3. 异常处理（Exception Handling）
**定义**：流程中可能出现的异常和补偿操作。

**例子**：
- 支付失败 → 重试 3 次 → 如果还是失败，取消订单
- 库存不足 → 通知用户 → 等待补货 / 推荐替代品
- 发货延迟 → 自动补偿 / 主动通知客户

### 4. 扩展点（Extension Point）
**定义**：流程中预留的、便于添加新功能的插入点。

**例子**：
```
订单创建事件 → [扩展点1] → 支付 → [扩展点2] → 发货

扩展点1 可以插入：
- 风控检查
- 欺诈检测
- 积分计算

扩展点2 可以插入：
- 仓库选择逻辑
- 物流商选择
- 发票生成
```

## Step-by-Step Guide

### Step 1: 梳理核心流程
从 Event Storming 识别的事件序列出发，去掉条件分支，描述最常见的业务流程。

**模板**：
```
流程：订单处理
核心步骤：
1. 用户下单
2. 系统验证库存
3. 用户支付
4. 系统确认支付
5. 系统扣库存
6. 仓库发货
7. 物流送达
8. 用户确认收货
```

### Step 2: 识别决策点和条件分支
在核心流程的基础上，加入条件分支。

**模板**：
```
1. 用户下单
2. 系统验证库存
   - 库存充足 → 继续
   - 库存不足 → 异常处理
3. 检查订单金额
   - > 1000 元 → 需要审批
   - ≤ 1000 元 → 继续
4. 用户支付
   ...
```

### Step 3: 标记可变点
对可能在不同场景下有不同处理的地方标记。

**示例**：
```
- 订单金额检查（阈值可配置）
- 支付方式（支付宝、微信、银行卡）
- 发货仓库选择（最近仓库、库存充足、运费最低等策略）
- 发票处理（是否需要、什么类型）
```

### Step 4: 设计扩展点
预留 3-5 个关键的扩展点，支持未来添加新功能。

**6 种常见扩展点模式**：

#### 模式 1：前置检查（Pre-Condition Check）
在操作前添加检查逻辑。

```
用户下单 → [检查：风控] → [检查：积分足不足] → 继续
```

**何时用**：需要在处理前验证条件

#### 模式 2：后置处理（Post-Operation Handler）
操作完成后触发其他操作。

```
支付完成 → [发送邮件通知] → [更新用户积分] → [触发营销活动]
```

**何时用**：需要在操作后触发多个事件

#### 模式 3：策略选择（Strategy Selection）
在多种策略中选择。

```
准备发货 → [选择仓库策略：最近/最便宜/库存最多] → 执行
```

**何时用**：同一个操作有多种实现方式

#### 模式 4：条件路由（Conditional Routing）
根据条件分配到不同的处理流程。

```
订单处理
├─ VIP 用户 → 快速通道（跳过审批）
├─ 普通用户 → 标准通道（需要审批）
└─ 新用户 → 风控通道（严格审批）
```

**何时用**：基于对象的属性有不同的处理

#### 模式 5：并行处理（Parallel Processing）
多个操作可以并行执行。

```
订单支付完成
├─ 扣库存
├─ 发邮件通知
├─ 更新积分
└─ 触发推荐系统
```

**何时用**：多个操作相互独立

#### 模式 6：补偿机制（Compensation）
失败时的反向操作。

```
扣库存 → [成功] → 生成订单
    ↓
  [失败] → 返还预占库存 → 通知用户
```

**何时用**：操作可能失败，需要回滚

### Step 5: 设计异常处理
对每个关键步骤定义失败场景和处理方式。

**模板**：
```
步骤：用户支付
成功场景：返回支付成功
失败场景 1：网络超时
  → 重试 3 次
  → 如果还是失败，标记为"待支付"，定时轮询

失败场景 2：余额不足
  → 提示用户
  → 引导充值或选择其他支付方式

失败场景 3：卡被冻结
  → 提示用户联系银行
  → 推荐其他支付方式
```

### Step 6: 输出流程设计文档
将上述分析整理成可视化和文字描述。

**输出物**：
- 流程图（包含决策点、扩展点）
- 流程描述（每个步骤、条件、异常）
- 可变点清单（哪些点可配置）
- 扩展点设计（预留的插入点）

## Best Practices

1. **从核心流程开始**：先搞清楚主流程，再考虑分支
2. **限制扩展点数量**：3-5 个最佳，太多会很复杂
3. **异常不是特例**：异常处理和补偿和常规流程一样重要
4. **并行优先**：能并行就并行，这样系统反应更快
5. **测试覆盖**：流程模型要覆盖核心路径和所有异常场景

## Common Pitfalls

- **❌ 流程太细**：包含了太多的小步骤，难以理解
  → **✅ 解决**：保持在 5-15 个核心步骤

- **❌ 忽视异常**：只设计了理想情况
  → **✅ 解决**：为每个步骤定义至少一个异常场景

- **❌ 过度扩展点**：预留太多扩展点，导致系统复杂
  → **✅ 解决**：只预留真正预期会变化的地方

- **❌ 串行设计**：所有步骤都是等待前一个完成
  → **✅ 解决**：识别可并行的操作

## Key Questions

- 核心的业务流程是什么？
- 哪些步骤经常会变化？
- 可能出现的异常有哪些？
- 哪些操作可以并行？
- 预留哪些扩展点支持未来的功能？
