## 实际例子：订单处理流程

### 流程基本信息

```
流程名称：订单处理全流程
业务域：订单管理
所有者：订单团队负责人
最后更新：2024-11-10
版本：v2.1
```

### 流程概述

```
目标：
  将客户订单从创建到完成，确保准确、及时、安全地交付

输入：
  - 订单信息（客户、商品、数量、地址）
  - 支付凭证
  - 配送地址

输出：
  - 发货单
  - 跟踪信息
  - 收据/发票

主要参与者：
  - 系统（库存查询、订单持久化）
  - 风控团队（异常审核）
  - 仓库（出库）
  - 物流（配送）
  - 客户（查询、退货）

平均执行时间：3-7 天（从下单到收货）
成功标准：商品完整发货且客户确认收货
```

### 核心路径（Happy Path）

```
Step 1: 订单创建
  输入：订单信息（CustomerId, Items, Address）
  操作：
    1. 构建 Order 对象
    2. 验证基本信息（客户、商品存在性）
    3. 计算订单金额
    4. 持久化到数据库
  输出：OrderId, 订单状态 = NEW
  责任人：订单系统（自动）
  成功条件：订单在数据库中存在，ID 已分配

Step 2: [扩展点] 风险检查
  输入：Order
  操作：
    1. 黑名单检查
    2. 异常金额检查
    3. 风险地址检查
  输出：检查通过 or 标记为待审核
  责任人：风控系统（自动）+ 人工审核
  成功条件：通过所有检查 or 人工确认可继续

Step 3: 支付处理
  输入：Order, PaymentInfo
  操作：
    1. 调用支付网关
    2. 扣款
    3. 记录交易 ID
  输出：PaymentId, 支付状态 = COMPLETED
  责任人：支付系统（自动）
  成功条件：支付成功，金额与订单匹配

Step 4: 库存预留
  输入：Order
  操作：
    1. 检查库存
    2. 锁定库存
    3. 生成库存单
  输出：InventoryLock, 可用库存确认
  责任人：库存系统（自动）
  成功条件：库存足够且已锁定

Step 5: [扩展点] 发货方式确定
  输入：Order Items, Customer Region
  操作：路由到不同的发货流程
  输出：选定的发货流程
  责任人：系统（自动）
  成功条件：发货方式已确定

Step 6a: [条件分支] 实物商品 - 仓库出库
  输入：Order, InventoryLock
  操作：
    1. 通知仓库出库
    2. 扫描商品
    3. 生成发货单
  输出：ShipmentId, 状态 = PICKED
  责任人：仓库（人工扫描）+ 系统

Step 6b: [条件分支] 虚拟商品 - 自动发送
  输入：Order, VirtualGood
  操作：
    1. 生成兑换码或下载链接
    2. 发送给客户（邮件/短信）
    3. 记录发送日志
  输出：DeliveryRecord, 状态 = DELIVERED
  责任人：系统（自动）

Step 7: [扩展点] 发货后处理（并行）
  输入：Shipment
  操作（并行执行）：
    - 发送发货通知邮件
    - 更新积分
    - 申请发票
    - 更新用户统计
  输出：处理完成标志
  责任人：多个系统（异步）

Step 8: 订单完成标记
  输入：所有步骤完成
  操作：
    1. 标记订单为 COMPLETED
    2. 释放库存锁
    3. 生成完成报告
  输出：Order, 状态 = COMPLETED
  责任人：系统（自动）
  成功条件：订单状态已更新，库存已释放
```

### 可变点定义

```
可变点 1：风险检查策略
  所在步骤：Step 2
  变化维度：订单风险等级 + 用户信誉等级
  选项：
    - 自动通过：低风险 + 高信誉 → 直接通过
    - 快速审核：中风险 → 24 小时人工审核
    - 严格审核：高风险 → 电话或视频核实
    - 拒绝：黑名单或明显欺诈 → 直接拒绝
  配置参数：
    - riskLevel_Threshold: 0.3
    - reputationLevel_Good: >= 4
    - approvalTimeout: 24h

可变点 2：发货方式
  所在步骤：Step 5
  变化维度：商品类型 + 客户地区
  选项：
    - 实物配送：实物商品 → 仓库出库 + 物流
    - 虚拟自动：虚拟商品 → 系统自动发送
    - 等待拼团：团购商品 + 未成团 → 等待
    - 物流直发：合作品牌 → 品牌仓库直发
  配置参数：
    - partnerRegions: [list]
    - groupBuyMinCount: 10

可变点 3：发货时间
  所在步骤：Step 6
  变化维度：订单时间 + 库存状态
  选项：
    - 当天发货：工作时间订单 + 库存充足 → 立即出库
    - 次日发货：下班或库存需补 → 次日出库
    - 约定时间：大单 → 按承诺时间出库
  配置参数：
    - businessHours: [9:00-18:00]
    - largeOrderThreshold: 50 items
```

### 扩展点定义

```
扩展点 1：订单创建前置检查（模式：前置条件检查）
  位置：Step 1 完成之后、Step 2 之前
  目的：在正式处理前，确保订单符合基本业务规则
  检查项：
    - 客户账户是否被冻结
    - 商品是否已下架
    - 订单是否在受限地区
  配置：
    checkpointsEnabled: [account_frozen, product_listed, region_restricted]

扩展点 2：风险处理（模式：后置操作处理）
  位置：Step 2 完成之后
  目的：检查通过后，执行不同的跟进操作
  操作：
    - 发送 Webhook 给风控系统（异步）
    - 记录检查日志（异步）
    - 更新用户风险评分（可选异步）
  配置：
    handlers:
      - riskWebhook: async
      - auditLog: sync
      - scoreUpdate: async

扩展点 3：发货方式选择（模式：条件路由）
  位置：Step 5
  目的：根据商品和地区，选择最优发货路线
  路由规则：
    rule_1: if product.type == PHYSICAL and !isRestrictedRegion → 标准物流
    rule_2: if product.type == VIRTUAL → 自动发送
    rule_3: if product.type == GROUPBUY and !groupFull → 等待拼团
    rule_4: if isPartnerRegion and hasPartnerStock → 直发
  配置：
    routingTable: [见下方路由矩阵]

扩展点 4：发货后处理（模式：并行处理）
  位置：Step 7
  目的：订单发货后，触发多个独立的后续处理
  并行任务：
    task_1: 发送邮件通知（5s 超时，可失败）
    task_2: 更新积分（3s 超时，不可失败）
    task_3: 申请发票（10s 超时，可失败）
    task_4: 分析数据（无超时，异步）
  配置：
    timeout: 15s
    failureStrategy: CONTINUE  # 单个任务失败不影响其他
```

### 异常处理

```
异常 1：库存不足
  触发条件：Step 4 检查库存时，实际库存 < 需求数量
  处理方式：
    - 如果有部分库存：通知客户可以分次发货，或等待补库
    - 如果无库存：退款 + 取消订单 + 发送道歉邮件
  恢复步骤：取消订单，回到初始状态，释放库存锁

异常 2：支付失败
  触发条件：Step 3 支付网关返回失败
  处理方式：
    - 重试最多 3 次（每次间隔 5 分钟）
    - 如果全部失败：取消订单，通知客户重新支付
  恢复步骤：回到 Step 3，重新支付

异常 3：发货地址无效
  触发条件：Step 6 仓库系统无法识别地址
  处理方式：
    - 通知客户确认地址
    - 等待客户反馈（24 小时超时）
    - 如果无反馈：冻结订单，人工处理
  恢复步骤：更新地址后，重新入队发货

异常 4：部分发货失败
  触发条件：Step 7 某个并行任务失败
  处理方式：
    - 记录失败任务
    - 自动重试 2 次（如果支持重试）
    - 人工报警（如果多次失败）
  恢复步骤：修复问题后，重试失败的任务
```

## 关键建议

1. **完整性**：确保所有 Happy Path 步骤都明确
2. **可变性识别**：列出所有已知的业务变化
3. **扩展点设计**：不超过 5 个，优先使用简单模式
4. **异常处理**：覆盖最常见的 3-5 个异常
5. **可观测性**：每一步都应该有可追踪的事件或日志
6. **定期评审**：每季度审查流程是否有新的变化或异常出现
