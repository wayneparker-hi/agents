# 可变性分析指南

## 什么是可变点？

**定义**：业务流程中，在不同的条件、角色或情景下会有不同的处理方式的地方。

**关键特征**：
- 同一个流程的多种实现方式
- 由具体的业务条件决定
- 不是异常，是正常的业务变化

## 识别可变点

### 方法 1：按条件分类

**维度：金额**
```
订单处理流程
├─ 金额 <= 1000 元：自动通过
└─ 金额 > 1000 元：需要审批

可变点：需要审批 (是/否)
参数：金额阈值
```

**维度：用户类型**
```
订单处理流程
├─ VIP 用户：跳过审批，直接发货
├─ 普通用户：需要审批
└─ 新用户：严格审批 + 人工核实

可变点：审批策略
参数：用户等级
```

**维度：商品类型**
```
发货流程
├─ 实物商品：走物流
├─ 虚拟商品：直接发送
└─ 团购商品：等待拼团成功

可变点：发货方式
参数：商品类型
```

### 方法 2：按责任人分类

```
订单处理流程
├─ 自动处理（系统）：库存检查、支付、订单生成
├─ 手动处理（人工）：订单审批
└─ 外包处理（第三方）：物流、售后

可变点：谁来负责这一步
```

### 方法 3：按时间分类

```
订单处理流程
├─ 同步处理：订单创建、支付
└─ 异步处理：发货通知、发票生成

可变点：处理方式（同步/异步）
```

## 可变点的文档格式

### 标准模板

```
可变点：[名称]

所在流程步骤：[哪一步可能变化]

变化维度：[什么条件导致变化]

变化选项：
1. [选项 1 名称]
   条件：[何时选择]
   处理方式：[如何处理]
   责任人：[谁来处理]

2. [选项 2 名称]
   条件：[何时选择]
   处理方式：[如何处理]
   责任人：[谁来处理]

配置参数：[需要配置的参数]
```

### 实际例子

```
可变点：订单审批

所在流程步骤：订单创建后、发货前

变化维度：订单金额 + 用户信用等级

变化选项：
1. 自动通过
   条件：金额 <= 1000 元 且 用户信用等级 >= 3
   处理方式：直接确认，无需人工审批
   责任人：系统自动

2. 自动审批（快速）
   条件：金额 <= 5000 元 且 用户信用等级 >= 2
   处理方式：发送通知给审批员，期限 24 小时
   责任人：订单审批员

3. 人工审批（严格）
   条件：金额 > 5000 元 或 用户信用等级 < 2
   处理方式：电话确认或视频核实
   责任人：高级审批员

4. 拒绝
   条件：用户有欺诈记录 或 金额异常
   处理方式：拒绝订单，返款，记录原因
   责任人：风控团队

配置参数：
- autoApprovalThreshold: 1000 (金额阈值)
- creditLevelThreshold: 3
- approvalTimeout: 24h
```

## 可变点的管理

### 记录可变点

创建可变点矩阵：

```
流程步骤 | 可变点 | 变化维度 | 选项数 | 优先级
---------|--------|---------|--------|-------
订单创建 | 审批需求 | 金额+等级 | 4 | 高
订单创建 | 风险检查 | 地址+金额 | 3 | 高
发货 | 仓库选择 | 商品+地区 | 2 | 中
发货 | 物流选择 | 地区+时效 | 5 | 中
```

### 实现可变点

**方法 1：配置表**
```
在数据库中配置各个可变点的参数：
- approval_threshold: 1000
- approval_levels: 3
- risk_check_enabled: true
```

**方法 2：策略模式**
```java
interface ApprovalStrategy {
    approve(order: Order): boolean
}

class AutoApprovalStrategy implements ApprovalStrategy { ... }
class ManualApprovalStrategy implements ApprovalStrategy { ... }
class RiskBasedApprovalStrategy implements ApprovalStrategy { ... }
```

**方法 3：规则引擎**
```
if amount > 5000 then requiresApproval = true
if userCreditLevel < 2 then requiresApproval = true
if userHasFraudRecord then reject = true
```

## 常见的可变点模式

### 模式 1：金额阈值
```
不同的金额范围有不同的处理流程
- 小订单：快速处理
- 中等订单：标准处理
- 大额订单：特殊处理
```

### 模式 2：用户分级
```
不同等级用户有不同的权限和流程
- VIP：优先处理、特殊折扣
- 普通：标准处理
- 新用户：额外验证
```

### 模式 3：商品分类
```
不同类型商品有不同的发货方式
- 实物：物流配送
- 虚拟：自动发送
- 团购：等待拼团
```

### 模式 4：地理位置
```
不同地区有不同的处理流程
- 本地：快速
- 远程：标准
- 国际：特殊
```

### 模式 5：时间窗口
```
不同时间段有不同的处理策略
- 工作日：标准处理
- 节假日：延迟处理
- 高峰期：简化流程
```

## 可变性 vs 扩展性

### 区别

**可变性**：流程中存在的多个合法变化
- 已知的、固定的选项数
- 由业务条件决定
- 需要配置和参数化

**扩展性**：系统应该支持未来的新需求
- 可能的变化未知
- 设计时考虑灵活性
- 用扩展点设计

### 处理方式

**可变性**：
```
在流程设计时就考虑，用参数、策略、规则引擎来处理
```

**扩展性**：
```
在架构设计时考虑，预留接口和钩子供未来扩展
```

---

**关键建议**：
1. 列出所有已知的可变点
2. 对每个可变点，明确参数和配置
3. 不要过度设计，只处理真正会发生的变化
4. 定期评审可变点，看是否有新的变化产生
