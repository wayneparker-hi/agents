# 质量属性冲突识别与解决模板

本模板帮助您系统地识别和解决应用架构中的质量属性冲突。

## 第 1 步：质量属性清单和优先级

### 关键质量属性定义

```
□ 性能（Performance）
  定义：系统响应请求的速度
  量化方式：
    ├─ 响应时间（latency）：P95 < 200ms
    ├─ 吞吐量（throughput）：> 5000 req/s
    └─ 并发用户数：> 10000

□ 可靠性（Reliability）
  定义：系统在故障下继续运行的能力
  量化方式：
    ├─ 可用性（availability）：99.9%
    ├─ 平均故障时间（MTBF）：> 720 小时
    └─ 恢复时间（RTO）：< 30 分钟

□ 一致性（Consistency）
  定义：数据在所有副本中保持一致的程度
  量化方式：
    ├─ 数据同步延迟：< 1 秒
    ├─ 异常数据率：< 0.01%
    └─ 冲突解决时间：< 5 分钟

□ 安全性（Security）
  定义：系统抵抗攻击的能力
  量化方式：
    ├─ 认证覆盖率：100%
    ├─ 数据加密：传输 + 存储
    └─ 审计日志：100%

□ 可扩展性（Scalability）
  定义：系统处理增长的能力
  量化方式：
    ├─ 水平扩展能力：可添加 N 个节点
    ├─ 成本增长率：< 线性增长
    └─ 最大容量：> 1 千万用户

□ 可维护性（Maintainability）
  定义：系统修改和改进的难度
  量化方式：
    ├─ 代码复杂度：平均 cyclomatic complexity < 5
    ├─ 测试覆盖率：> 80%
    └─ 文档完整度：> 90%

... （根据实际业务添加更多属性）
```

### 优先级排序

```
优先级排序方法：
  1. 列出所有需要的质量属性
  2. 从中选择最重要的 3-5 个（P1）
  3. 其次重要的 3-5 个（P2）
  4. 其他的列为 P3

对于电商系统的示例：

┌─────────────────┬──────┬─────────────────────────┐
│ 质量属性        │ 优先级│ 理由                   │
├─────────────────┼──────┼─────────────────────────┤
│ 性能            │ P1   │ 用户体验关键，转化率   │
│ 可靠性          │ P1   │ 收入直接相关           │
│ 一致性          │ P1   │ 订单和支付数据准确性   │
│ 安全性          │ P2   │ 重要但可借助第三方     │
│ 可扩展性        │ P2   │ 未来需要，可逐步优化   │
│ 可维护性        │ P3   │ 长期考虑               │
└─────────────────┴──────┴─────────────────────────┘

说明：
  - P1：绝不妥协，必须满足
  - P2：尽力满足，有冲突时次于 P1
  - P3：有条件满足，P1/P2 没有冲突时才考虑
```

## 第 2 步：冲突识别

### 常见冲突矩阵

```
              │ 性能 │ 可靠性 │ 一致性 │ 安全性 │ 可扩展
──────────────┼──────┼────────┼────────┼────────┼────────
性能          │ ─    │ ✗✗    │ ✗✗    │ ✗✗    │ ✗
可靠性        │ ✗✗   │ ─      │ ○     │ ✗      │ ○
一致性        │ ✗✗   │ ○      │ ─      │ ✗      │ ✗
安全性        │ ✗✗   │ ✗      │ ✗      │ ─      │ ○
可扩展        │ ✗    │ ○      │ ✗      │ ○      │ ─

图例：
  ✗✗：强冲突（互相制约严重）
  ✗：冲突（有取舍关系）
  ○：弱冲突（可通过架构设计平衡）
  ─：自身，无冲突
```

## 第 3 步：权衡策略设计

### 分层处理方案

```
方案模板：

冲突：性能 vs 一致性

当前问题：
  └─ 为了保证所有数据强一致，需要同步写入多个副本
  └─ 导致写入延迟 > 500ms，影响用户体验

分层解决方案：

数据层（底层）：
  └─ 数据库保证强一致性（ACID 事务）
  └─ 通过主从复制，最终一致性（< 1 秒）

应用层（中间层）：
  ├─ 关键数据（订单、支付）：使用主库，强一致
  │  └─ 性能成本：可以接受（< 200ms）
  │
  └─ 非关键数据（统计、推荐）：使用从库，最终一致
     └─ 性能优：< 50ms

缓存层（顶层）：
  ├─ 热数据缓存在内存中（< 5ms）
  │  └─ 缓存可能是旧的，但用户可以刷新获得最新
  │
  └─ 缓存失效策略：
     ├─ 时间失效：10 分钟
     ├─ 主动失效：数据更新时立即失效
     └─ 延迟双删：写库后失效，再等待失效

API 设计：
  └─ 提供参数控制一致性要求
     GET /orders/{id}?consistency=strong  # 性能低，但最新
     GET /orders/{id}?consistency=eventual # 性能高，可能延迟
     GET /orders/{id}  # 默认（自动选择）

结果：
  ├─ 关键操作保证一致性
  ├─ 大多数操作获得性能
  └─ 用户体验和数据准确都满足
```

## 第 4 步：验证和监控

### 权衡效果验证

```
验证清单：

□ 是否满足优先级 P1 的要求？
  ├─ 所有 P1 属性都满足 ✓ / 部分满足 △ / 不满足 ✗
  └─ 如果未满足，解释原因：_____________

□ P2 属性的满足情况如何？
  ├─ 满足 ✓ / 部分满足 △ / 未满足但可接受 ✗
  └─ 改进计划：_________________________

□ 是否产生了新的冲突或问题？
  ├─ 无 ✓ / 有小问题 ⚠️ / 有大问题 ❌
  └─ 需要调整的方案：___________________

□ 团队是否理解权衡方案？
  ├─ 充分理解 ✓ / 基本理解 ○ / 不理解 ✗
  └─ 需要补充说明的内容：______________
```

### 监控指标

```
为权衡方案建立监控：

指标 1：性能指标
  ├─ P50 响应时间：____ ms
  ├─ P95 响应时间：____ ms
  ├─ P99 响应时间：____ ms
  └─ 告警阈值：> 300ms（P95）

指标 2：一致性指标
  ├─ 数据同步延迟：____ 秒
  ├─ 不一致数据比例：____ %
  └─ 告警阈值：> 1% 或 > 5 分钟

指标 3：可靠性指标
  ├─ 可用性：_____%
  ├─ 故障恢复时间：____ 分钟
  └─ 告警阈值：< 99.9% 或 > 30 分钟

定期评估（每月）：
  □ 指标是否符合预期？
  □ 需要调整权衡方案吗？
  □ 用户反馈如何？
  □ 运维成本是否可接受？
```

## 常见权衡方案速查表

```
如果需要：性能 + 一致性
  → 分层处理（见上文）
  → 或考虑单体应用（不分布式）

如果需要：性能 + 可靠性
  → 使用缓存 + 降级
  → 缓存失败时降级服务
  → 接受可靠性下降（容错能力强）

如果需要：一致性 + 可扩展性
  → 数据分片（分区）
  → 每个分区独立一致
  → 跨分区最终一致

如果需要：性能 + 安全性
  → 分离认证和业务逻辑
  → 使用快速安全校验（如 JWT）
  → 避免在关键路径上做复杂校验

如果需要：可靠性 + 成本
  → 分层 SLA（关键高，非关键低）
  → 使用云自动扩展（只为需要的容量付费）
  → 定期评估是否真需要当前 SLA
```
