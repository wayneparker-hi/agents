# 可靠性与成本权衡分析

## 概述

构建高可靠系统需要投入大量成本。本文帮助您理解这个权衡，制定合理的可靠性目标。

---

## SLA 与成本的关系

### SLA 定义

```
SLA（服务级别协议）定义了系统的可靠性承诺

可用性等级：
  99%（2 个 9）    │ 年停机时间：3.65 天      │ 每分钟价值：$ ___
  99.5%            │ 年停机时间：1.83 天      │
  99.9%（3 个 9）  │ 年停机时间：8.6 小时     │
  99.95%           │ 年停机时间：4.3 小时     │
  99.99%（4 个 9） │ 年停机时间：52 分钟      │
  99.999%（5 个 9）│ 年停机时间：5.3 分钟     │

每提升一个"9"的成本倍数：
  99% → 99.5%：成本 × 1.5
  99.5% → 99.9%：成本 × 1.5
  99.9% → 99.99%：成本 × 2-3（开始用到高端硬件）
  99.99% → 99.999%：成本 × 3-5（需要多地区、专业团队）
```

### 成本分解

**实现 99.9% 的成本：**

```
基础设施（$5k/月）：
  ├─ 2-3 台服务器（$2k）
  ├─ 数据库（$2k）
  └─ 监控和备份（$1k）

运维成本（$3k/月）：
  ├─ 1 个全职运维（$2k 工资）
  └─ 工具和许可证（$1k）

故障处理（$2k/月）：
  ├─ 平均故障修复时间：4 小时
  ├─ 故障频率：每月 1-2 次
  └─ 人力成本（修复 + 验证）

总成本：$10k/月
```

**实现 99.99% 的额外成本：**

```
多地区部署（+$10k/月）：
  ├─ 第二个数据中心或云区域（+$5k）
  ├─ 实时数据同步（+$3k）
  └─ 跨地区故障转移（+$2k）

增强监控（+$5k/月）：
  ├─ 实时监控系统（+$2k）
  ├─ 告警系统（+$2k）
  ├─ 日志聚合（+$1k）

增强运维（+$8k/月）：
  ├─ 增加到 2-3 个运维工程师（+$5k）
  ├─ 7×24 on-call 轮班（+$2k）
  └─ 专业知识和培训（+$1k）

自动故障转移（+$5k/月）：
  ├─ 开发和维护故障转移系统
  └─ 定期演练和测试

总额外成本：+$28k/月
总成本：$38k/月（原来的 4 倍！）
```

## 分层 SLA 策略

### 核心原则

```
不同的应用有不同的重要性，应该有不同的 SLA 目标

关键应用 >> 重要应用 >> 普通应用 >> 试验应用

成本和可靠性分布：
  关键应用：10% 的应用，占 50% 的成本，99.99% 可用性
  重要应用：20% 的应用，占 30% 的成本，99.9% 可用性
  普通应用：40% 的应用，占 15% 的成本，99.5% 可用性
  试验应用：30% 的应用，占 5% 的成本，95% 可用性
```

### 分类标准

```
如何判断应用的重要性？

关键应用：
  ├─ 直接影响收入
  │  例：支付系统、订单系统、库存系统
  │
  ├─ 故障导致用户流失
  │  例：登录系统、搜索系统
  │
  └─ 监管或法律要求
     例：财务记录、审计日志

重要应用：
  ├─ 影响用户体验但不影响核心业务
  │  例：推荐系统、分析系统
  │
  ├─ 故障时可以降级运行
  │  例：缓存层、非关键数据
  │
  └─ 可以使用备用方案
     例：图片服务（使用占位符）

普通应用：
  ├─ 可选功能
  │  例：用户评论、点赞、分享
  │
  ├─ 不影响核心业务流程
  │
  └─ 故障时可以完全不可用

试验应用：
  ├─ 新功能或 A/B 测试
  ├─ 可能的高风险
  └─ 用户理解可能不稳定
```

### 电商系统的分层 SLA 示例

```
┌──────────────────┬────────┬──────────────┬────────┐
│ 应用             │ 分类   │ SLA 目标     │ 成本   │
├──────────────────┼────────┼──────────────┼────────┤
│ 支付系统         │ 关键   │ 99.99%       │ $50k   │
│ 订单系统         │ 关键   │ 99.99%       │ $45k   │
│ 库存系统         │ 关键   │ 99.99%       │ $40k   │
│ 推荐系统         │ 重要   │ 99.9%        │ $15k   │
│ 分析系统         │ 重要   │ 99.9%        │ $12k   │
│ 评论系统         │ 普通   │ 99.5%        │ $5k    │
│ A/B 测试         │ 试验   │ 95%          │ $2k    │
├──────────────────┼────────┼──────────────┼────────┤
│                  │        │ 加权平均     │ $169k  │
└──────────────────┴────────┴──────────────┴────────┘

单位：USD/月

如果所有应用都要 99.99%：
  成本会是：$50k + $45k + $40k + $25k + $20k + $15k + $10k = $205k

分层策略节省：$205k - $169k = $36k/月 = $432k/年
```

## 成本优化策略

### 策略 1：精准的 SLA 目标

```
常见的过度设计：
  ❌ "所有应用都要 99.99%，绝对可靠"
  ❌ 结果：成本极高，但其实不必要

正确做法：
  ✅ 根据业务价值设定 SLA
  ✅ 定期评估是否真正需要当前 SLA
  ✅ 降低不必要的 SLA 目标

问题清单：
  □ 您最后一次 99.99% 故障是什么时候？
  □ 那次故障对业务的影响有多大？
  □ 是否可以接受降低到 99.9%？
  □ 降低 SLA 能节省多少成本？
```

### 策略 2：分散关键性

```
不要将所有功能都依赖于一个高可靠系统

反例：单一支付系统（99.99%）
  ├─ 成本：极高
  ├─ 复杂度：极高
  └─ 维护：困难

改进方案：分散可靠性
  ├─ 支付网关（99.99%，依赖第三方）
  ├─ 支付验证（99.9%，自建）
  ├─ 支付通知（99.5%，可以延迟）
  └─ 支付统计（99%，不影响业务）

好处：
  ✅ 只有关键部分需要极高可靠性
  ✅ 其他部分可以用成本更低的方案
  ✅ 总体可靠性仍然很高
```

### 策略 3：使用托管服务

```
自建 99.99% 的成本：
  └─ 需要多地区部署、专业团队、专业工具
  └─ 总成本：$50k+/月

使用云服务 99.99%：
  └─ 仅需 SLA 成本（$5-10k/月）
  └─ 云厂商负责基础设施
  └─ 总成本：$10-15k/月

成本节省：75% 以上

但注意：
  ├─ 厂商的 SLA 是否足够？
  ├─ 是否有锁定风险？
  ├─ 是否符合合规要求？
```

## 故障恢复相关成本

### RTO 与 RPO

```
RTO（Recovery Time Objective）= 故障到恢复的时间
RPO（Recovery Point Objective）= 允许丢失的最大数据量

关系图：
        RTO
        ↓
  故障发生 → [停机时间] → 恢复完成
        ↑                    ↑
      RPO                 恢复完成时数据是多久前的？

例子：银行系统
  RTO：< 1 小时（无法承受长时间故障）
  RPO：< 5 分钟（不能丢失太多交易数据）

例子：社交媒体日志
  RTO：< 24 小时（可以容忍一段时间不可用）
  RPO：< 1 小时（可以丢失最近 1 小时的日志）

成本与 RTO/RPO 的关系：
  RTO < 15 分钟：需要实时故障转移，成本 ★★★★★
  RTO 15-60 分钟：需要快速恢复机制，成本 ★★★★
  RTO 1-4 小时：需要快照恢复，成本 ★★★
  RTO > 4 小时：可以手动恢复，成本 ★★

  RPO < 1 分钟：需要实时复制，成本 ★★★★★
  RPO 1-5 分钟：需要近实时复制，成本 ★★★★
  RPO 5-60 分钟：可以周期性备份，成本 ★★★
  RPO > 1 小时：可以定期备份，成本 ★★
```

### 备灾成本

```
无备灾：
  成本：$0
  故障恢复时间：数小时到数天
  数据丢失：可能很多

冷备灾（定期备份）：
  成本：$2k/月
  故障恢复时间：1-2 天
  数据丢失：最近几小时
  适合：非关键应用

温备灾（定期同步）：
  成本：$10k/月
  故障恢复时间：15-60 分钟
  数据丢失：< 5 分钟
  适合：重要应用

热备灾（实时故障转移）：
  成本：$30k+/月
  故障恢复时间：< 1 分钟（自动）
  数据丢失：接近 0
  适合：关键应用
```

## 决策框架

### 可靠性投资决策

```
每次投资可靠性时，问自己：

Q1：这个故障对业务的影响有多大？
  ├─ 不可接受的损失（影响收入、用户流失）→ 投资
  ├─ 可以接受的损失（用户不满意但可以承受）→ 评估
  └─ 可以忽略的影响（用户基本无感）→ 不投资

Q2：故障发生的概率有多高？
  ├─ 很高（经常发生）→ 必须投资修复根本问题
  ├─ 中等（每月几次）→ 评估投资回报
  └─ 很低（几年才发生一次）→ 考虑接受

Q3：投资 $X 能将故障概率降低多少？
  ├─ 能大幅降低（如 50%+）→ ROI 高，投资
  ├─ 能略微降低（如 10-20%）→ 评估
  └─ 降低空间不大 → 不投资

Q4：有无更便宜的替代方案？
  ├─ 有（使用托管服务、降级方案等）→ 优先
  └─ 没有 → 评估自建成本
```

## 总结

```
可靠性与成本的权衡原则：

1. 不是所有应用都需要 99.99%
   → 根据业务价值分类

2. 每个"9"的成本呈指数增长
   → 从 99% 到 99.99% 成本翻 10 倍

3. 使用托管服务往往更经济
   → 不要重复造轮子

4. 分散关键性
   → 只有关键部分需要极高可靠性

5. 定期评估和调整
   → 不要固守过时的 SLA 目标

正确做法：
  ✅ 明确的分层 SLA 策略
  ✅ 按业务价值投资
  ✅ 定期评估和优化
  ✅ 成本和可靠性的合理权衡
```
