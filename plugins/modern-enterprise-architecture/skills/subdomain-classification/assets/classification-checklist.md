# 子域分类检查清单

## Phase 1：识别子域

### 步骤 1：列举所有业务流程

```
□ 主流程识别（5-10 个）
  - 流程 1：商品发布到销售的流程
  - 流程 2：用户下单到收货的流程
  - 流程 3：...

□ 流程图绘制
  - 使用图表（BPMN、泳道图）展示每个流程
  - 标记参与者和关键步骤

□ 识别关键概念
  - 每个流程涉及哪些核心概念？
  - 例：订单流程涉及 Order, OrderLine, Customer, Product

□ 识别子域候选
  - 每个流程对应一个潜在子域
  - 例：订单流程 → 订单子域
```

### 步骤 2：分组相关概念

```
□ 聚合相关概念
  订单相关：
    - Order（聚合根）
    - OrderLine
    - OrderStatus
    - ShippingAddress
    → 这些都属于订单子域

  库存相关：
    - Inventory（聚合根）
    - Stock
    - StockAllocation
    - WarehouseLocation
    → 这些都属于库存子域

□ 检查内聚性
  - 同一子域内的概念是否相关？
  - 如果相关性弱，考虑拆分或合并

□ 检查边界清晰性
  - 概念是否清晰属于某个子域？
  - 如果模糊，检查是否需要调整边界
```

### 步骤 3：命名子域

```
□ 命名规范
  - 使用业务术语，不用技术术语
  ✓ Good：订单子域、库存子域
  ✗ Bad：OrderService、InventoryDB

□ 命名清晰性
  - 名字应该清晰表达职责
  - 避免含糊的名字
  ✓ Good：推荐算法子域
  ✗ Bad：算法子域、系统子域

□ 一致性
  - 同类子域使用一致的命名模式
  ✓ Good：订单子域、库存子域、支付子域
  ✗ Bad：Order 处理、库存管理、Payment 子域
```

## Phase 2：分类子域

### 步骤 1：评估差异化程度

```
问题：我们相比竞争对手的优势在这里吗？

评分标准（1-10 分）：

10 分：核心竞争力
  □ 直接贡献收入
  □ 竞争对手难以复制
  □ 我们有独特的算法或流程
  例：推荐算法

8-9 分：重要优势
  □ 支持主业务
  □ 有我们的特色
  □ 竞争对手可以复制，但需要时间
  例：订单管理（我们有特殊的定价或审批规则）

5-7 分：基础能力
  □ 必需但非差异化
  □ 竞争对手做法类似
  例：用户管理

1-4 分：完全通用
  □ 所有人都一样
  □ 有现成的解决方案
  □ 自己实现没有优势
  例：支付处理

□ 为每个子域评分
  - 子域 1：_____ 分
  - 子域 2：_____ 分
  - ...
```

### 步骤 2：评估战略重要性

```
问题：这个子域对我们的战略有多重要？

评分标准（1-10 分）：

10 分：战略核心
  □ 与 3-5 年战略直接相关
  □ 改进能显著提升竞争力
  例：推荐算法（战略是提升转化率 30%）

8-9 分：战略重要
  □ 与战略相关
  □ 改进能带来中等收益
  例：订单管理（与战略"提升用户满意度"相关）

5-7 分：基础支撑
  □ 不直接相关战略，但必需
  □ 改进收益一般
  例：用户认证

1-4 分：可选或边缘
  □ 与战略无关
  □ 改进收益低
  例：数据报告功能

□ 为每个子域评分
  - 子域 1：_____ 分
  - 子域 2：_____ 分
  - ...
```

### 步骤 3：分类决策

```
分类规则：
┌───────────────────────────┬──────────────┐
│ 条件                      │ 分类         │
├───────────────────────────┼──────────────┤
│ 差异化 >= 8 分            │ 核心域       │
│ 且战略重要性 >= 8 分      │              │
├───────────────────────────┼──────────────┤
│ 差异化 >= 5 分            │ 支持域       │
│ 或战略重要性 >= 6 分      │              │
├───────────────────────────┼──────────────┤
│ 差异化 < 5 分             │ 通用域       │
│ 且战略重要性 < 6 分       │              │
└───────────────────────────┴──────────────┘

□ 应用分类规则
  - 子域 1：____________ → 分类：_______
  - 子域 2：____________ → 分类：_______
  - ...

□ 检查比例
  - 核心域：应该占 20-40%
  - 支持域：应该占 30-50%
  - 通用域：应该占 20-30%

  当前比例：
    - 核心域：____% （应该 ___% → 调整）
    - 支持域：____% （应该 ___% → 调整）
    - 通用域：____% （应该 ___% → 调整）
```

## Phase 3：验证分类

### 步骤 1：检查内聚性

```
对每个子域，检查：

□ 概念内聚性：
  - 子域内的概念是否紧密相关？
  ✓ Good：订单子域包含 Order, OrderLine, OrderStatus
  ✗ Bad：订单子域包含 Order, User, Product

□ 职责内聚性：
  - 子域内的职责是否相关？
  ✓ Good：订单子域负责订单的全生命周期
  ✗ Bad：订单子域既负责订单又负责支付

□ 数据内聚性：
  - 子域内的数据是否紧密相关？
  ✓ Good：订单子域包含订单表、订单行表
  ✗ Bad：订单子域包含订单表、用户表、商品表
```

### 步骤 2：检查耦合度

```
子域间的依赖关系（✓ = 有依赖）：

        │ 订单│ 库存│ 支付│ 用户│
────────┼─────┼─────┼─────┼─────┤
订单    │  -  │  ✓  │  ✓  │  ✓  │
库存    │  -  │  -  │  -  │  -  │
支付    │  -  │  -  │  -  │  ✓  │
用户    │  -  │  -  │  -  │  -  │

检查项：
□ 是否有循环依赖？
  - 订单 → 库存 → 订单？NO ✓
  - 发现循环？→ 需要重新划分边界

□ 是否有过多的双向依赖？
  - 双向依赖数 / 总依赖数 = ___% （应该 < 20%）

□ 是否有过多的跨域调用？
  - 跨域调用数 / 总调用数 = ___% （应该 < 30%）
```

### 步骤 3：检查可操作性

```
对每个子域，检查：

□ 团队是否能独立负责？
  - 有对应的团队或人员？
  - 是否有明确的所有者？

□ 是否能独立部署？
  - 修改这个子域不会影响其他子域吗？
  - 是否可以独立发版？

□ 是否能独立扩展？
  - 添加新功能时是否只需修改这个子域？
  - 是否容易添加新的变种或策略？

□ 边界是否清晰？
  - 能否清晰地说出"什么在这个子域，什么不在"？
```

## Phase 4：制定行动计划

### 步骤 1：识别问题

```
常见问题：

□ 边界不清晰
  症状：团队不知道谁负责什么
  解决：重新定义边界，分配清晰的所有权

□ 耦合度过高
  症状：修改一个子域需要修改其他子域
  解决：通过 API 或事件驱动解耦

□ 子域粒度不合适
  症状：子域过大（难以维护）或过小（管理开销大）
  解决：合并相关子域或拆分大子域

□ 缺少关键子域
  症状：某些功能无人维护或分散在多个子域
  解决：新增专门的子域

□ 比例失衡
  症状：核心域太多或太少
  解决：重新评估和重新分类

□ 人员分配不匹配
  症状：最好的团队在通用域
  解决：重新分配人员到核心域
```

## Phase 5：定期评审

### 步骤 1：季度评审

```
每季度评审：

□ 子域分类是否仍然适用？
  - 有战略变更吗？
  - 有市场变化吗？
  - 是否需要调整？

□ 成熟度变化
  - 哪些子域成熟度在提升？
  - 哪些子域有问题？

□ 耦合度变化
  - 是否有新的跨域调用？
  - 耦合度是否在上升？

□ 人员配置
  - 团队规模是否匹配重要性？
  - 是否有人力缺口？
```

### 步骤 2：年度深度评审

```
每年评审一次：

□ 完整的分类重评
  - 是否需要调整某个子域的分类？
  - 是否有新的子域需要新增？
  - 是否有子域可以合并或拆分？

□ 策略调整
  - 核心域的投资是否足够？
  - 通用域是否有更好的第三方方案？

□ 组织结构调整
  - 是否需要创建新团队？
  - 是否需要调整团队职责？

□ 文档更新
  - 更新架构文档
  - 更新团队的职责说明
  - 传达给所有相关人员
```

## 完整检查清单

```
整体检查：
  ✓ 是否明确列出了所有子域？
  ✓ 是否为每个子域分配了分类？
  ✓ 是否建立了清晰的边界？
  ✓ 是否分配了负责人或团队？
  ✓ 是否制定了投资计划？
  ✓ 是否有跨团队协调机制？

可行性检查：
  ✓ 是否有足够的资源？
  ✓ 是否有实现的技术方案？
  ✓ 是否有明确的时间表？
  ✓ 是否有成功的度量指标？

沟通检查：
  ✓ 是否与领导层对齐？
  ✓ 是否与所有团队沟通？
  ✓ 是否有相关文档？
  ✓ 是否有定期评审机制？
```

## 关键建议

1. **从业务开始**：先理解业务，再进行分类
2. **包容性**：让跨职能的人参与分类讨论
3. **迭代改进**：不要期望一次完美，定期调整
4. **文档记录**：记录分类决策的原因，便于未来审视
5. **传达清晰**：确保所有人理解分类和职责
6. **监督执行**：定期检查是否按照分类执行
