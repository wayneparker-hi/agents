# 子域边界设计

## 边界划分的原则

### 原则 1：业务内聚，松耦合

```
内聚（Cohesion）：同一个子域内的概念相关性强
┌─────────────────────────────┐
│ 订单子域                    │
│ ├─ Order              ✓ 相关
│ ├─ OrderLine          ✓ 相关
│ ├─ OrderStatus        ✓ 相关
│ └─ ShippingAddress    ✓ 相关
└─────────────────────────────┘

松耦合（Loose Coupling）：子域之间依赖最小
订单子域 ──→ 库存子域（通过 API）
  ↑              ↓
  └──────────────┘ 事件驱动

不是：
订单子域 ──直接调用──→ 库存子域 ❌ 紧耦合
```

### 原则 2：一致的数据模型

```
✅ 正确：每个子域有独立的数据模型

订单子域：
  ├─ Order
  ├─ OrderLine
  └─ OrderStatus

库存子域：
  ├─ Stock
  ├─ Inventory
  └─ StockAllocation

❌ 错误：多个子域共享同一个数据模型
  （如果共享，说明边界划分有问题）
```

### 原则 3：明确的职责边界

```
划分不清的例子：
┌──────────────────────────────┐
│ 订单服务（职责模糊）         │
│ ├─ 创建订单                  │
│ ├─ 库存检查？                │ ← 应该在库存子域
│ ├─ 支付处理？                │ ← 应该在支付子域
│ ├─ 发送邮件？                │ ← 应该在通知子域
│ └─ 生成报表？                │ ← 应该在分析子域
└──────────────────────────────┘

划分清晰的例子：
┌──────────────┐  ┌──────────────┐  ┌──────────────┐
│ 订单子域     │  │ 库存子域     │  │ 支付子域     │
│ ├─ 创建      │  │ ├─ 检查      │  │ ├─ 处理      │
│ ├─ 修改      │  │ ├─ 预留      │  │ ├─ 退款      │
│ └─ 取消      │  │ └─ 扣减      │  │ └─ 对账      │
└──────────────┘  └──────────────┘  └──────────────┘
```

## 边界识别方法

### 方法 1：按业务流程的主角分类

```
问题：谁是这个流程的主要责任人？

订单流程：
  主角 = 订单管理员 → 订单子域 ✓
  参与方 = 库存管理员 → 库存子域 ✓
  参与方 = 财务人员 → 支付子域 ✓

问诊流程（医疗系统）：
  主角 = 医生 → 诊疗子域 ✓
  参与方 = 病人 → 患者子域 ✓
  参与方 = 药房 → 药物子域 ✓
```

### 方法 2：按数据模型的聚合根分类

```
关键问题：谁是聚合根？

聚合根 = 子域的中心

订单域：
  聚合根 = Order
  包含 = OrderLine, OrderStatus
  不包含 = Payment（独立聚合根）

库存域：
  聚合根 = Inventory
  包含 = Stock, StockAllocation
  不包含 = Product（在商品域）
```

### 方法 3：按变更周期分类

```
问题：这些概念的变更是否独立？

独立变更 → 可能应该分离到不同子域
┌────────────────────────────────────┐
│ 订单子域                           │
│ └─ Order                           │
│    └─ 变更频率：高（随时创建/修改）│
└────────────────────────────────────┘

┌────────────────────────────────────┐
│ 商品子域                           │
│ └─ Product                         │
│    └─ 变更频率：低（偶尔更新信息）  │
└────────────────────────────────────┘

同一变更周期 → 应该在同一子域
Order 和 OrderLine 都随订单创建而变 → 同一子域 ✓
```

### 方法 4：按通信模式分类

```
同步通信多 → 考虑合并
异步通信多 → 可以分离

订单 ←→ 库存（同步：需要立即知道库存）
  → 考虑紧耦合设计或实时同步

订单 → 积分（异步：可以最终一致）
  → 事件驱动分离
```

## 常见的边界设计错误

### 错误 1：边界过粗（包含过多概念）

```
❌ 错误设计：
┌──────────────────────────────────┐
│ 订单大域                         │
│ ├─ 订单创建、修改、取消          │
│ ├─ 库存检查、扣减                │
│ ├─ 支付处理、退款                │
│ ├─ 发货管理、物流跟踪            │
│ └─ 售后、退货处理                │
└──────────────────────────────────┘

问题：
  - 职责过多，难以维护
  - 修改订单可能影响支付逻辑
  - 团队之间协作困难
  - 难以独立部署

✅ 正确设计：
┌──────────┐ ┌──────────┐ ┌──────────┐ ┌──────────┐
│ 订单     │ │ 库存     │ │ 支付     │ │ 发货     │
└──────────┘ └──────────┘ └──────────┘ └──────────┘
```

### 错误 2：边界过细（拆分过多）

```
❌ 错误设计：
┌─────┐ ┌─────┐ ┌─────┐ ┌─────┐
│创建 │ │修改 │ │查询 │ │删除 │
└─────┘ └─────┘ └─────┘ └─────┘

问题：
  - 服务太多，难以管理
  - 通信开销大
  - 部署复杂

✅ 正确设计：
┌──────────────────────┐
│ 订单子域             │
│ ├─ 创建、修改、删除   │
│ └─ 查询、分析         │
└──────────────────────┘
```

### 错误 3：沿着技术边界划分（而非业务边界）

```
❌ 错误设计（按技术分层）：
┌──────────┐
│ 持久化层 │ （所有数据库操作）
├──────────┤
│ 业务逻辑 │ （所有业务逻辑）
├──────────┤
│ API 层   │ （所有 API）
└──────────┘

问题：
  - 无法按业务独立部署
  - 团队之间协作困难
  - 无法清晰表达业务边界

✅ 正确设计（按业务分域）：
┌──────────┐ ┌──────────┐ ┌──────────┐
│ 订单     │ │ 库存     │ │ 支付     │
│ (持久+  │ │ (持久+  │ │ (持久+  │
│  逻辑+  │ │  逻辑+  │ │  逻辑+  │
│  API)   │ │  API)   │ │  API)   │
└──────────┘ └──────────┘ └──────────┘
```

### 错误 4：沿着组织结构划分（而非业务边界）

```
❌ 错误设计（按团队）：
我们有订单团队和库存团队
  → 所以订单子域 = 订单团队的代码
  → 库存子域 = 库存团队的代码

问题：
  - 如果重组会很痛苦
  - 边界不稳定
  - 无法真实反映业务

✅ 正确做法：
  - 业务边界优先
  - 团队结构跟随业务边界（反向）
```

## 跨边界通信设计

### 模式 1：事件驱动（异步）

**适合场景**：最终一致性、可以延迟

```
订单子域：
  Order.create() → 发布 OrderCreatedEvent

库存子域：
  监听 OrderCreatedEvent
  → 检查库存
  → 发布 StockAllocatedEvent

支付子域：
  监听 StockAllocatedEvent
  → 处理支付

优点：
  ✅ 子域完全独立
  ✅ 可以轻松添加新的监听者
  ✅ 易于扩展

缺点：
  ❌ 最终一致性，有延迟
  ❌ 调试困难
  ❌ 需要补偿机制
```

### 模式 2：API 调用（同步）

**适合场景**：需要立即得到结果、强一致性

```
订单子域：
  createOrder() {
    result = inventoryService.checkStock(items)
    if (!result.available) {
      throw InsufficientStockException()
    }
    // 创建订单
  }

优点：
  ✅ 实时性强
  ✅ 易于理解和调试

缺点：
  ❌ 子域耦合
  ❌ 库存服务故障会影响订单创建
  ❌ 性能取决于最慢的服务
```

### 模式 3：编排服务（Saga）

**适合场景**：多个子域协调、需要补偿

```
OrderOrchestrator:
  1. 创建订单 → OrderService
  2. 等待结果，如果失败 → 补偿

  3. 检查库存 → InventoryService
  4. 如果失败 → 取消订单

  5. 处理支付 → PaymentService
  6. 如果失败 → 释放库存、取消订单

优点：
  ✅ 能处理复杂的多步骤
  ✅ 有补偿机制

缺点：
  ❌ 复杂度高
  ❌ 补偿逻辑困难
  ❌ 需要额外的编排服务
```

## 边界演进

### 场景 1：边界需要调整

```
初期（2 个子域）：
┌──────────────┐ ┌──────────────┐
│ 订单与库存   │ │ 支付与物流   │
└──────────────┘ └──────────────┘

发现：订单业务快速增长，变更频率高
       库存管理相对稳定

演进（4 个子域）：
┌────────┐ ┌────────┐ ┌────────┐ ┌────────┐
│ 订单   │ │ 库存   │ │ 支付   │ │ 物流   │
└────────┘ └────────┘ └────────┘ └────────┘
```

### 场景 2：新增子域

```
初期业务：电商平台
┌────────┐ ┌────────┐ ┌────────┐
│ 订单   │ │ 库存   │ │ 支付   │
└────────┘ └────────┘ └────────┘

新增需求：社交购物、直播带货
┌────────┐ ┌────────┐ ┌────────┐
│ 订单   │ │ 库存   │ │ 支付   │
└────────┘ └────────┘ └────────┘
     ▲
     │
┌────────┐ ┌────────┐
│ 社交   │ │ 直播   │
└────────┘ └────────┘
```

## 边界确认清单

```
□ 每个子域有明确的聚合根吗？
□ 子域间的依赖是否通过 API 或事件？
□ 子域内的概念内聚性强吗？
□ 子域间是否有交叉更新？（如有，考虑合并）
□ 子域的变更周期是否一致？
□ 是否可以由一个团队独立负责？
□ 是否可以独立部署？
□ 子域的名字是否清晰反映其职责？
□ 是否遗漏了重要的子域？
□ 子域粒度是否合适？
```

---

## 关键建议

1. **业务优先**：沿业务边界划分，而非技术边界
2. **聚合根优先**：围绕聚合根划分子域
3. **适度粒度**：3-5 个子域合适，太多或太少都有问题
4. **定期评审**：随着业务发展，定期重新评审边界
5. **清晰通信**：明确跨边界的通信方式
6. **演进友好**：设计能容易调整边界的架构
